## Vary presentation, not policy

An experiment changes only how the prompt and the preference center look:
variant, position, layout, primary actions, blocking. The policy rule, its
categories and its copy stay the same for every arm, so every arm records a
choice under the same policy fingerprint.

Your normal `presentation` is the `control` arm. Every other arm lists only
what it changes. Pass the arm your feature flag resolved:

```tsx title="src/app/providers.tsx"
'use client';

import { ConsentProvider, hosted } from 'c15t/react';

const bannerShape = {
	id: 'banner-shape',
	arms: {
		invasive: { prompt: { variant: 'wall' } },
	},
};

export const Providers = ({
	children,
	arm,
}: {
	children: React.ReactNode;
	arm: 'control' | 'invasive';
}) => (
	<ConsentProvider
		options={{
			mode: hosted({ url: 'https://your-project.inth.app' }),
			presentation: { prompt: { variant: 'floating', position: 'bottom-left' } },
			experiment: { ...bannerShape, arm },
		}}
	>
		{children}
	</ConsentProvider>
);
```

Or let c15t split visitors itself:

```ts
experiment: { ...bannerShape, split: { control: 60, invasive: 40 } }
```

| Field | Purpose |
| --- | --- |
| `id` | Stable experiment name, recorded with every choice |
| `arms` | What each arm changes, merged over `presentation`. `control` is your `presentation` and is not listed |
| `arm` | The arm your flag resolved: `control` or a key of `arms` |
| `split` | Relative weights when c15t picks the arm; default equal. Keys are `control` and the arms |
| `acknowledgeDiagnostics` | Run an arm that trips a presentation diagnostic and record that you reviewed it |

c15t merges the arm over `presentation`, exposes it as `snapshot.experiment`,
sends it with `/init`, and records it on the choices of visitors the banner
showed it to, so you can compare opt-in rate and time to decision per arm.

The same option exists on `c15t/next` (`ConsentRoot` options), `c15t/vue`,
`@c15t/svelte`, `@c15t/astro` and `@c15t/browser`.

`experiment` is read once, when the provider mounts. Changing it later has
no effect; remount the provider (a `key` in React) to switch experiments.

Build the experiment with `defineExperiment()` to have TypeScript check the
arm names in `arm` and `split`:

```ts
import { defineExperiment } from 'c15t';

export const bannerShape = defineExperiment({
	id: 'banner-shape',
	arms: { invasive: { prompt: { variant: 'wall' } } },
});
```

Assignment and arm validation load as a separate chunk, only on pages that
set `experiment`. A site without an experiment does not download them.

### Astro

The Astro banner is server-rendered HTML that the browser only shows or
hides, so the arm is resolved on the server. To pick it per request, set
`middleware: false` in `c15t()` and compose the consent middleware yourself
with `experimentArm`:

```ts title="src/middleware.ts"
import { consentMiddleware } from '@c15t/astro/middleware';

export const onRequest = consentMiddleware({
	experimentArm: async (context) => await bannerShapeFlag(context),
});
```

Return `undefined` to run no experiment for that request. A fixed
`experiment.arm` in `c15t()` puts every visitor in one arm, which only
suits a staged rollout. Prerendered routes render once for every visitor, so
they get no per-request arm. `c15t()` throws at config time when
`experiment` has neither.

### Vary the theme

An arm can carry `theme` overrides next to its presentation fragment. They
merge over the host `theme` one token group deep, so an arm can change one
colour or radius and keep the rest of your palette. Arrays and scalars are
replaced.

```tsx
experiment: {
	id: 'button-style',
	arms: {
		bold: {
			theme: {
				colors: { primary: '#0a0a0a' },
				radius: { lg: '4px' },
			},
		},
	},
}
```

Read the merged theme with `useResolvedTheme()` in React,
`useResolvedTheme(theme)` in Vue, `getConsentManager().theme` in Svelte and
`client.theme` in `@c15t/browser`. Astro renders the arm's tokens with the
banner. In React, `consentActions` and slot overrides apply through the
provider, but colour, radius and other tokens reach the page through
`ConsentTheme`, so render it from the resolved theme:

```tsx
'use client';

import { ConsentTheme, useResolvedTheme } from 'c15t/react';

export const ExperimentTheme = () => (
	<ConsentTheme theme={useResolvedTheme()} />
);
```

Rendered from a client component, `ConsentTheme` ships the theme generator.
With an arm from your flag, you can instead render
`<ConsentTheme theme={resolveExperimentTheme(theme, experiment, { arm })} />`
from a Server Component. Per-action styling through
`theme.consentActions` runs through the same prominence check as
presentation: an arm that fills accept and outlines reject trips
`equivalent-prominence-overridden` and needs `acknowledgeDiagnostics: true`.

## Resolve the arm with a flag provider

Resolve the arm wherever your flags live and pass its name as `arm`. c15t
records `assignedBy: 'host'` and never re-assigns a visitor you assigned.

### Vercel Flags SDK

Use the `identify` you already have and split however you like; c15t only
needs the result.

```ts title="src/flags.ts"
import { flag } from 'flags/next';

export const bannerShape = flag<'control' | 'invasive'>({
	key: 'banner-shape',
	identify, // your existing identify
	decide: ({ entities }) =>
		toPercent(entities.user.id) < 60 ? 'control' : 'invasive',
});
```

```tsx title="src/app/layout.tsx"
import { bannerShape } from '../flags';
import { Providers } from './providers';

export default async function RootLayout({
	children,
}: {
	children: React.ReactNode;
}) {
	const arm = await bannerShape();
	return (
		<html lang="en">
			<body>
				<Providers arm={arm}>{children}</Providers>
			</body>
		</html>
	);
}
```

To keep some visitors out of the experiment entirely, have the flag return a
value such as `'off'` and pass no `experiment` for it. Those visitors see
`presentation` and are not counted.

### PostHog

PostHog resolves flags asynchronously in the browser. Because `experiment`
is read once at mount, wait for the flags, then mount the provider with the
resolved arm.

```tsx title="src/app/flagged-providers.tsx"
'use client';

import { useEffect, useState } from 'react';
import posthog from 'posthog-js';

import { Providers } from './providers';

export const FlaggedProviders = ({
	children,
}: {
	children: React.ReactNode;
}) => {
	const [arm, setArm] = useState<'control' | 'invasive' | null>(null);
	useEffect(
		() =>
			posthog.onFeatureFlags(() => {
				const flag = posthog.getFeatureFlag('banner-shape');
				setArm(flag === 'invasive' ? 'invasive' : 'control');
			}),
		[]
	);
	if (arm === null) {
		// Flags not loaded yet: no provider, no banner.
		return children;
	}
	return <Providers arm={arm}>{children}</Providers>;
};
```

### LaunchDarkly, GrowthBook, Statsig

```ts
const arm = ldClient.stringVariation('banner-shape', 'control');
const arm = growthbook.getFeatureValue('banner-shape', 'control');
const arm = StatsigClient.instance()
	.getExperiment('banner-shape')
	.get('arm', 'control');
```

An `arm` that is not `control` or a key of `arms` logs an error and runs no
experiment for that visitor; the page still renders. Treat that as a flag
misconfiguration.

## Let c15t assign the arm

Omit `arm` and c15t picks one by `split` (equal by default) when the page
starts, before `/init`, and records `assignedBy: 'c15t'`. A visitor who
already saw an arm keeps it.

The banner waits until the arm is picked, so the visitor never sees the base
banner swap for their arm. On a server-rendered page that means the banner is
not in the server HTML; it appears once the browser has loaded the
assignment chunk. If the chunk fails to load, the base banner shows and no
experiment runs. To keep the banner in the server HTML, resolve the arm on
the server and pass it as `arm`.

Once the banner has shown the arm, c15t stores `{ id, arm }` under
`c15t-experiment-v1` in localStorage (a cookie when localStorage is
unavailable), so the visitor keeps seeing the banner they saw. Nothing is
stored for a visitor who is never prompted, and nothing is stored for a
host-resolved arm: your flag provider decides that one on every visit. The
record holds no identifier. It exists only to keep the consent banner
consistent, so treat it like the consent record itself when you describe
your storage.

A `split` that gives no arm a positive weight, or that names an arm that does
not exist, logs an error and runs no experiment. An arm missing from the
split gets no visitors.

```ts
experiment: {
	id: 'banner-shape',
	arms: { invasive: { prompt: { variant: 'wall' } } },
	split: { control: 60, invasive: 40 },
}
```

Changing `id` starts a new experiment and re-assigns everyone. Removing an
arm re-assigns only the visitors who were in it. For a clean analysis, change
`id` rather than editing the arms of a running experiment.

Built-in assignment is not available on `@c15t/astro`; see
[Astro](#astro).

## Acknowledge presentation diagnostics

Each arm is resolved under the visitor's policy the same way `presentation`
is. An arm that trips a diagnostic, for example
`equivalent-prominence-overridden` because it makes accept primary while
reject stays neutral, is not shown under that policy: those visitors see the
base presentation, are not counted in the experiment, and c15t logs the
diagnostics. Set `acknowledgeDiagnostics: true` to run the arm anyway. c15t
then logs the diagnostics as a warning once per policy and records
`acknowledgedDiagnostics: true` with the arm on every choice. You own the
legal review of that arm; c15t records that you made it.

The check runs in the browser once the policy is known, so catch a rejected
arm before you deploy with `validateExperiment` in a test:

```ts
import { validateExperiment } from 'c15t/experiment';

test('banner-shape arms pass under the EU policy', () => {
	validateExperiment(bannerShape, euPolicy, { presentation });
});
```

It throws for an invalid definition and for arms with unacknowledged
diagnostics.

## Read the assignment

```tsx
import {
	useExperiment,
	useResolvedPresentation,
	useResolvedTheme,
} from 'c15t/react';

const { id, arm, assignedBy } = useExperiment() ?? {};
const presentation = useResolvedPresentation();
const theme = useResolvedTheme();
```

React exposes three hooks:

- `useExperiment()` returns the assigned arm (`id`, `arm`, `assignedBy`,
  `acknowledgedDiagnostics`), or `null` while no experiment is configured
  or no arm is assigned yet.
- `useResolvedPresentation()` returns `presentation` with the assigned
  arm merged over it per surface. While no arm is assigned it returns
  `presentation` itself. The stock banner, dialog and widget render from it,
  as do `usePromptPresentation()` and `usePreferencesPresentation()`.
- `useResolvedTheme()` returns `theme` with the arm's `theme` merged one
  token group deep over it. While no arm is assigned, or the arm has no
  `theme`, it returns `theme` itself. The provider injects this merged theme.

Built-in assignment lands after mount, so `useExperiment()` is `null` on the
server render and during hydration and the resolved hooks return the base
values. The banner is held until then, and a clean preferences draft reseeds
from the arm's `preferences.defaults` when it lands. An
arm from your flag is known from the first render, on the server too.

Vue exposes `useExperiment()`, `useResolvedPresentation()` and
`useResolvedTheme(theme)`, Svelte `getConsentManager().experiment`,
`.presentation` and `.theme`, and `@c15t/browser` `client.presentation` and
`client.theme`. Every adapter also reports the arm on `snapshot.experiment`.

## What is recorded

An impression or a choice carries the arm only once the banner has shown it
in the current page. A returning visitor who reopens the preference center
from a footer link, or saves from an inline widget, never saw the arm's
banner, so their choice is recorded without it and does not count toward any
arm.

Each choice saved through `POST /subjects` carries in `metadata`:

| Key | Value |
| --- | --- |
| `experiment` | `{ id, arm, assignedBy, acknowledgedDiagnostics }` |
| `timeToDecisionMs` | Milliseconds from the surface's first impression to the action |

`uiSource` on the same record names the surface (`banner`, `dialog`,
`widget`). The `surface:shown` and `choice:recorded` kernel events and the
`onSurfaceShown` and `onChoiceRecorded` callbacks carry the same
`experiment` object, so impressions and decisions can be joined per arm in
your analytics without a backend query.

## Report impressions and choices

Set `reportTo` on the experiment and c15t sends every impression and choice to
your analytics tool. Built-in targets cover the GTM data layer and PostHog; a
function receives the same events for anything else.

```ts
experiment: {
	id: 'banner-shape',
	variants: { floating: {}, bar: { prompt: { variant: 'bar' } } },
	reportTo: 'dataLayer',
}
```

`'dataLayer'` pushes `{ event, ...properties }` onto `window.dataLayer`, so a
GTM container can fire a Custom Event trigger named `c15t_surface_shown` or
`c15t_choice_recorded` and read the properties as Data Layer Variables. GTM
merges every push into one model, so each push carries every property, set to
`undefined` when the event has none, and `confirmed` is a comma-separated
string. A later impression never inherits the previous choice's values.
`'posthog'` calls `window.posthog.capture(name, properties)`. While PostHog
is not on the page yet, up to 50 events are held for 30 seconds and sent in
order once it loads; after that they are dropped. Both targets are no-ops
during server rendering.

A function gets the camelCase event object. Pass several targets as an array.

```ts title="Segment"
import type { ExperimentReportEvent } from 'c15t';

const toSegment = ({ name, ...properties }: ExperimentReportEvent) => {
	window.analytics.track(name, properties);
};

experiment: {
	id: 'banner-shape',
	variants: { floating: {}, bar: { prompt: { variant: 'bar' } } },
	reportTo: ['dataLayer', toSegment],
}
```

A reporter that throws is logged with `console.error` and never blocks the
consent flow or the other reporters.

### Events

Every event carries the arm and the surface. The built-in targets send the
snake\_case property names; a function receives the camelCase ones.
`c15t_notice_dismissed` fires when a visitor dismisses an opt-out `notice`
prompt, which records no choice.

| Property (built-in) | Function field | `c15t_surface_shown` | `c15t_choice_recorded` | `c15t_notice_dismissed` |
| --- | --- | --- | --- | --- |
| `experiment_id` | `experimentId` | yes | yes | yes |
| `variant` | `variant` | yes | yes | yes |
| `assigned_by` | `assignedBy` | `host` or `c15t` | `host` or `c15t` | `host` or `c15t` |
| `surface` | `surface` | `banner` or `dialog` | `banner`, `dialog`, `widget` or `none` | `banner`, `dialog` or `none` |
| `shown_at` | `shownAt` | epoch ms | - | - |
| `action_at` | `actionAt` | - | epoch ms | epoch ms |
| `consent_action` | `consentAction` | - | `all`, `necessary` or `custom` | - |
| `confirmed` | `confirmed` | - | categories the action confirmed | - |
| `time_to_decision_ms` | `timeToDecisionMs` | - | ms from impression to action, when known | ms from impression to dismissal, when known |

`surface: none` means the choice or dismissal was made programmatically,
through `save()` or `dismissNotice()` with no prompt open, so it has no
impression to count against and no `time_to_decision_ms`.

### What is sent

c15t adds nothing that identifies the visitor: no subject id, no external id,
no user properties, no consent values beyond the category names confirmed.
The receiving tool may add its own. PostHog attaches its `distinct_id` and
super properties to every `capture`, and a GTM container forwards whatever
user id it is configured with. An impression fires before any consent
exists, so either treat the report as first-party, necessary-category
telemetry under your own policy, or gate it with a function that reads the
current permissions from your own runtime reference before forwarding. The
event itself carries no permissions.

```ts title="Only report once measurement is allowed"
import { createConsentRuntime } from 'c15t/runtime';

const runtime = createConsentRuntime({
	// ...
	experiment: {
		id: 'banner-shape',
		variants: { floating: {}, bar: { prompt: { variant: 'bar' } } },
		reportTo: (event) => {
			if (runtime.kernel.getSnapshot().effectivePermissions.measurement) {
				window.dataLayer?.push({ event: event.name, ...event });
			}
		},
	},
});
runtime.start();
```

Under an opt-in policy this drops the impression, since measurement is not
yet allowed when the banner appears; only the choice gets through. Use it
when the choice event alone is what your policy allows you to send.

### Read the results

Consent rates move by a few points, not by half. At a 30% base rate you need
roughly 2,500 impressions per arm to detect a 5-point change with 80% power,
and about 10,000 per arm to detect 2 points. Run a sample-size calculator
against your own base rate before you start, decide the stop date up front,
and do not stop early on a good-looking day. Most analytics tools compute the
significance for you once the two counts are grouped by arm.

The opt-in rate of an arm is the number of visitors with a
`c15t_choice_recorded` event with `consent_action: all`, divided by the number
of visitors with a `c15t_surface_shown` event with `surface: banner`, both
grouped by `experiment_id` and `variant`. Count visitors, not events: the
banner fires an impression on every page it appears on until the visitor
decides, so a small banner people ignore for a few pages collects more
impressions than a wall that forces a decision on the first. Use your tool's
unique-user count (PostHog `distinct_id`, the GA4 client id) for both sides.

The reporting target has to receive impressions from visitors who decline.
A tool that loads only after consent, such as PostHog under the loader's
`after-consent` mode, never sees a decliner's impression, so the rate trends
towards 100% and says nothing about the arm. Load the target independently of
the consent it measures, or send the events with a function to a first-party
endpoint.

Under an `opt-out` policy with `prompt: 'notice'`, dismissing the notice
records no choice, so the rate to compare is `c15t_notice_dismissed` events
per `c15t_surface_shown` event with `surface: banner`. The secondary metric
is `c15t_surface_shown` events with `surface: dialog` per banner impression:
whether the arm drove more visitors into the preference center to opt out.

Under `opt-out` with `prompt: 'choice'`, the choice event still fires. Count
`c15t_choice_recorded` events with `consent_action: necessary` per impression
as the opt-out rate.

Time to decision is the median `time_to_decision_ms` per `experiment_id` and
`variant` over the choice events. Use the median, not the mean: a visitor who
leaves the tab open skews the mean without saying anything about the arm.

## Try it

Every example app under `examples/` runs this experiment. Open
`/?experiment=1` in the React, Vue, Svelte, JavaScript and script-tag
examples, `/app-router?experiment=1` in Next.js, or
`/consent-example?experiment=1` in TanStack Start and SvelteKit; add
`&arm=wall` to see a host-resolved arm. The Nuxt and Astro examples take
static config, so start them with `NUXT_PUBLIC_C15T_EXPERIMENT=1` or
`C15T_EXPERIMENT=1`. Each page shows the assigned arm and the events it
reported to `window.dataLayer`.

## End an experiment

Move the winning arm's fragment into `presentation` (and its `theme` into
`theme`), then remove `experiment`. Visitors keep their consent; the stored
arm is ignored once no experiment reads it.

## Copy is out of scope

Arms change presentation and theme tokens only. Copy is not a variant dimension because
`copyRevision` is hashed into the prompt fingerprint: a copy change re-prompts
every returning visitor, so a copy experiment would re-prompt them on each
arm switch. Vary layout, shape, position and action prominence instead.
