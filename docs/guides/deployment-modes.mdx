## Choose who manages policy and records

| Mode | Policy resolution | Record storage | Use when |
| --- | --- | --- | --- |
| Hosted backend | Backend init or a published manifest | Browser records plus backend submissions | You want centrally managed policy and records |
| Self-hosted backend | Your c15t backend or its manifest | Browser records plus your database | You operate the consent service |
| Browser-only | Local `policyRules` | Browser persistence | You deliberately do not need backend submissions |

Hosted and self-hosted use the same client transport factory, `hosted({ url })`.
Browser-only uses `offline({ policyRules })`. Frameworks have different
configuration entry points; use [your framework guide](/docs/frameworks)
for the exact provider or module setup.

```ts
import { hosted, offline } from 'c15t';
import { policyRulePresets } from '@c15t/schema';

const backendMode = hosted({ url: 'https://consent.example.com' });
const localMode = offline({ policyRules: [policyRulePresets.europeOptIn()] });
```

These are alternative factories, not two modes to mount together. Replace the
backend URL with your service. Local policy configuration does not give you
backend audit history or geographic detection by itself.

## Choose when consent initializes

| Application output | Initial state | Required setup |
| --- | --- | --- |
| Request SSR | Prepared for this request | Adapter request helper, matching client configuration |
| Static HTML or SPA | Resolved in the browser | Reachable external URLs or local rules |
| Manifest resolution | Policy evaluated from a manifest | Correct manifest URL, location inputs and save destination |

Request SSR can include the visitor's prompt in the initial HTML. Pass the
prepared records and policy resolution through to hydration. Do not convert
effective permissions into new stored choices.

Static HTML is shared across visitors. It cannot contain a policy resolved from
each visitor's cookies or geography. Initialize in the browser instead. A
same-origin `/api/c15t` URL only works if something actually serves that route.
A development server is not evidence that a static deployment has one.

A consent manifest contains policy data that can be cached. A visitor's resolved
init response also contains visitor-specific inputs. Do not cache the two as if
they were interchangeable, or share personalized consent HTML across users.

## Decide what failure should look like

While no policy resolves, optional permissions stay denied and stock consent UI
stays hidden. No banner can therefore mean pending or failed initialization,
not permission to load everything. Observe errors and resolution state before
changing presentation.

Browser storage can also be unavailable. A working in-memory interaction does
not prove the choice survives reload. Use
[verification](/docs/guides/verify-consent) to test the actual deployment.
