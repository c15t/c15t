## Replace the runtime and state model

```ts
import {
  createConsentKernel,
  createHostedTransport,
  evaluateConsent,
} from '@c15t/core';
import { createPersistence } from '@c15t/core/modules/persistence';

const kernel = createConsentKernel({
  transport: createHostedTransport({
    backendURL: 'https://consent.example.com',
  }),
});
const persistence = createPersistence({ kernel });
await kernel.commands.init();

const canMeasure = evaluateConsent(
  { category: 'measurement' },
  kernel.getSnapshot()
);
```

Attach persistence in the browser. Dispose the persistence handle and kernel
when their owner unmounts. Framework providers manage that lifecycle for you.

| v2 pattern | v3 replacement |
| --- | --- |
| Runtime factory and Zustand store | `createConsentKernel`, `getSnapshot`, `subscribe` and browser modules |
| `hasConsented` (removed) | `effectivePermissions` for processing, `promptRequirement` for interaction, `explicitChoice` for receipt presence |
| One boolean map and confirmation time | `explicitChoice` with latest receipt per confirmed category |
| `PolicyConfig` and `ResolvedPolicy` | `PolicyRule`, `ResolvedPolicyRule` and explicit `resolution` outcome |
| `policyPacks`, nested `consent`, policy-owned `ui` | `policyRules`, top-level behavior fields and host `presentation` |
| `worldNoBanner` or permission model `none` | Explicit opt-out rule with prompt `none`, if appropriate for your deployment |
| `onConsentSet`, `onConsentChanged` | `onChoiceRecorded`, `onPermissionsChanged` |
| `initialHasConsented` or raw cookie booleans | Validated `initialRecords` and prepared `initialPolicyResolution` |
| `initialConsents` and `set.consent()` | `initialDraft` and `set.draft()` for editable values only |
| Snapshot `consents` and `subjectId` | `effectivePermissions` and `subject?.subjectId` |
| `policyDecision` and `policyProvisional` | Versioned `resolution` and `policyPending` |
| `@c15t/dev-tools/react` | Framework `/devtools` adapters; `@c15t/dev-tools` is the imperative engine |
| Legacy consent storage readers/writer | `readStoredRecords` and `readStoredRecordsFromCookieHeader`; persistence owns writes |
| Consent-dependent preferences trigger | Persistent preferences and opt-out access |
| Specialized Maps and YouTube components | `Frame` around an iframe, or consent-aware scripts |

No automatic codemod performs this migration. Review processing categories,
policy rules and UI controls together.

## Keep existing v2 choices

v3 reads valid v2 records for the lifetime of v3. A package upgrade alone does not
require a new choice. The reader preserves original category decisions, confirmation
time, subject identifiers and legacy material fingerprint when present. Missing
fingerprints alone do not force a prompt. Expiry, invalid records, incomplete
coverage and a known material mismatch can still require one.

Startup normalization is read-only. It does not rewrite browser storage, renew a
receipt, call the consent-saving endpoint or invoke a choice callback. The next
explicit user action writes v3 storage. Untouched legacy receipts retain their
original basis and time even when the same envelope contains new v3 receipts.

Legacy JSON preserves absent categories as undecided. The old compact cookie
omitted false values, so its reader retains that format's historical false
interpretation. It cannot recover the distinction between an omitted denial and
an undecided category from those old bytes. v3 represents both distinctly.

The first structurally valid cookie record takes precedence over localStorage.
An expired but valid cookie does not fall through to a fresher local grant.
Invalid cookies may fall through to valid storage. Never replace these readers
with code that fills absent JSON categories or stamps `Date.now()` on load.

The shipped presets carry frozen material metadata for their original v2
definitions. A custom rule can provide `legacyMaterial` with the exact old
`input` and the `policyFingerprint` of the reviewed v3 behavior. This metadata
only supports comparison with old receipts. It does not configure current
permissions or presentation and is absent from the resolved rule. Changing the
v3 behavior invalidates that comparison, even when spreading a preset. Do not
invent an old fingerprint or assume an unknown custom policy was equivalent.

## Confirm only the categories the visitor chose

```ts
await kernel.commands.save({ measurement: true });
await kernel.commands.save({ marketing: false });
```

An object confirms exactly its own optional category keys. Repeating an unchanged
value renews that category's receipt. Omitted categories keep their original time
and policy basis. An empty object is a successful no-op. Accept all and reject all
confirm the active selectable scope. Positive out-of-scope keys and
`necessary: false` reject the whole command; necessary remains allowed.

Use `initialDraft` or `kernel.set.draft()` to seed editable values without granting permissions. Backend initialization carries records and policy resolution, never draft values.

No-input `save()` confirms the current unmasked selection for the active scope.
Preference forms pass their displayed draft explicitly. Drafts start from explicit
choices and displayed defaults, before GPC restrictions. Never turn masked
permissions into a saved choice. A material policy change makes a dirty draft
stale until the visitor reviews the updated choices.

For example, confirming marketing on day 0 and measurement on day 29 with a
30-day validity gives separate deadlines on days 30 and 59. Saving measurement
again never renews marketing. A partial save may succeed while the prompt still
requires choices for other categories. Local recording precedes remote completion;
retries preserve the original action time and do not emit another choice event.

## Separate permission expiry from denials

Positive receipts expire according to the active rule. Opt-in and IAB stop using
expired positive authority. Opt-out returns to its configured default without
rewriting the receipt. Explicit denials and standing opt-out directives do not age
into permission. A material policy change may request confirmation again while
a denial remains effective.

Scripts, frames, network blocking and Google Consent Mode consume effective
permissions. Gate-time evaluation handles expiry even if a browser timer runs
late. IAB targets additionally require confirmed, valid TC authority; editable
vendor or purpose maps and category acceptance cannot provide it. All applicable
category restrictions still apply to an IAB target.

## Observe the right event

```ts
const stopChoices = kernel.events.on(
  'choice:recorded',
  ({ confirmed, actionAt }) => {
    console.log('Confirmed', confirmed, actionAt);
  }
);
const stopPermissions = kernel.events.on(
  'permissions:changed',
  ({ snapshot }) => {
    console.log('Processing permissions', snapshot.effectivePermissions);
  }
);
```

Call the returned cleanup functions on teardown. Provider callbacks receive the
same payload without `type`. Only explicit accept, reject and nonempty save actions
record a choice. Reconfirmation fires once even when permission values stay the
same. Hydration, initialization, expiry, policy changes, GPC and replay do not
create choice events. A permission event can occur without a choice.

`notice:dismissed` and `privacy:opt-out` are separate events. Registering listeners
or mounting components does not replay a choice.

## Keep notices local and preferences reachable

```ts
if (kernel.getSnapshot().promptRequirement.kind === 'notice') {
  await kernel.commands.dismissNotice();
}
```

Connect dismissal to a direct dismiss action. It records only that the visitor
dismissed the current notice. It does not prove delivery, reading, understanding
or consent. It changes no category permission and has no backend endpoint, audit
entity or proof capability.

Choice, notice and privacy records have separate storage. Notice and privacy
records use localStorage with compact cookie projections for server rendering.
A missing local dismissal can show the notice again, but cannot change permissions.
Clearing c15t data removes those local records and queued writes; it does not erase
server history. A live GPC signal continues to restrict processing after clear.

Preferences remain available while a notice is required. Accepting, rejecting or
saving categories does not dismiss it. Keep disclosure, preferences and opt-out
controls available even when the prompt is `none` or no explicit choice exists.

## Configure policy behavior and host presentation

```tsx
import type { ReactNode } from 'react';
import {
  ConsentProvider,
  ConsentBanner,
  ConsentDialog,
  ConsentDialogLink,
  offline,
} from '@c15t/react';

export function PrivacyProvider({ children }: { children: ReactNode }) {
  return (
    <ConsentProvider
      options={{
        mode: offline({
          policyRules: [
            {
              id: 'default',
              match: { isDefault: true },
              model: 'opt-in',
              prompt: 'choice',
              categories: ['measurement', 'marketing'],
              scopeMode: 'strict',
              validity: { choiceDays: 365, noticeDays: 365 },
            },
          ],
        }),
        presentation: {
          prompt: { layout: [['reject', 'accept'], 'customize'] },
          preferences: { layout: [['reject', 'accept'], 'save'] },
        },
      }}
    >
      {children}
      <ConsentBanner />
      <ConsentDialog />
      <ConsentDialogLink>Privacy settings</ConsentDialogLink>
    </ConsentProvider>
  );
}
```

The permission models are `opt-in`, `opt-out` and `iab`. Prompts are `choice`,
`notice` and `none`. Only opt-out allows notice or none. Rules own scope, actions,
rights, validity and privacy handling. Component presentation overrides host
presentation, then built-in defaults apply. There is no policy UI bridge.

The shared synchronous resolver restores required actions and removes forbidden
ones. Accept and reject receive equivalent default prominence and reachability
when both are offered. Customize does not replace reject. Equivalent does not
mean identical color, label, size or order. Deliberate visual differences can
produce a development diagnostic; headless hosts own their rendered controls.
This is a conservative product invariant, not a claim about every jurisdiction.

Read `promptRequirement` rather than comparing fingerprints. Policy, choice and
notice hashes have separate versioned inputs; presentation diagnostics are
separate again. Producers compute behavioral hashes during resolution, outside
render and hydration. Cosmetic changes do not invalidate choices or notice
records. Use `copyRevision` for material legal-copy changes.

## Honor GPC without manufacturing consent

```ts
import type { PolicyRule } from '@c15t/schema';

const rule: PolicyRule = {
  id: 'custom-notice',
  match: { isDefault: true },
  model: 'opt-out',
  prompt: 'notice',
  categories: ['marketing', 'measurement'],
  privacySignals: { gpc: { denyCategories: ['marketing', 'measurement'] } },
};
```

Only `Sec-GPC: 1` or `navigator.globalPrivacyControl === true` counts as detection.
Generic core code has no built-in category mapping. Mappings reject necessary,
duplicates, unknown categories and categories outside scope. The mapping applies
after defaults and choices, so a saved true can remain in the receipt while its
effective permission is false.

Detection records a separate standing directive with source `gpc`. Removing the
browser signal does not erase it. An ordinary accept or save cannot override it.
There is no informed-exception or user override flow in this release. Developer
signal overrides are separate test inputs and do not create standing directives.
GPC never saves consent, dismisses a notice or suppresses a required disclosure.

Anonymous directives remain local. Identification can resolve locally while the
transport queues association until a real server subject exists. It must not call
the consent-saving endpoint just to create that subject. Clear and disposal cancel
pending identity and privacy work. Do not claim remote persistence before the
separate privacy endpoint succeeds. Associated-profile propagation needs trusted
server identity linkage; a browser external ID alone is insufficient.

## Prepare server rendering and handle failures

Use each adapter's server helpers to carry `initialRecords`,
`initialPolicyResolution` and one evaluation `now` into hydration. The core
`readStoredRecordsFromCookieHeader` helper reads raw cookies without inventing
receipts. Equal prepared inputs produce equal initial permissions and prompts.
Prepared initialization does not need another init request. Older localStorage-only
notice records cannot suppress a server-rendered prompt before hydration.

`policyPending` indicates that policy initialization is still outstanding. Keep
that lifecycle state separate from `promptRequirement`. Failed initialization
keeps the first layer hidden while the kernel retries and applies safe fallback
permissions. It never retains a stale permissive policy or treats failure as a
successful no-match.

Resolution preserves four outcomes: `unconfigured`, `matched`, `no-match` and
`failed`. Every non-matched outcome carries explicit `policy: null`, clears stale
policy-derived state and adopts safe opt-in choice behavior. Omission and malformed
wire data fail validation. An empty pack and unknown geography cannot authorize
processing. An intentional opt-out plus none rule must be configured explicitly.

React is the reference adapter. Next.js resolves server-known data before selecting
its client boundary. Vue/Nuxt and Svelte/SvelteKit use the same record, action and
presentation contract. Solid currently exports primitives only and is not a
supported consent-provider adapter.

## Coordinate the wire rollout

v3 manifests use `schemaVersion: 2`; policy resolution uses contract version 1.
Clients send `x-c15t-policy-contract: 1`. Package version headers remain telemetry
and are not capability negotiation. Custom producers must send the canonical
records and explicit nullable policy resolution. Rebuild static manifests with
the matching builder. Run the backend receipt/privacy migration before using
those endpoints; see [backend policy rules](/docs/self-host/guides/policy-packs).

The backend can return a safe opt-in compatibility projection to old clients.
That does not repair an old runtime's interpretation of existing storage. Tests
with the original cached client and its hosted and manifest transports found
that fresh visitors deny, but visitors with stored grants retain those grants
even under GPC. Invalidate and redeploy cached old clients before relying on the
new policy semantics. Header negotiation alone cannot close that gap.

External hosted producers and identity linkage must also be deployed and verified.
Local package tests do not establish that those external services support the
contract. Devtools integration is deferred until its prerequisite work merges;
do not depend on a new diagnostic panel as part of this migration.

## Review preset assumptions

The existing presets retain their source review dated 2026-09-05 and review-by
date 2027-03-05. These dates do not expire receipts. The CAI consent guideline is
a published guideline; the cited W3C GPC document is a Working Draft, not a final
Recommendation. Preserve that distinction when reviewing the
[preset sources and assumptions](/docs/frameworks/react/concepts/policy-packs#policy-rules).
No new country preset is implied by this release. c15t supplies controls and
records; it does not establish legal compliance for your deployment.

## Load DevTools through the framework adapter

Use `c15t/react/devtools`, `c15t/next/devtools`, `c15t/vue/devtools` or
`c15t/svelte/devtools` with the umbrella package. Scoped packages expose the
same `/devtools` subpath. The adapter reads the existing provider kernel.
Keep its dynamic import behind your bundler's development flag so the engine
stays out of ordinary production routes.

For direct kernel inspection, use `createDevTools({ kernel })` from
`@c15t/dev-tools` and destroy the panel during application cleanup. See the
[JavaScript guide](/docs/frameworks/javascript/dev-tools) or your framework's
DevTools page for complete examples. DevTools choices follow the same receipt,
policy scope, GPC and notice rules as the rest of the application.
