<section id="overview">
  The provider constructs a kernel, restores validated records without rewriting
  them, resolves policy, and evaluates effective permissions and required prompts.
  Prepared server records and policy use the same evaluation time during hydration.
  A pending policy keeps the first layer hidden.
</section>

<section id="flow-diagram">
  ## Initialization sequence

  1. Construct the kernel without browser effects.
  2. Hydrate validated category, notice and privacy records with original times.
  3. Fetch the versioned policy contract, or use prepared server/offline data.
  4. Apply the matched rule or safe fallback and derive `promptRequirement`.
  5. Attach processing gates to effective permissions.
  6. Record only actual user choices, notice dismissals and detected directives
     through their separate commands and events.

  No stored-record presence check decides visibility or processing permission.
</section>

<section id="how-it-works">
  ## Records and policy

  Hydration preserves original receipt times and creates no choice event. The
  transport returns an explicit versioned policy resolution. Permission evaluation
  combines rules and records, then applies denials and privacy restrictions.
  Prompt derivation independently checks current choice or notice validity.
</section>

<section id="choices-and-permissions">
  ## Choices, permissions, and prompts

  The kernel snapshot keeps three facts apart, and they never collapse into one flag:

  - `explicitChoice` is the latest receipt per optional category. Only accept, reject, and save write it. Rendering, hydration, dismissing a notice, navigation, and privacy signals never create or change a choice.
  - `effectivePermissions` is what script, iframe, network, and Consent Mode gates consume. It is derived from the choice, the active policy rule, expiry, scope, and privacy signals. `consents` is an alias of the same object during the v3 migration.
  - `promptRequirement` says which interaction the policy still needs: `{ kind: 'choice' | 'notice', reason: 'missing' | 'expired' | 'policy-changed' }` or `{ kind: 'none' }`. UI visibility derives from it, not from whether a choice exists.

  Positive grants expire after the policy's choice validity. Under `opt-in` and `iab` an expired grant stops being effective and the prompt reports `expired`; under `opt-out` it falls back to the policy default. Explicit denials and recorded opt-out directives stay effective until a later permitted action replaces them or c15t data is cleared. The kernel re-evaluates at construction, hydration, init, every save, and when the earliest expiry passes; `kernel.refresh()` re-evaluates on demand so a gate never trusts a delayed timer.

  A notice prompt is dismissed only through `commands.dismissNotice()`, which records a local dismissal against the current notice fingerprint and changes no permission. Saving preferences while a notice is required records the choice and leaves the notice required.

  A detected Global Privacy Control signal (`navigator.globalPrivacyControl === true` or `Sec-GPC: 1`) masks the categories the active policy maps to it and, once the lifecycle has started, records a standing opt-out directive in local storage. Removing the signal does not remove the directive, and an ordinary save cannot override it. GPC never creates a choice, never dismisses a notice, and never runs consent callbacks. The `overrides.gpc` option is a developer override: it masks permissions the same way but records no directive.

  Clearing c15t data also invalidates records from pending initialization and subject reads. A late response can update policy resolution but cannot restore the cleared choice, identity, or privacy directive. Privacy forwarding retries failures with the original recorded time and acknowledges each subject separately.

  Kernel events follow the same split: `choice:recorded` fires only for an explicit save, `permissions:changed` fires when the effective permissions differ by value, `notice:dismissed` and `privacy:opt-out` fire for their own records.
</section>

<section id="when-init-fails">
  ## When init fails

  Hosted initialization fails closed. c15t records the resolution as `failed`, withholds the banner, adopts the safe opt-in fallback rule so optional categories stay denied, and leaves consent-gated scripts blocked instead of asking the visitor to consent to placeholder policy text. A permissive policy from an earlier init never survives a failed one. The resolution status stays observable on `snapshot.resolution`, which also distinguishes `unconfigured` (no policy system), `no-match` (valid configuration matched nothing), and `matched`. Every non-matched outcome uses the same fallback and is never reported as a matched policy.

  The kernel retries up to five total attempts by default. Retries use exponential backoff with jitter, pause while the tab is hidden, and run immediately when the browser comes online. Set `initRetry: false` on `createConsentKernel()` to disable retries, or set `maxAttempts`, `baseDelayMs`, and `maxDelayMs` to tune them. The `init:failed` kernel event reports the error, attempt number, and next retry delay.

  Offline mode does not use this failure path. Its local policy is authoritative, so it can render without a backend init request.
</section>

<section id="banner-visibility">
  ## Prompt visibility

  Render the current `promptRequirement` only when policy initialization is ready.
  Failed initialization keeps the first layer hidden while retries and fallback
  permissions apply. A notice remains required after a preference save. Persistent
  preferences and disclosure remain accessible independently of that first layer.
</section>

<section id="debugging">
  ## Inspect the snapshot

  Read `resolution`, `promptRequirement`, `explicitChoice`, `effectivePermissions`
  and `restrictions`. Observe `choice:recorded` for confirmations and
  `permissions:changed` for processing updates. New devtools panels are deferred;
  these public state fields do not depend on them.
</section>
