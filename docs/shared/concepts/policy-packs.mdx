<section id="overview">
  Different countries need different consent experiences. Policy packs let you define those rules once — c15t picks the right one automatically based on where the visitor is.

  A policy pack is an ordered array of policies. Each policy targets a region or country and controls the consent model, which categories are in scope, what UI is shown, and how consent is recorded.

  There are three ways to configure policy packs:

  1. **inth.com (recommended)** — use [inth.com](https://inth.com) as your hosted backend. Configure packs visually in the dashboard or via API — no code changes required. Works with any frontend, including static sites.
  2. **Self-hosted backend** — define packs in code via `policyPacks` and resolve them from real request geo data. Full control over policy logic and storage.
  3. **Offline mode** — pass the same policy shapes to the frontend via `offlinePolicy.policyPacks`. Use this for local development, demos, deterministic testing, or a deployment that deliberately has no backend. If you omit `offlinePolicy.policyPacks`, offline mode uses a synthetic worldwide opt-in banner instead of no-banner mode.

  In both hosted and self-hosted modes, the **backend is always the source of truth**. A failed hosted init withholds the banner and retries. It does not promote an offline policy to replace the missing backend decision.
</section>

<section id="quickstart">
  ## Quickstart

  The fastest way to get started is with the built-in presets:

  ```ts
  import { policyPackPresets } from 'c15t';

  const policies = [
    policyPackPresets.europeOptIn(),    // GDPR opt-in banner
    policyPackPresets.californiaOptOut(), // CCPA opt-out banner
    policyPackPresets.worldNoBanner(),          // No banner elsewhere
  ];
  ```

  | Preset | Model | UI | Matches |
  |--------|-------|----|---------|
  | `europeOptIn()` | `opt-in` | banner | EEA + UK countries + geo fallback |
  | `europeIab()` | `iab` | banner | EEA + UK countries + geo fallback (TCF 2.3) |
  | `californiaOptOut()` | `opt-out` | none | US-CA region |
  | `quebecOptIn()` | `opt-in` | banner | CA-QC region |
  | `worldNoBanner()` | `none` | none | default fallback |

  Most apps only need these presets — pick the ones that match your regions, pass them to your backend config or provider, and you're done. Customize individual fields or write fully custom policies when you need more control.

  For banner/dialog actions, policy packs can also control grouped button arrangement:

  ```ts
  ui: {
    mode: 'banner',
    banner: {
      allowedActions: ['reject', 'accept', 'customize'],
      layout: [['reject', 'accept'], 'customize'],
      direction: 'row',
      primaryActions: ['accept', 'customize'],
    },
  }
  ```

  That expresses arrangement only. Button appearance like `stroke`, `filled`, or `ghost` lives in the UI theme.
</section>

<section id="what-users-see">
  ## What Users See

  Each policy combination produces a different consent experience:

  | Policy Config | User Experience |
  |--------------|-----------------|
  | `model: 'opt-in'`, `ui.mode: 'banner'` | Banner appears, nothing loads until the user consents |
  | `model: 'opt-out'`, `ui.mode: 'none'` | No banner, everything loads immediately — user opts out via a "Do Not Sell" link |
  | `model: 'none'`, `ui.mode: 'none'` | No banner, all categories auto-granted silently |
  | `model: 'opt-in'`, `ui.mode: 'dialog'` | Full-screen dialog, nothing loads until the user consents |
  | `model: 'iab'`, `ui.mode: 'banner'` | IAB TCF 2.3 banner with vendor-level controls |
</section>

<section id="resolution-flow">
  ## How Policy Resolution Works

  When a visitor arrives, c15t walks the policy pack in priority order:

  1. **Match by region** — checks for a policy targeting the specific region (e.g., US-CA, CA-QC)
  2. **Match by country** — if no region match, checks for a country-level policy (e.g., US, DE)
  3. **Fallback (geo failure)** — if geo-location failed (no country detected), uses the policy marked with `match.fallback`
  4. **Fall back to default** — if nothing matches, uses the policy marked as the default
  5. **No match, no default** — resolves to no-banner mode (silent, no consent UI)

  Within the same matcher type, the first policy in the array wins. Pack order matters when two policies target the same country or region.

  The **fallback** step is distinct from **default**: `isDefault` is a catch-all for known locations that don't match any specific policy ("rest of world"), while `fallback` is a safety net for unknown locations when geo-headers are missing ("assume strictest"). The `europeOptIn()` and `europeIab()` presets include `fallback: true` by default so EU-level consent applies when geo fails.

  <Callout type="warning">
    Only one default and one fallback policy are allowed. Use `inspectPolicies()` to surface overlapping matchers and other warnings before deployment.
  </Callout>
</section>

<section id="common-patterns">
  ## Common Patterns

  **The 80% case** — strict in Europe, light in California, silent everywhere else:

  ```ts
  const policies = [
    {
      id: 'eu',
      match: { countries: ['DE', 'FR', 'IT'] },
      consent: { model: 'opt-in', categories: ['necessary', 'measurement', 'marketing'] },
      ui: { mode: 'banner' },
    },
    {
      id: 'ca',
      match: { regions: [{ country: 'US', region: 'CA' }] },
      consent: { model: 'opt-out', gpc: true },
      ui: { mode: 'none' },
    },
    {
      id: 'default',
      match: { isDefault: true },
      consent: { model: 'none' },
      ui: { mode: 'none' },
    },
  ];
  ```

  **Region overrides country** — stricter rules for California than the rest of the US:

  ```ts
  const policies = [
    {
      id: 'us_ca',
      match: { regions: [{ country: 'US', region: 'CA' }] },
      consent: { model: 'opt-in', scopeMode: 'strict' },
      ui: { mode: 'banner' },
    },
    {
      id: 'us',
      match: { countries: ['US'] },
      consent: { model: 'opt-out' },
      ui: { mode: 'banner' },
    },
  ];
  // US-CA → us_ca (region match wins)
  // US-NY → us (country match)
  ```

  **Different wording per region** — use `i18n.messageProfile` to vary copy without changing the consent model:

  ```ts
  const c15t = c15tInstance({
    i18n: {
      defaultProfile: 'default',
      messages: {
        default: {
          translations: {
            en: { cookieBanner: { title: 'Privacy choices' } },
            es: { cookieBanner: { title: 'Tus opciones de privacidad' } },
          },
        },
        eu: {
          fallbackLanguage: 'en',
          translations: {
            en: { cookieBanner: { title: 'EU GDPR Consent' } },
            fr: { cookieBanner: { title: 'Consentement RGPD' } },
            de: { cookieBanner: { title: 'GDPR-Einwilligung' } },
          },
        },
      },
    },
    policyPacks: [
      {
        id: 'eu',
        match: { countries: ['DE', 'FR', 'IT'] },
        i18n: { messageProfile: 'eu' },
        consent: { model: 'opt-in' },
        ui: { mode: 'banner' },
      },
    ],
  });
  ```

  In that setup, the `eu` policy uses only the `eu` language set. So Europe can
  resolve to `en`, `fr`, or `de`, but not to `es` or any other locale defined
  only in `default`. If the browser asks for an unsupported locale, c15t falls
  back to the `eu` profile's `fallbackLanguage`.
</section>

<section id="re-prompting">
  ## Re-Prompting on Policy Change

  When you change a policy in a way that affects consent semantics — like adding a category, changing the consent model, or modifying allowed actions — c15t automatically re-prompts returning users.

  This works through the **material policy fingerprint**: a hash of only the consent-affecting fields (model, categories, scope, allowed actions, grouped action layout, direction, proof settings). Presentation-only changes like copy, button styling, or scroll lock do not trigger re-prompts.

  | Change | Re-prompts? |
  |--------|------------|
  | Add a consent category | Yes |
  | Change `model` from `opt-out` to `opt-in` | Yes |
  | Remove an `allowedAction` | Yes |
  | Change `uiProfile` or button styling | No |
  | Update translation copy | No |
  | Change `scrollLock` | No |
</section>

<section id="gpc">
  ## Global Privacy Control (GPC)

  Each policy can opt in to respecting the [Global Privacy Control](https://globalprivacycontrol.org/) signal via `consent.gpc`:

  ```ts
  {
    id: 'california',
    match: { regions: [{ country: 'US', region: 'CA' }] },
    consent: { model: 'opt-out', gpc: true },
  }
  ```

  When `gpc: true` and the visitor's browser sends a GPC signal (`Sec-GPC: 1` header or `navigator.globalPrivacyControl`), `marketing` and `measurement` categories are automatically denied during auto-granting — honoring the user's opt-out preference.

  When `gpc` is `false` or omitted, the GPC signal is ignored for that policy. This is the right default for GDPR/EEA policies where consent is already opt-in and GPC is redundant.

  | Preset | `gpc` | Why |
  |--------|-------|-----|
  | `californiaOptIn()` | `true` | CCPA recognizes GPC as a legal opt-out |
  | `californiaOptOut()` | `true` | CCPA recognizes GPC as a legal opt-out |
  | `europeOptIn()` | — | GDPR already requires opt-in |
  | `europeIab()` | — | TCF handles consent signals |
  | `worldNoBanner()` | — | No regulation applies |

  <Callout type="info">
    The `overrides.gpc` option on the provider and the DevTools GPC toggle still work as a manual override for testing — they force the GPC signal on or off regardless of policy settings.
  </Callout>

  ### GPC in v3 rules

  v3 rules replace the `gpc: true` flag with an explicit category mapping:

  ```ts
  privacySignals: {
    gpc: { denyCategories: ['marketing', 'measurement'] },
  }
  ```

  Only `Sec-GPC: 1` or `navigator.globalPrivacyControl === true` counts as a detected signal. The mapping must stay inside the rule's scope, cannot name `necessary`, and cannot repeat a category. GPC never creates consent and never dismisses a notice; it masks the mapped categories after policy defaults and stored choices, so it can hide a stored grant, and it may record a separate opt-out directive. Removing the browser signal does not erase that directive. The California presets keep the marketing and measurement mapping as a conservative product default; check it against your actual processing purposes.
</section>

<section id="policy-rules">
  ## Policy rules (v3 contract)

  v3 replaces the mixed policy shape with a rule that owns behavior only. A rule says which permission model applies, which first-layer prompt it needs, which categories are in scope, which actions and rights the prompt must offer, how long a choice or a notice dismissal stays valid, and how the Global Privacy Control signal maps to categories. Layout, button order, colors and copy stay with your app.

  ```ts
  import { policyRulePresets, type PolicyRule } from '@c15t/schema';

  const rules: PolicyRule[] = [
    policyRulePresets.europeOptIn(),
    {
      id: 'california',
      match: { regions: [{ country: 'US', region: 'CA' }] },
      model: 'opt-out',
      prompt: 'none',
      privacySignals: { gpc: { denyCategories: ['marketing', 'measurement'] } },
      validity: { choiceDays: 365, noticeDays: 365 },
    },
    policyRulePresets.worldOptOutNoPrompt(),
  ];
  ```

  There are three permission models and three prompts. A notice is a prompt, not a model.

  | Model | Allowed prompts | Default for optional categories |
  |-------|-----------------|---------------------------------|
  | `opt-in` | `choice` | denied until an explicit choice |
  | `opt-out` | `choice`, `notice`, `none` | allowed until an opt-out |
  | `iab` | `choice` | managed by TCF 2.3 |

  - A `choice` prompt must offer `accept` and `reject`; `customize` is optional. Accept and reject form one equivalence group: they sit at the same depth with the same prominence. Order, labels and variants are yours.
  - A `notice` prompt offers one `dismiss` action. Dismissing records nothing about categories and changes no permission.
  - A `none` prompt shows no first layer. It never grants anything on its own.
  - Every rule carries the `disclosure` and `preferences` rights. Opt-out rules add `opt-out`. These stay reachable whether or not a prompt is visible.
  - Validity defaults to 365 days for both choices and notice dismissals. Configure them separately; they never affect each other.

  `inspectPolicyRules()` reports errors and warnings for a pack. It rejects an invalid model and prompt pair, unknown categories, a GPC mapping outside the rule's scope, and unknown fields anywhere in a rule.

  The built-in presets are `europeOptIn`, `europeIab`, `californiaOptIn`, `californiaOptOut`, `quebecOptIn` and `worldOptOutNoPrompt`. The last one replaces `worldNoBanner`: allow-by-default with no prompt is now an explicit `opt-out` plus `none` rule you choose, not a model. Each preset carries source-review metadata dated `2026-09-05`. This records a check of its documented assumptions, not approval of your deployment. The 365-day validity defaults and equivalent default accept/reject prominence are product choices. You still need to classify your processing purposes and assess the applicable requirements.

  - Europe groups the EEA and UK conservatively. Check your purposes and exemptions against the [ICO cookie guidance](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guide-to-pecr/cookies-and-similar-technologies/) and [EDPB consent guidelines](https://www.edpb.europa.eu/sites/default/files/files/file1/edpb_guidelines_202005_consent_en.pdf).
  - California maps GPC to marketing and measurement as a conservative default. Measurement is not always sale or sharing; check the mapping against your processing. The sources are the [California Attorney General CCPA guidance](https://oag.ca.gov/privacy/ccpa) and the [W3C GPC Working Draft of 11 June 2026](https://www.w3.org/TR/2026/WD-gpc-20260611/), which is not a final Recommendation.
  - Quebec opt-in is a conservative configuration. The [CAI consent guidelines, version 1.0](https://www.cai.gouv.qc.ca/uploads/pdfs/CAI_Criteres_Validite_Consentement.pdf) describe consent validity, including specific purposes and duration. The [Law 25 changes](https://www.cai.gouv.qc.ca/protection-renseignements-personnels/sujets-et-domaines-dinteret/principaux-changements-loi-25) do not establish a blanket cookie opt-in rule from the highest-privacy-default provision.
  - `worldOptOutNoPrompt` is an explicit controller choice with no regional legal claim and no default GPC mapping. It is never the runtime fallback for failed or unmatched resolution.

  Each preset sets `reviewBy: '2027-03-05'` as a six-month source review reminder. This date does not expire choices or change runtime permissions. Review sooner if the cited sources or your processing change.

  Inspect the assumptions before adapting a preset:

  ```ts
  const rule = policyRulePresets.californiaOptOut();
  console.log(rule.review?.reviewedOn);
  console.log(rule.review?.reviewBy);
  console.log(rule.review?.sources);
  console.log(rule.review?.assumptions);
  ```
</section>

<section id="resolution-outcomes">
  ## Resolution outcomes

  Resolving a pack for a request ends in one of four outcomes. They never collapse into one empty value.

  | Status | Meaning | `policy` |
  |--------|---------|----------|
  | `unconfigured` | No policy system was configured | `null` |
  | `matched` | A rule matched by region, country, fallback or default | the resolved rule plus its fingerprints |
  | `no-match` | Valid pack, known location, nothing matched | `null` |
  | `failed` | Invalid configuration, unknown location without a fallback or default, a transport error, or a wire the client cannot represent | `null` |

  `/init` carries this as `policyResolution` with a contract `version`. `policy: null` is explicit and clears policy-derived state. Leaving the field out means the producer predates the contract; a client never reads that as "nothing matched".

  Everything other than `matched` runs the safe fallback: strict opt-in with a choice prompt. The status stays visible so you can see why the fallback is active. Allow-by-default behavior with no prompt only ever comes from an explicit rule.

  ```ts
  import { resolvePolicyRules } from '@c15t/schema';

  const resolution = resolvePolicyRules({ rules, countryCode: 'DE', regionCode: null });
  if (resolution.status === 'matched') {
    resolution.policy.prompt; // 'choice'
    resolution.fingerprints.choice; // what a stored choice is compared against
  }
  ```
</section>

<section id="fingerprint-domains">
  ## Fingerprint domains

  v3 keeps three separately versioned hashes, each with one job.

  | Domain | Answers | Hashes |
  |--------|---------|--------|
  | `policy` | Did the exact behavior change? | model, prompt, scope and scope mode, preselected categories, actions, rights, both validities, GPC mapping, copy revision, proof settings |
  | `choice` | Is a stored category choice still current? | model, prompt, scope and scope mode, required actions, choice validity, rights, GPC mapping, copy revision |
  | `notice` | Is a notice dismissal still current? | model, prompt, scope and scope mode, required actions, notice validity, rights, GPC mapping, copy revision |

  Presentation never enters any of these. Sets are sorted and deduplicated before hashing, so two authors writing the same behavior in a different order get the same hash. Bump `copyRevision` when the wording a visitor agreed to changes materially; that re-prompts through the choice and notice hashes without touching the policy hash's other inputs.

  A separate presentation fingerprint exists for diagnostics only. It hashes layout and copy you pass in, never decides a prompt, and stays out of production payloads.

  Producers (the backend, the manifest builder and offline resolution) compute these once at resolution time. Nothing hashes during render or hydration. Records written by v2 keep their material fingerprint, which the v2 compatibility reader compares in its own domain.
</section>

<section id="design-guidelines">
  ## Design Guidelines

  - **Start from presets.** Use `policyPackPresets` to get running, then customize for your needs.
  - **Keep packs small.** A handful of regional policies is better than dozens of tiny fragments.
  - **Think risk, not geography.** Geography is just a matcher — the real question is what consent behavior each region needs.
  - **Always include a default.** Unless "no banner for unmatched traffic" is intentional.
  - **Set a fallback for geo failures.** Mark your strictest policy with `match.fallback=true` so users in unknown locations still see a consent banner. The `europeOptIn()` and `europeIab()` presets do this automatically.
  - **Keep policy IDs stable.** They appear in debugging output, snapshots, and audit records.
  - **Use `inspectPolicies()` before deploying.** It catches overlapping matchers, missing defaults, and IAB misconfigurations.
</section>
