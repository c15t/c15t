## Configure cleanup

Gating stops new requests, but it leaves the cookies and storage keys a vendor
already wrote. List the ones each optional category owns in
`clearOnRevocation`. When that category is denied, c15t deletes them:

{/* example: fragment */}

```ts title="src/main.ts (partial)"
init({
  backendURL: 'https://your-project.inth.app',
  scripts,
  clearOnRevocation: {
    measurement: { cookies: ['_ga', '_ga_*'], localStorage: ['analytics:*'] },
    marketing: { cookies: ['_fbp'], sessionStorage: ['campaign-id'] },
  },
});
```

`init()` from `@c15t/browser` and `createConsentRuntime` from `c15t/runtime`
take the same option. Each reads it once, when the client or runtime is
created.

## Attach cleanup to your own kernel

If you assemble c15t modules yourself, attach cleanup in the browser after
persistence and the script loader:

<include src="../../shared/examples/javascript/clear-on-revocation.mdx" />

`createClearOnRevocation({ kernel, config, storageConfig? })` returns
`{ dispose }`. Pass the same `storageConfig` as your persistence module, so a
custom `storageKey` stays protected. If the policy has already resolved,
attaching can delete data for denied categories at once. Disposing stops the
cleanup; it deletes nothing. Do not attach it when `init()` or the runtime
already has `clearOnRevocation`.
