## Where choices are stored

The persistence module writes each recorded choice to a first-party cookie
and to localStorage, and reads them back when the page loads. The visitor's
choice survives reloads and later visits without a backend request.
`@c15t/browser` and `createConsentRuntime` run it by default.

| Stored item | Name, with the default key |
| --- | --- |
| Category choice | `c15t` cookie and localStorage key |
| Notice acknowledgement | `c15t-notice` |
| Vendor choice | `c15t-vendors` |
| Subject ID | `c15t-sid` |
| Saves waiting to reach the backend | a separate localStorage queue |

The cookie is readable by your server, so a server-rendered page can see the
visitor's choice before any script runs.

## A subject ID from the first page load

Every visitor gets a subject ID (`sub_…`) when the module starts, before
they decide anything. It is in `snapshot.subject.subjectId` from the first
snapshot after the runtime starts, so you can link activity to the visitor
from the first page load and still find it when they opt out later.

- The ID is stored in `c15t-sid` at once, so a reload keeps it. The first
  save records the same ID with the choice.
- `c15t-sid` is not a choice. A visitor with only an ID still sees the
  banner, and `hasConsented()` stays `false`.
- `clear()` and a revocation keep the ID; only recorded choices go. Call
  `kernel.set.subjectId(null)` to start over with a new ID.
- An ID stored with a choice wins over `c15t-sid`. Two tabs that open
  together each generate one. Until a tab saves or identifies the visitor,
  its ID follows the one another tab stored, and the kernel emits
  `subject:resolved` with `previousSubjectId` so you can move anything
  recorded under the old ID.
- For a visitor with a stored choice, a new ID from `kernel.set.subjectId()`
  reaches `c15t-sid` when the choice is rewritten with it. If the page
  unloads before the write code loads, both keep the old ID.

## Set the subject ID on your server

When your server answers the first request, it can create the subject ID
and send it back as the `c15t-sid` cookie. The server render and the browser
then start with the same ID, as long as the browser keeps accepting c15t's
cookie writes. The Next.js, TanStack Start, Astro, SvelteKit
and Nuxt adapters do this for you; see their rendering pages. On another
server, call `resolveRequestSubject()` from `c15t/server` in your request
handler:

<include src="../../../shared/examples/javascript/server-subject.mdx" />

`resolveRequestSubject()` reads the ID from the stored consent records, then
from `c15t-sid`, and creates one only when neither has it, the same order
the browser uses. It reads cookies only. If the browser refused to rewrite a
record cookie after the subject ID changed, that cookie still holds the old
ID while the browser's localStorage holds the new one. The server then
reports the old ID, and the browser starts with the new one from its
storage. This happens even when the request's `c15t-sid` cookie already holds
the new ID. It lasts until a later write of that record reaches the cookie,
which may never happen while the browser keeps refusing it. The server never
replaces a `c15t-sid` cookie the request already has, so it cannot store the
old ID over the new one. It returns:

| Field | What it is |
| --- | --- |
| `subjectId` | The visitor's subject ID. |
| `setCookie` | The `c15t-sid` cookie to set on the response, with its `header` value and attributes. `null` when the request already has a `c15t-sid` cookie, even one holding a different ID. |
| `cookie` | The request `Cookie` header, with `c15t-sid` added when the request had none. Pass it to a render in the same request so the render sees the ID. |

It returns `null` for a prefetch, a prerender, and any response marked
`shared: true`, such as cached HTML. A cookie on a shared response would give
every visitor who receives it the same ID.

Pass the browser's `storage` options so the cookie has the same name,
domain and lifetime. The cookie is `Secure` when the request URL is
`https`. Behind a proxy that terminates TLS, set
`trustForwardedHeaders: true` to read the scheme from `X-Forwarded-Proto`.
Only do that when the proxy overwrites those headers.

## When records are read and written

Stored records are read synchronously when the module starts, so a
returning visitor's choice applies before the first banner renders.

The code that writes and reconciles records is a separate chunk. Once a
banner or dialog has been shown, it starts loading in browser idle time after
the page's `load` event. It also starts at the first write or reconciliation
if one comes sooner. A returning visitor who sees no prompt downloads it only
when something needs it. Until it has loaded:

- A save waits for its record to be stored before its backend request
  leaves, and before the save resolves. On the first save of a page load,
  this can add the time it takes to fetch the chunk.
- If the chunk fails to load, the save keeps waiting rather than count as
  stored. Its request does not leave, and a revocation reload does not run
  while storage still holds the old choice. c15t tries the chunk again after
  1, 4 and 16 seconds, and at every later save, focus or tab change.
- `reconcile()` returns `false` and runs when the chunk lands.

`clear()` needs no chunk. It removes every record except the subject ID
from the cookie and localStorage, stores the clear epoch and resets the
kernel's records before it returns, so reloading right after a clear cannot
restore a cleared choice.

- `pagehide` cannot store anything. A page restored from the back/forward
  cache stores its pending records when the chunk lands. A page that unloads
  first loses them, along with the save request still waiting for them.

After the chunk has loaded, each write runs in the macrotask after the
visitor acts, and `pagehide` runs any write still waiting.

## Name, domain and lifetime

`storageConfig` sets where and how long records live:

| Option | Default | What it does |
| --- | --- | --- |
| `storageKey` | `'c15t'` | The cookie and localStorage name. Other records use it as a prefix. |
| `crossSubdomain` | `false` | Set the cookie on the root domain, so `www.example.com` and `shop.example.com` share it. |
| `defaultDomain` | current host | An explicit cookie domain, such as `'.example.com'`. Wins over `crossSubdomain`. |
| `defaultExpiryDays` | `365` | Cookie lifetime in days. The policy's own validity still decides when a choice expires. |

Use the same `storageConfig` on every site that shares the cookie. Pass it to
`init()` or `createConsentRuntime`, or inside `persistence` for a runtime:

{/* example: fragment */}

```ts
storageConfig: { crossSubdomain: true },
```

## Keep open tabs in step

Tabs on the same origin share localStorage, so a choice made in one tab
reaches the others at once through the `storage` event. A tab on another
subdomain that shares only the cookie gets no such event. It reads stored
records again when the page becomes visible or the window regains focus.

Call `runtime.reconcileStorage()` to read them at another moment, for
example after a response set the consent cookie. With `@c15t/browser`, call
`client.runtime.reconcileStorage()`. `persistence: { sync: false }` on the
runtime or the `@c15t/browser` client turns the automatic reads off.
[Keep open tabs in step](/docs/concepts/consent-state#keep-open-tabs-in-step)
explains the merge rules.

## Turn it off

`persistence: false` on `createConsentRuntime` or on `init()` from
`@c15t/browser` keeps choices in memory only.
Every page load starts without a choice, so the banner shows on every page.
The subject ID also lives in memory only, so each page load gets a new one.

## Attach it to your own kernel

A kernel from `createConsentKernel` stores nothing. Create the module before
`commands.init()` so stored choices apply first:

<include src="../../../shared/examples/javascript/kernel.mdx" />

`createPersistence({ kernel, storageConfig?, skipHydration?, sync? })`
returns:

| Member | What it does |
| --- | --- |
| `hydrate()` | Read storage again. Returns whether any record was found. |
| `reconcile()` | Merge records another tab or runtime stored. Returns whether anything changed. |
| `clear()` | Delete every c15t record except the subject ID and reset the kernel's records. |
| `dispose()` | Stop writing and remove the tab listeners. Stored records stay. |

`skipHydration: true` skips the first read, for a kernel a server already
seeded with the visitor's records.

## Check it works

1. Load the page and open DevTools, Application. A `c15t-sid` cookie holds a
   `sub_…` ID and the banner still shows.
2. Accept all. A `c15t` cookie and a `c15t` localStorage entry exist.
3. Reload. The banner stays closed and `c15t-sid` holds the same ID.
4. Open a second tab, reject all there and switch back. The first tab now
   shows the rejection.
