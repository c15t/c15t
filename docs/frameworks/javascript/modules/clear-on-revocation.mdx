## Delete what a vendor stored

Gating stops new requests but leaves cookies and storage keys a vendor
already wrote. `clearOnRevocation` names them per category, and c15t deletes
them when that category is denied:

{/* example: fragment */}

```ts
clearOnRevocation: {
  measurement: { cookies: ['_ga', '_ga_*'], localStorage: ['analytics:*'] },
},
```

Pass it to `init()` from `@c15t/browser` or to `createConsentRuntime`. It is
read once, when the client or runtime is created.

## When it runs

c15t waits for the policy to resolve, then deletes the listed data:

- once at start, for categories that are already denied;
- whenever an allowed category becomes denied.

It never deletes c15t's own records. Editing switches in the dialog without
saving deletes nothing.

## Targets

| Field | Takes |
| --- | --- |
| `cookies` | Cookie names, or prefixes ending in `*` such as `'_ga_*'`. An object `{ name, domain?, path?, partitioned? }` targets a cookie set on another domain or path. |
| `localStorage` | Keys, or prefixes ending in `*`. |
| `sessionStorage` | Keys, or prefixes ending in `*`. |

A script cannot delete an `HttpOnly` cookie or a cookie set for another site.
[Clear on revocation](/docs/integrations/clear-on-revocation) covers cookie
domains, paths and the other browser limits.

## Attach it to your own kernel

<include src="../../../shared/examples/javascript/clear-on-revocation.mdx" />

`createClearOnRevocation({ kernel, config, storageConfig? })` returns
`{ dispose }`. Pass the same `storageConfig` as your persistence module, so a
custom `storageKey` stays protected. Disposing stops the cleanup; it deletes
nothing.

## Check it works

1. Allow measurement and let the vendor set its cookies. DevTools,
   Application, Cookies shows them.
2. Withdraw measurement. The listed cookies and keys are gone after the save,
   before the page reloads.
