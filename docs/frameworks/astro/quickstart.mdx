## Before you start

[Create an Inth project](https://inth.com) and set it up before you touch the
code:

1. Add policy rules that cover the `measurement` and `marketing` categories.
   This guide loads PostHog on measurement and X Pixel on marketing.
2. Add your site's origin to the project's trusted origins.
3. Copy the project's backend URL. It is public configuration, not a secret.

Then decide how Astro builds your pages. The integration supports both, and
[Rendering and deployment](/docs/frameworks/astro/rendering) covers mixed and
cached setups.

| Your site | Astro output | c15t mode |
| --- | --- | --- |
| Static pages on any static host, no adapter | `output: 'static'` | `hosted()` |
| Pages rendered on each request, with a server adapter | `output: 'server'` | `manifest()` |

## Install the packages

<CommandTabs command="c15t@alpha @astrojs/svelte svelte @c15t/scripts@alpha" mode="install" />

The banner is plain `.astro` markup and ships no framework JavaScript. The
preference dialog is an island that loads when a visitor first reaches for it.
The `ui` option picks the framework that renders it, and the `c15t` package
includes the dialog for Svelte, React and Vue.

Use the framework your site already ships, so visitors do not download a second
one for a single dialog. This guide uses Svelte, the default. For React, install
`@astrojs/react react react-dom` instead of `@astrojs/svelte svelte`, register
`react()` and set `ui: 'react'`. For Vue, install `@astrojs/vue vue`, register
`vue()` and set `ui: 'vue'`.

## Set the backend URL

The configuration below reads the backend URL from `C15T_BACKEND_URL`. Astro
evaluates `astro.config.mjs` before it loads `.env` files, so set the variable
in your shell for local work and in your host's build settings for deploys.
Paste the URL from your Inth project:

```sh
C15T_BACKEND_URL="<backend URL from your Inth project>" npx astro dev
```

## Configure the integration

Pick the file that matches your output. Register the framework integration
before `c15t()`.

### Static output

<include src="../../shared/examples/astro-demo/static-config.mdx" />

`hosted()` sends the browser straight to your Inth backend, so no server is
needed. A static page is the same for every visitor, which means the banner
appears once the browser's `/init` request returns, not in the first HTML.

### Server output

<include src="../../shared/examples/astro-demo/server-config.mdx" />

`manifest()` caches your project's public policy file on the server and
resolves each request from it. The first HTML already contains the banner, or
no banner at all for a visitor who has chosen. It adds `/api/c15t/init` and
`/api/c15t/manifest` routes, so it needs a server adapter. Use the adapter for
your host in place of `@astrojs/node`.

The integration writes its options into the page as JSON. Keep callbacks,
vendor helpers and secrets out of `c15t({ ... })`. They belong in the module
that `clientEntrypoint` names.

## Register vendor scripts

Remove any existing PostHog or X Pixel snippet first, so each vendor loads once.
Add the public IDs to your environment. Unlike the backend URL, Vite reads these
from `.env`:

```dotenv title=".env"
PUBLIC_POSTHOG_KEY=
PUBLIC_X_PIXEL_ID=
```

Astro builds these values into the browser code, so restart `astro dev` or
rebuild after you change them. An empty value leaves that vendor out. Create
the script list. It selects
PostHog's EU region. Change `region` to `'us'` for a US project.

<include src="../../shared/examples/astro-demo/scripts.mdx" />

PostHog waits for measurement permission and does not fall back to cookieless
capture. X Pixel waits for marketing permission.

Then export the scripts from the client entrypoint that `astro.config.mjs`
points at:

[integrations](/docs/integrations/overview) for the list, and

iframes and network blocking.

## Add the consent components to your layout

<include src="../../shared/examples/astro-demo/layout.mdx" />

Wrap every page in this layout. `ConsentScript` goes in `<head>`, where it
hands the browser the server's decision and sets the color scheme before first
paint. `ConsentBanner` renders the banner, `ConsentDialog` reserves a place for
the preference dialog, and `ConsentDialogTrigger` is the link visitors use to
change their mind later. The integration adds the stylesheet to every page, so
you do not import one.

`ClientRouter` is optional. With it, the consent runtime survives page
navigation. Without it, each page load starts the runtime again from the stored
choice.

## Check that it works

Build and preview the site, then open it in a private window with DevTools open
on the Network tab:

1. Before you choose, the banner shows and there are no requests to
   `posthog.com` or `static.ads-twitter.com`.
2. Select **Reject All** and reload. The banner stays closed and neither vendor
   loads.
3. Open **Cookie preferences**, turn on **Measurement** and select **Save Settings**. PostHog loads;
   X Pixel does not.
4. Turn on **Marketing** and save. X Pixel loads.
5. Turn both off and save. The page reloads, and neither vendor loads again.

On server output, the page source of a first visit contains the banner markup.
On static output it does not, and the banner appears after the `/init`
request. Follow [Verify consent](/docs/guides/verify-consent) before you
ship.
