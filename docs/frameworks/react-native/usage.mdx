## The provider

`C15tProvider` is the only component you must mount. It reads the handshake from the
native core once, publishes the client to the tree below it, and holds no consent state
of its own. It takes a single prop, `children`.

```tsx title="src/Consent.tsx"
import type { ReactNode } from 'react';
import { C15tProvider } from '@c15t/react-native';

export function Consent({ children }: { children: ReactNode }) {
	return <C15tProvider>{children}</C15tProvider>;
}
```

Mount it once, near the root. A nested provider reuses the ancestor's client rather
than attaching a second native listener, so a test harness or a Storybook story that
wraps an already-provided subtree is safe.

The provider runs the protocol handshake during render and throws rather than
rendering a consent surface over state it cannot trust:

- `NativeC15tUnavailableError` when the native module is not in the running binary,
  which is what happens in Expo Go or after an install without a rebuild.
- `C15tProtocolMismatchError` when the embedded native build speaks a protocol this
  bundle does not support. The fix is a rebuild, not a JavaScript update.

## Hooks

Every hook reads the native snapshot or forwards an action. None of them hold state.

| Hook | Returns | Rerenders when |
| --- | --- | --- |
| `useIsAllowed(category)` | `boolean` | that one category flips |
| `useConsentDecision(category)` | `'granted' \| 'denied' \| 'pending'` | that one category's answer moves |
| `useConsentStatus()` | `{ ready, policyPending, activeUI, promptRequirement }` | one of those four fields moves |
| `useConsentSelector(selector, equals?)` | whatever `selector` returns | the selected value changes under `equals` |
| `useConsentActions()` | a stable `ConsentActions` object | never, the object is stable |
| `useC15tBootstrap()` | `BootstrapPayload` | never, it is read once at mount |
| `useConsent()` | the whole `ConsentSnapshot` | every native change |
| `useIsTrackingAllowed(category)` | `boolean` | consent for that category or the platform tracking answer moves |
| `useTrackingAuthorization()` | `'authorized' \| 'denied' \| 'not-determined' \| 'restricted' \| 'unsupported'` | a tracking request resolves |

Every type those hooks trade in is exported from `@c15t/react-native`: `ConsentSnapshot`,
`ConsentActions`, `ConsentGateProps`, `ConsentPromptState`, and the vocabulary behind them
(`AllConsentNames`, `OptionalConsentCategory`, `ConsentState`, `PromptRequirement`,
`RestrictionReason`). `CONSENT_CATEGORIES` and `OPTIONAL_CONSENT_CATEGORIES` are exported
too, for a preference center that renders whatever categories exist rather than naming
four. They are the same names and the same order the native cores and the web kernel use,
and a test in this repository fails if the three ever disagree.

`necessary` is always allowed. Every optional category reads `false` while hydration or
the first policy resolution is outstanding, so `useIsAllowed` needs no loading branch.

```tsx
import type { ReactNode } from 'react';
import { useIsAllowed } from '@c15t/react-native';

export function PersonalisedAds({ children }: { children: ReactNode }) {
	return useIsAllowed('marketing') ? <>{children}</> : null;
}
```

`useConsent()` rerenders on changes your screen does not care about. Reach for it only
in a surface that genuinely reads several slices, such as a preference center.

## Pending is not a refusal

`useIsAllowed` answers `false` twice for two different reasons: the subject refused, or
the policy has not resolved yet. Rendering nothing is usually right in both cases.
Starting a vendor SDK imperatively is not, because those two answers need opposite
handling. A refused category stays off. An unresolved one stays off *and keeps
listening*, because waiting on an unknown is the violation a CMP exists to prevent, and
giving up on it switches off a category the subject was about to grant.

`useConsentDecision` answers `'pending'` for the second case:

```tsx
import { useEffect } from 'react';
import { useConsentDecision } from '@c15t/react-native';

export function Attribution() {
	const decision = useConsentDecision('measurement');

	useEffect(() => {
		// `pending` is not a promise that an answer is coming: a first launch with
		// no network stays pending for the life of the process. Bound the wait
		// yourself if you cannot afford it.
		if (decision === 'granted') measurementSdk.init();
	}, [decision]);

	return null;
}
```

The three answers come from the snapshot the consent UI is rendering, so a gate cannot
disagree with what the user is looking at. The native cores expose the same three states
to Swift and Kotlin callers, which is what lets an SDK initialized in
`Application.onCreate` or `AppDelegate` make the same call as one initialized in a
component.

Pass `useConsentSelector` a selector that outlives the render. Hoist it to module scope
or wrap it in `useCallback`; an inline arrow is new every render and makes React
resubscribe each time.

```tsx
import { Text } from 'react-native';
import type { ConsentSnapshot } from '@c15t/react-native';
import { useConsentSelector } from '@c15t/react-native';

const selectSubjectId = (snapshot: ConsentSnapshot): string | null =>
	snapshot.subject?.id ?? null;

export function SubjectId() {
	const subjectId = useConsentSelector(selectSubjectId);

	return subjectId === null ? null : <Text>{subjectId}</Text>;
}
```

The actions object is stable for the life of the provider, so it is safe in a
dependency list:

```tsx
import { useCallback } from 'react';
import { Pressable, Text } from 'react-native';
import { useConsentActions } from '@c15t/react-native';

export function AcceptButton() {
	const actions = useConsentActions();
	const onPress = useCallback(() => {
		void actions.acceptAll();
	}, [actions]);

	return <Pressable onPress={onPress}><Text>Accept all</Text></Pressable>;
}
```

`acceptAll()`, `rejectAll()` and `save()` resolve with a `CommitResult`. Consent is
applied locally either way, so check `queued` before treating a resolved promise as a
delivered write. `dismissNotice()` is local and synchronous: a notice is an
acknowledgement, not a consent record, so nothing is sent to the backend.

`identify(externalId)` attaches an id from your own account system and loads that
subject's stored record. `logout()` detaches it and keeps consent on the c15t subject
id, so signing out does not reset consent.

## Start the device over

`reset()` wipes consent and puts the device back in the state a first launch boots with.
Use it for a "start over" affordance, for a subject who withdrew everything and has to
answer again, and for a reviewer who needs the fresh-install state without reinstalling
the app.

```tsx
import { useConsentActions } from '@c15t/react-native';

const actions = useConsentActions();

await actions.reset();
```

The prompt is owed again afterwards, so the banner or dialog returns: a wipe is not a
recorded reject-everything, and the difference is the receipt. A recorded denial keeps
`explicitChoice` and leaves `promptRequirement` at `none`, so nothing comes back and the
subject has no way out of it. A wipe clears the receipt, and once the policy resolves
again `useConsentStatus()` reads `promptRequirement: { kind: 'choice', reason: 'missing' }`
and `activeUI: 'banner'`, exactly as it did before the subject was ever asked. In between,
while the re-resolve is outstanding, it reads `policyPending: true` and `ready: false` with
every optional category denied, which is the same answer an unreadable store and a device
that has never been used both give.

A wipe keeps three things:

- the c15t subject id, because the backend files the audit history under it. Erasing what
  the backend holds for that subject is a backend call; `reset()` only clears the device.
- overrides and the GPC override, which are configuration. See
  [overrides](/docs/frameworks/react-native/configuration#overrides).
- the configured category scope, for the same reason.

It deletes the stored snapshot and the queued offline writes rather than writing a denial
over them, so a save that had not been delivered is dropped instead of replayed: it carried
a decision the subject just withdrew. A save already on the wire cannot be recalled, and the
promise does not wait for one. `reset()` resolves once the device is durable, and the policy
re-resolves in the background the way a first launch does, so a banner that comes back can
arrive a moment after the promise.

The revision counter keeps counting up rather than restarting: a wipe is one committed
mutation, so it publishes the revision the device was on plus one. On a binary older than
this package, `reset()` rejects with `NativeBridgeError` naming a rebuild, because a
JavaScript update cannot add a native method.

## Tracking needs two answers

An advertising identifier takes two separate yeses. The subject's comes from c15t. The
device's comes from the platform: App Tracking Transparency on iOS, and nothing on
Android, where the identifier sits behind Google Play services' own consent surface
rather than anything this package reads.

`useIsTrackingAllowed(category)` is `true` only when both are in. Consent granted on a
device where Apple says no is `false`, and ATT authorized for a category the subject
refused is `false`. This is the hook an analytics or ad SDK gates on, because either
half read alone is wrong in a different direction.

```tsx
import { useEffect } from 'react';
import { useIsTrackingAllowed } from '@c15t/react-native';

export function Attribution() {
	const allowed = useIsTrackingAllowed('measurement');

	useEffect(() => {
		if (allowed) adSdk.enableAttribution();
	}, [allowed]);

	return null;
}
```

Read the platform half on its own with `useTrackingAuthorization()`. Two of its arms are
instructions to do opposite things, so keep them apart:

| Arm | Means |
| --- | --- |
| `authorized` | Apple said yes. |
| `denied` | Apple said no, or a parental control did. |
| `restricted` | A device policy decides, and no app can change it. |
| `not-determined` | Nobody has been asked yet. This is where a prompt still belongs. |
| `unsupported` | The platform asks nothing of this build: Android always, and iOS without a prompt string. |

`authorized` and `unsupported` satisfy the platform half. `denied`, `restricted`, and
`not-determined` hold it off.

### Asking the platform

Nothing calls the system prompt for you, and that is deliberate. Apple's dialog is the
first thing a subject reads about tracking if you show it at launch, before anyone has
said what is tracked and why, which is the case App Review rejects. Your consent UI is
where tracking gets explained, so the prompt goes after it:

```tsx
// In the preference center's submit handler, once the choice is recorded.
const onFinish = useCallback(async () => {
	await actions.save({ measurement: true });

	try {
		// The subject knows by now, so Apple may ask.
		await actions.requestTrackingAuthorization();
	} catch {
		// Either this build cannot ask or this platform has nothing to ask.
		// Both mean the platform answer is already final.
	}
}, [actions]);
```

Apple shows the dialog at most once per install, and a later call resolves with the
answer already on the device. The call rejects with:

- `C15T_TRACKING_NOT_CONFIGURED` on an iOS build whose `Info.plist` carries no
  `NSUserTrackingUsageDescription`. Apple suppresses the dialog there and reports the
  answer back as denied without saying why, so the bridge refuses instead of spending
  the one prompt an install gets for nothing. The Expo plugin writes that key under
  `enableAppTrackingTransparency`, described in
  [configuration](/docs/frameworks/react-native/configuration).
- `C15T_TRACKING_UNSUPPORTED` on Android, where there is no platform question to ask.

### What no platform answer changes

A tracking arm never moves a consent decision. `useConsentDecision` and `useIsAllowed`
read the snapshot alone, so `marketing` refused on a device with ATT authorized is still
`denied`, and a policy that has not resolved is still `pending` however Apple answered.
The two answers meet in one exported function,
`isTrackingPermitted(decision, authorization)`, and both native cores are held to the
same rule by [native behaviour](/docs/frameworks/react-native/native-behaviour).

## Built-in surfaces

Three components ship with the package. They are optional, and everything they render
is reachable through the hooks.

| Component | Props | Opens itself |
| --- | --- | --- |
| `ConsentBanner` | `onCustomize?`, `styles?`, `theme?` | yes, while a prompt is owed |
| `ConsentDialog` | `open`, `onRequestClose`, `onOpenPreferences?`, `styles?`, `theme?` | no |
| `ConsentPreferences` | `open`, `onRequestClose`, `styles?`, `theme?` | no |

The banner is an absolutely positioned layer over your app, never a row in its layout,
so nothing on screen moves when a policy resolves a prompt. Without `onCustomize` it
opens the built-in dialog itself, which is what makes `<ConsentBanner />` alone a
complete prompt.

```tsx title="src/Consent.tsx"
import { useState } from 'react';
import type { ReactNode } from 'react';
import { Pressable, Text, View } from 'react-native';
import {
	ConsentBanner,
	ConsentPreferences,
	C15tProvider,
} from '@c15t/react-native';

export function Consent({ children }: { children: ReactNode }) {
	const [preferencesOpen, setPreferencesOpen] = useState(false);

	return (
		<C15tProvider>
			<View style={{ flex: 1 }}>
				{children}
				<Pressable onPress={() => setPreferencesOpen(true)}>
					<Text>Manage preferences</Text>
				</Pressable>
			</View>
			<ConsentBanner />
			<ConsentPreferences
				onRequestClose={() => setPreferencesOpen(false)}
				open={preferencesOpen}
			/>
		</C15tProvider>
	);
}
```

Keep a standing entry point like that one. The banner only appears while a prompt is
owed, so without it a subject cannot revisit a decision.

`ConsentDialog` and `ConsentPreferences` both show every category in scope with one
switch each, and both write only the categories on screen. `ConsentPreferences` does
not gate on a prompt, so it works at any time, and closing it without pressing save
writes nothing at all.

Use `ConsentDialog` instead of `ConsentPreferences` when you want the mid-prompt
experience and a link into your own finer controls:

```tsx title="src/Consent.tsx"
// Fragment: add this state and these elements inside your provider component.
const [dialogOpen, setDialogOpen] = useState(false);

<>
  <ConsentBanner onCustomize={() => setDialogOpen(true)} />
  <ConsentDialog
    onOpenPreferences={() => setPreferencesOpen(true)}
    onRequestClose={() => setDialogOpen(false)}
    open={dialogOpen}
  />
</>
```

The dialog reads copy only while it is closed, so a grant made elsewhere in the app
leaves it alone. A mounted-and-shut dialog holds no consent subscription at all.

Copy comes from the translation bundle on the snapshot, which the backend serves in the
resolved language. Every string has an English fallback, so a partial bundle renders
readable labels rather than `undefined`.

### Restyle them

`theme` takes a `ConsentTheme`, `styles` takes per-part overrides. Themes are plain
data, so build one at module scope.

```tsx
import { ConsentBanner, createConsentTheme } from '@c15t/react-native';

// Build themes at module scope so the object identity stays stable.
const theme = createConsentTheme({
	colors: { primary: '#7C3AED' },
	radius: { surface: 20 },
});

export const StyledBanner = () => <ConsentBanner theme={theme} />;
```

Overrides are shallow per group, so that theme changes two values and inherits the
rest. For one part of one surface, pass `styles` keyed by a part name from
`CONSENT_THEME_PARTS`: `sheet`, `header`, `title`, `description`, `footer`,
`primaryButton`, `primaryLabel`, `secondaryButton`, `secondaryLabel`, `categoryRow`,
`categoryTitle`, `categoryDescription`, `switch`, `scroll`, `overlay`, `banner`,
`handle`, `row`, `label`, `caption`, `captionLink`. The list is closed on purpose:
anything it does not cover belongs in a theme token.

Without `theme`, the surfaces follow the platform scheme and pick `light` until
`useColorScheme()` answers, so the first frame never flashes the dark palette.

`lightTheme` and `darkTheme` are finished themes for when you want to pick one rather than
describe one. Both are `createConsentTheme` output, and a theme you pass is used exactly as
given, so nothing merges your palette over the platform one behind your back.

To build a surface out of the same tokens the built-ins use, call `useConsentStyles`. It
takes the same `theme` and `styles` props and returns the resolved per-part styles plus the
scale facts a layout needs: `fontScale`, `controlMinHeight`, `maxBodyHeight`, `safeArea`,
and `bannerLayer`. Copying numbers out of the built-in sheets instead is how a custom prompt
ends up with a 28 pt tap target the first time a subject turns their device font size up.

## Build your own surfaces

Three headless components call a function with the smallest slice they need. Use them
where a hook would force an extra component just to hold the call.

| Component | Hands its children | Renders children when |
| --- | --- | --- |
| `ConsentReady` | `{ status, actions }` | hydration and the first policy resolution are done |
| `ConsentPrompt` | `{ activeUI, promptRequirement, actions }` | the policy owes an interaction |
| `ConsentGate` | `{ category, actions }` | the category is allowed |

Each takes `fallback` for the other case.

```tsx title="src/MyPrompt.tsx"
import { Pressable, Text, View } from 'react-native';
import { ConsentPrompt } from '@c15t/react-native';

export function MyPrompt() {
	return (
		<ConsentPrompt
			fallback={null}
		>
			{({ actions, activeUI, promptRequirement }) => (
				<View
					accessible
					accessibilityLabel="Privacy"
					style={{ padding: 16 }}
				>
					<Text>
						{promptRequirement.kind === 'notice'
							? 'How we use your data'
							: 'Your privacy'}
					</Text>
					{activeUI === 'banner' ? (
						<Pressable
							onPress={() => {
								void actions.acceptAll();
							}}
						>
							<Text>Accept all</Text>
						</Pressable>
					) : null}
					{promptRequirement.kind === 'notice' ? (
						<Pressable onPress={actions.dismissNotice}>
							<Text>Acknowledge</Text>
						</Pressable>
					) : null}
				</View>
			)}
		</ConsentPrompt>
	);
}
```

`ConsentPrompt` never renders before the native core has decided, which is the flash
this package exists to prevent. Do not add your own `ready` check around it.

Gate a vendor SDK with `ConsentGate`, or with `useIsAllowed` when the gate is a
condition rather than a subtree:

```tsx
import { ConsentGate } from '@c15t/react-native';

// `AdProvider` and `PlaceholderAdProvider` are your own components.
export function Attribution() {
	return (
		<ConsentGate category="measurement" fallback={<PlaceholderAdProvider />}>
			{() => <AdProvider />}
		</ConsentGate>
	);
}
```

A JavaScript gate only covers what React Native renders. An analytics SDK you start
from `AppDelegate`, an `Application` class or a native module reads the same snapshot
natively and has to check it there too. See
[native behaviour](/docs/frameworks/react-native/native-behaviour).

For your own preference UI, read the categories from the snapshot and save exactly what
the subject saw:

```tsx
import { Switch } from 'react-native';
import type { ConsentSnapshot } from '@c15t/react-native';
import { useConsentActions, useConsentSelector } from '@c15t/react-native';

const selectMeasurement = (snapshot: ConsentSnapshot): boolean =>
	snapshot.effectivePermissions.measurement;

export function MeasurementSwitch() {
	const allowed = useConsentSelector(selectMeasurement);
	const actions = useConsentActions();

	return (
		<Switch
			onValueChange={(value) => {
				void actions.save({ measurement: value });
			}}
			value={allowed}
			accessibilityLabel="Measurement"
		/>
	);
}
```

`save()` writes only the categories you pass. Omitted categories keep their stored
receipts, which is what stops a preference-center save from renewing a consent the
subject never looked at.

### Clear the home indicator

`useConsentSafeArea()` returns the bands the built-in surfaces lay out against: `bottom`,
`top`, `left`, `right`, and `measured`, which says whether a host supplied real insets or
the package fell back to its reserved floor.

```tsx title="src/MySheet.tsx"
import type { ReactNode } from 'react';
import { View } from 'react-native';
import { useConsentSafeArea } from '@c15t/react-native';

export function MySheet({ children }: { children: ReactNode }) {
	const safeArea = useConsentSafeArea();

	return (
		<View
			style={{
				paddingBottom: safeArea.bottom,
				paddingHorizontal: Math.max(safeArea.left, safeArea.right),
			}}
		>
			{children}
		</View>
	);
}
```

Outside a provider, or where the provider was given nothing, the hook returns the floor and
`measured: false` rather than throwing. The floor is a real layout answer, so your sheet is
never flush against the home indicator just because a host skipped a step. Read `measured`
when you need to know, for example to skip an entrance animation on the pass where the
insets are not final yet.

### Select without over-rerendering

`useConsentSelector` rerenders a subscriber only when its selected value changes, and by
default it compares with `Object.is`. A selector that returns a new object therefore looks
different on every snapshot event, so pass the comparer as the second argument:

```tsx
import {
	isConsentStatusEqual,
	selectConsentStatus,
	useConsentSelector,
} from '@c15t/react-native';

// A shell that shows something different while the policy is still resolving.
const status = useConsentSelector(selectConsentStatus, isConsentStatusEqual);
```

`selectConsentStatus` gives you `ready`, `policyPending`, `activeUI`, and
`promptRequirement`, which are the four fields a shell needs to decide what to render at
all. `shallowEqual` is the comparer for any other flat slice you write yourself, and it is
one level deep because snapshot slices are flat.

For a single category you do not need either hook: `useConsentDecision` returns one of three
strings and `useIsAllowed` returns a Boolean, so both compare by identity and rerender only
on a real change.
