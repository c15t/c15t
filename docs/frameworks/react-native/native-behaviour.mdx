This page is the reason the package exists. Consent decisions are only useful if the
code that acts on them can trust the answer it got, and on mobile that trust is an
ordering problem: an analytics SDK starts long before your React tree has painted.

## The order things happen in

1. The native core starts ahead of React Native. On iOS an Objective-C `+load` runs at
   image load, before React Native initializes. On Android an `androidx.startup`
   initializer runs during `Application.onCreate`, before the first `Activity` exists.
2. `bootstrap()` reads the stored envelope synchronously, before it puts anything on a
   worker. Hydration is the reason this is its own step.
3. The React host starts. `C15tProvider` calls `getBootstrap()` and `getSnapshot()`,
   both synchronous reads of what the core already holds. Neither touches the network or
   the disk.
4. `/init` resolves sometime later. That folds a policy into the snapshot, bumps
   `revision`, and the mounted subscribers whose slice moved rerender.

So the first JavaScript frame already resolves against real stored consent, not an empty
in-memory object. This is what prevents the common bug where an SDK initializes on a cold
start because the check ran against state that had not loaded yet.

## Four states, and only two are answers

Every gate reads two flags: `ready` covers hydration, `policyPending` covers the first
init.

| `ready` | `policyPending` | What it means | `useIsAllowed('measurement')` |
| --- | --- | --- | --- |
| `false` | `true` | Nothing has hydrated yet, or the store could not be read. | `false` |
| `true` | `true` | Stored consent is loaded; the policy has not resolved. | stored value, `false` for optional categories |
| `true` | `false` | A real answer. | the effective permission |
| `false` | `false` | Not a state the cores produce; treat it as the row above. | `false` |

`necessary` is the one category that is always allowed. While either flag is unset, every
optional category reads `false`, with no default-on and no model sniffing. `isAllowed`
never needs a loading branch, because "unknown" and "denied" give the same instruction:
do not process. What those two rows do not share is what happens next, and a vendor
wrapper that holds events waiting for a grant has to know which one it received.
`decision` is that answer.

## An unreadable store fails closed

A stored envelope the running build cannot read is indistinguishable from a fresh
install: `ready: false`, `policyPending: true`, every optional category `false`, and
nothing from those bytes applied. That identity is the point. There is no partial read,
because half an envelope answers like a returning user, and a permission assembled out of
garbage is indistinguishable from one the subject actually gave.

It covers a field the build does not model, a write that stopped partway through (the
one shape most likely to read as valid), a document written by an older wire revision,
and a document from another codec entirely, including a genuine web v3 record. The web
SDK writes a v3 consent record to `localStorage` or a cookie and neither native core
reads it, so a shared-origin document is not a fallback.

The subject id survives on both platforms. Losing the consent envelope never costs a
device its identity, which matters because the identity is a random UUID the SDK owns and
nothing derived from IDFV, ADID or any other persistent hardware identifier.

`reset()` lands on that same shape on purpose, and it gets there by deleting the stored
envelope and the offline queue on both platforms rather than writing a denial over them.
It is also the only way back to a first launch on a device you already used: an iOS
uninstall leaves the Keychain item behind, and an Android reinstall keeps `SharedPreferences`
unless you clear app data, so a wipe is the repeatable path and a reinstall is not. The
subject id is kept through it, for the reason above.

A failed init does not throw into your app. It sets `snapshot.error`, keeps
`policyPending` true, and leaves every optional category denied. If JavaScript receives a
snapshot payload it cannot parse at all, it serves the same deny-all shape with the error
code `invalid-native-snapshot` and keeps the last snapshot it did understand for
rendering.

## What JavaScript never does

The React Native layer holds no consent state, evaluates no policy, persists nothing, and
queues nothing. It imports the core package for types and pure selectors only. Selectors
in this package read `effectivePermissions` and apply the two lifecycle flags. They decide
nothing.

That single-owner rule is why `useConsent()` and a native `isAllowed` read cannot
disagree, and why there is no reconciliation step to reason about. The Swift, Kotlin and
TypeScript implementations are held to identical request bodies and snapshots by shared
protocol fixtures, so a difference between platforms is a bug rather than a documented
variance.

## Gating a native analytics SDK

An SDK you start from `AppDelegate`, an `Application` class or a native module runs
outside React and outside `ConsentGate`. Read the same snapshot natively. The reads are
synchronous and never block on I/O, which is what makes them safe to call from an SDK
initializer on the main thread.

```swift
// After the launch hook has run, in your analytics setup.
// `Analytics` is your own wrapper around the vendor SDK.
if C15t.isAllowed(.measurement) {
    Analytics.start()
}
```

```kotlin
// Application.onCreate, after c15t's initializer has run.
// `Analytics` is your own wrapper around the vendor SDK.
if (C15t.isAllowed(ConsentCategory.MEASUREMENT)) {
    Analytics.start()
}
```

Neither call waits, so neither defers your launch. A permission that changes later does
not un-start an SDK you only started on a `false`, so register for the change as well:

```swift
// Keep the core reachable; the core owns the subscription it hands back.
C15t.current?.gate(.measurement) { allowed in
    if allowed { Analytics.start() } else { Analytics.pause() }
}
```

The core fires the callback immediately with the current value and then on every change,
so there is no initial-state race to write around. `gate` lives on the core instance,
which is `C15t.current` after bootstrap, and takes an `OptionalConsentCategory` and a
`(Bool) -> Void`. Android exposes the same shape through
`C15t.gate(category) { allowed -> }`.

### Three answers, not two

`isAllowed` returns one Boolean, and `false` in it means two opposite things: the subject
refused, or nothing has resolved yet. Both say "do not process", so a banner needs no
branch for it. A vendor wrapper does, because the two want different code after the
refusal: a refusal drops what it was holding, and an unresolved policy keeps holding it.

| Decision | When | What the caller owes |
| --- | --- | --- |
| `granted` | Hydrated, policy resolved, permission true. `necessary` always. | Run. |
| `pending` | Not hydrated, or the first init has not answered. | Do not run, and keep listening. |
| `denied` | Hydrated, policy resolved, permission false. | Do not run, and stop waiting. |

```swift
// AppDelegate, before React mounts. `Analytics` is your own wrapper.
guard let core = C15t.current else {
    Analytics.pause()
    return
}

switch core.decision(for: .measurement) {
case .granted:
    Analytics.start()
case .pending:
    Analytics.pause() // Keep the buffer. The grant may arrive on the next line.
case .denied:
    Analytics.pauseAndDiscard()
}
```

```kotlin
// Application.onCreate, after c15t's initializer has run.
when (C15t.decision(ConsentCategory.MEASUREMENT)) {
    ConsentDecision.GRANTED -> Analytics.start()
    ConsentDecision.PENDING -> Analytics.pause() // Keep the buffer.
    ConsentDecision.DENIED -> Analytics.pauseAndDiscard()
}
```

`isReady()` is the same question one level up: hydrated, and the first init resolved a
readable policy. Read it when you need to log or report why something stayed off, because
`isReady() == false` says the `false` you are acting on is not the subject's answer.
`decision` derives from the snapshot and nothing else, so it can never disagree with what
`useConsent` is showing, and neither read touches disk or network.

To observe the three-valued answer instead of reading it, register on the same gate:

```swift
// Swift takes an overload; the closure type selects it.
C15t.current?.gate(.measurement) { decision in
    if decision == .granted { Analytics.start() } else { Analytics.pause() }
}
```

```kotlin
// Kotlin names it, because (Boolean) -> Unit and (ConsentDecision) -> Unit both
// erase to Function1 and cannot be declared as two methods.
C15t.gateDecision(ConsentCategory.MEASUREMENT) { decision ->
    if (decision == ConsentDecision.GRANTED) Analytics.start() else Analytics.pause()
}
```

Both fire at registration with the decision as it stands, including one reached long
before the call, then on every change, and the returned handle cancels. Registration is
never silence.

Two rules decide whether this API earns its place:

- Treating `pending` as `denied` and unsubscribing is the bug. An SDK that stops listening
  while the policy is unresolved never hears the grant, and nothing tells you.
- No platform permission moves a category from `pending` or `denied` to `granted`.
  A device with App Tracking Transparency authorized and consent denied is still denied.
  Advertising identifiers are a second, separate question, and answering it is not consent.

Three consequences worth stating plainly:

- A gate that starts an SDK only when a React component renders is a leak. Anything the
  binary starts before React mounts has already bypassed your JSX.
- Starting an SDK on a `false` because hydration had not finished is the failure this
  ordering exists to prevent, and it is silent. If a vendor request must not happen
  before consent, gate the vendor where it is started, not only where it is rendered.
- Gating JavaScript-rendered functionality is not the same as putting a vendor behind
  consent. The vendor's own initialization is the request.

## Tracking authorization is a second gate

The bridge answers two questions about tracking and keeps both away from consent.
`getTrackingAuthorization()` reports the arm the platform holds right now. It is
synchronous, reads no disk and no network, and requests nothing.
`requestTrackingAuthorization()` asks, and only when a host calls it.
`requestTracking()` is the same call with the two fields that say how the request ended,
and `useTrackingRequest` is the hook that drives the whole journey from one button. The
combined answer a caller should gate on is `isTrackingAllowed(category)`, which is consent
and platform together.

On iOS the read is Apple's `trackingAuthorizationStatus` and the request is Apple's
dialog. Both start by checking `NSUserTrackingUsageDescription`, the same key Apple
checks. A binary without it cannot show a dialog, and asking anyway returns `denied` with
no explanation, so the bridge refuses with `C15T_TRACKING_NOT_CONFIGURED` instead of
putting a refusal nobody made on the record. For the same reason a read reports `unsupported`
rather than Apple's silent `denied`: holding every optional category off on a device
whose host never asked for Apple tracking would be an analytics bug, not a privacy win.

Android always reports `unsupported`, and its request rejects with
`C15T_TRACKING_UNSUPPORTED`. The advertising identifier there sits behind Google Play
services' own consent surface, which this package does not depend on, and the platform has
no equivalent question to answer. Inventing one would report either a platform yes or a
platform no, and neither is true. A caller has to be able to tell "there is no such
question here" from "the subject has not been asked yet", which is what the separate
`not-determined` arm is for: it means a prompt still belongs somewhere, and `unsupported`
means the platform adds no bar and the subject's choice decides alone.
`useTrackingRequest` runs into the same rejection and hands it to its caller instead of
opening anything, which is why one consumer integration covers both platforms.

Two arms clear the platform half, `authorized` and `unsupported`.

How often a dialog can appear is Apple's decision, not this package's. A request always
goes to Apple rather than being answered from the arm the device already holds. In the
regions where Apple has enabled its expanded prompt, an answered request can be presented
again about a year after the answer, whichever way it went. Answering from the cache would
have this package enforce a one-prompt lifetime Apple no longer holds, and it would do it
silently, so no host could ever get the later prompt. Asking costs nothing when the install
is not eligible: Apple draws nothing and calls back with the arm on file. `restricted` is
the one arm kept out of Apple's way, because a device policy has already answered and a
call would only report the same arm back.

Apple is equally quiet about an answer the subject changes in the Settings app, so
`C15tProvider` re-reads the platform arm when the app returns to the foreground. That is
the moment the gap matters: someone turns tracking off under `Privacy & Security`, comes
straight back, and a cached `authorized` would otherwise keep tracking behaviour running
until the next launch. Outside that, a read still only moves after a request or on the next
launch.

None of it moves a consent decision. `decision`, `isAllowed`, and the snapshot are a
function of the resolved policy and the subject's c15t choice, with no tracking arm among
the inputs: `granted` with ATT denied stays denied, and `pending` with ATT authorized
stays pending. The combination is one function per side, `isTrackingPermitted` in
JavaScript and `C15tTrackingGate.mayTrack(decision:authorization:)` for a Swift caller
that gates outside React, and both are asserted against every arm rather than left to the
caller to remember. A Kotlin caller has nothing to combine: `C15t.isAllowed(category)` is
already the whole answer on a platform that asks nothing.

### Two Apple calls, and how the SDK picks one

Apple ships the expanded tracking request with iOS and iPadOS 27.2, a release Apple
currently documents as beta. That is newer than the SDK this package compiles against, so
there is no declaration to write an availability check against. Instead the bridge asks the
running process whether `ATTrackingManager` answers the expanded selector, which is the same
question the Objective-C runtime asks itself before it dispatches: true on a system that
has the call, false on every older one. The package floor stays where
[platform support](/docs/frameworks/react-native/platform-support) lists it, and a system
without the call gets the standard prompt rather than a failed request. If the runtime
declines the expanded call after answering true for the probe, the request falls back to
the standard one in the same flight, and `presentation` reports the call that actually ran.

A request that pauses is the reason `requestTracking()` exists. Apple's Additional
Information button closes the expanded sheet without recording an answer, runs the app's
own closure, and completes with `not-determined`. `stage: 'additional-information'` names
that tap, so a caller never reports a refusal the subject did not make. `stage: 'final'`
means the request settled. Both fields are additions to a payload older binaries already
send without them, and a payload that carries no `stage` is read as a settled request,
never as a pause: an over-the-air bundle can run against a binary that predates the
feature, and guessing a pause there would open a preference center nothing asked for.

## What c15t does not control

### The system sheet is Apple's

The words inside Apple's dialog come from `NSUserTrackingUsageDescription` and, on the
expanded sheet, `NSUserTrackingMarkdownUsageDescription`. Both are compiled into the app
binary. c15t cannot change that copy at runtime, cannot translate it beyond the localized
string tables the Expo plugin writes, and cannot decide when the sheet appears or what
buttons it carries. What c15t does control is the in-app preference center: its copy, its
styling, and its components, all plain text and styles you write.

### Apple decides who sees the expanded prompt

Apple gates the expanded presentation on rules this process cannot read, including the
device's country and the country of the signed-in Apple Account. Outside those rules Apple
shows the plain alert even when the SDK made the expanded call. The reverse happens too:
Apple documents that in France, Germany, Italy, Poland and Romania only the expanded
interface is available whatever the app asks for, so a standard call can raise the
expanded sheet there. Either way `presentation` records which call this SDK made on a
runtime that had it. It is not proof of EU eligibility, and it is not evidence that the
subject saw the expanded sheet. c15t's
geolocation and the `country` and `region` overrides are never evidence of eligibility
either: they choose which consent policy matches, which is a separate question with a
separate answer.

### Allow is not consent

Pressing Allow in Apple's sheet writes no consent record and does not imply `acceptAll()`.
The two answers meet only in `isTrackingPermitted`, and neither one supplies the other's
half. App Tracking Transparency is not a lawful basis: an app that owes GDPR or TCF
obligations still owes them with ATT authorized, and the records that discharge them come
from the c15t surfaces.

### None of this is a privacy declaration

Nothing here implies tracking domains or any other privacy declaration. This feature does
not touch `NSPrivacyTracking` or `NSPrivacyTrackingDomains`, and no parameter added for it
writes either. Whether your app links data across apps or contexts is a fact about your
app, and [configuration](/docs/frameworks/react-native/configuration) leaves that decision
where it was.

## Offline writes

Every write is persisted before the request, not after, and replayed on the next launch,
on foreground, and on a reachability change. The pending queue keeps at most the newest
twenty payloads, oldest dropped first, and replays each one unchanged: a later init that
changes the policy must not rewrite a queued payload.

`commit()` therefore resolves `queued: true` and the snapshot is already correct offline.
Check `queued` before describing a resolved promise as a delivered write. Consent
applies locally either way, which is the correct privacy behavior: a subject's rejection
takes effect on the device immediately, whether or not the receipt has reached a server.

Nothing in the core wakes itself on a timer, so the two wake-ups after launch belong to the
native layer, which arms them once a core is in place. Android skips its reachability leg
and logs once when the host app never declared `ACCESS_NETWORK_STATE`; iOS has no such
branch because `NWPathMonitor` needs no entitlement. To drive the queue and the policy
refresh yourself instead, pass `observeForeground: false` to Android's `C15tAndroid.install`
or call `C15tReactNativeBootstrap.shutdown()` on iOS.

## Cost

The contract's budgets, measured on the reference device profile:

- `bootstrap()` to the first synchronous `snapshot()`: under 5 ms warm, under 15 ms cold.
- Hydrate from a stored envelope: under 3 ms for a realistic payload.
- Consent action to native commit acknowledged: under 50 ms without network.
- Cold-start overhead attributable to c15t: under 10 ms.
- React rerenders per consent change: at most one per subscribed component.

The cores publish their own measurements through their bench tasks, in microseconds, for
hydrate, policy evaluation, snapshot reads, and an acknowledged save. Treat those as the
numbers to compare against, and reproduce them with the commands in the repository rather
than quoting them as device-independent.

## Turning the automatic start off

Set `com.c15t.reactnative.AutoBootstrap` to `false` on iOS, or
`com.c15t.reactnative.AUTO_BOOTSTRAP` to `false` on Android, when your app installs its
own core. The bridge then keeps answering reads deny-all until you install it, and works
against whatever core is there afterwards.

Call it before the first JavaScript frame or you get a real gap: on iOS hand your own
core to `C15tReactNativeBootstrap.install(_:)`, or have the bridge build and start one
from the `Info.plist` with `C15tReactNativeBootstrap.start()`, which takes an explicit
`C15tBridgeConfiguration` when you would rather pass one than rely on the plist.
`C15tReactNativeBootstrap.isRunning` tells you whether a core is in place. On Android,
`C15t.bootstrap` ignores a second call, so an initializer that wins the race is harmless.

`com.c15t.storage` of `memory`, and the equivalent in-memory store you can install
yourself, means nothing survives relaunch. That is a preview and test configuration, not
a production one.
