## Before you start

This guide is for a Svelte 5 app without SvelteKit, such as a Vite
single-page app. The browser resolves consent after the page loads, so the
banner appears after the first paint. For a banner in the server HTML, use
SvelteKit; [choose your setup](/docs/concepts/choose-your-setup) compares the
options. The `examples/svelte` app in the c15t repository is the finished
result.

The guide uses [Inth](https://inth.com) for policies and consent records.
Create an Inth project, then:

1. Set its policy rules, including the `measurement` category for the
   vendor below.
2. Add your app's origin, such as `http://localhost:5173`, to its trusted
   origins.
3. Copy the project's backend URL.

A self-hosted backend or offline mode works too; see
[other setups](#other-setups).

Build-time manifests are the recommended production setup. Complete the
[build-time manifest step](#bundle-the-manifest-during-vite-builds) before
deploying, and rebuild after changing policies, translations or vendors.

## Install

<CommandTabs command="@c15t/svelte@alpha @c15t/integrations@alpha" mode="install" />

Svelte uses its own package, `@c15t/svelte`. The `c15t` package has no Svelte
entry point. `@c15t/integrations` holds the vendor helpers.

## Mount the provider

Render `ConsentManagerProvider` around your app in `src/App.svelte`:

<include src="../../shared/examples/svelte/app.mdx" />

Replace `https://your-project.inth.app` with your project's backend URL,
including any path prefix. The `<main>` element stands in for your app's
content. `hosted()` points the provider
at your Inth project for both the policy and saved choices. The provider
starts consent when it mounts and stops it when it unmounts, so keep it at the
root of the app.

`ConsentBanner` shows the banner when the visitor's policy asks for one.
`ConsentDialog` is the preference dialog; it loads in its own chunk after the
page, before anyone opens it. `ConsentDialogLink` is the persistent way back to
preferences. Put it where visitors look for privacy settings, such as the
footer.

`@c15t/svelte/styles.css` holds the stock styles for all three. Import it
once.

## Bundle the manifest during Vite builds

Add `consentManifest` to your existing Vite plugins:

{/* example: fragment */}

```ts title="vite.config.ts (plugins option)"
import { consentManifest } from '@c15t/svelte/vite';

export default {
	plugins: [
		// Keep your existing framework plugins here.
		consentManifest({ backendURL: 'https://your-project.inth.app' }),
	],
};
```

Vite writes `src/c15t-manifest.ts` before compilation or development startup.
Keep it out of Git. Install `@c15t/browser@alpha` for its browser manifest
transport. In the provider's script block, replace the `hosted()` factory:

{/* example: fragment */}

```ts title="src/App.svelte script block"
import { manifest } from '@c15t/browser/headless';

import { consentManifest } from './c15t-manifest';

const mode = manifest({
	backendURL: 'https://your-project.inth.app',
	manifest: consentManifest,
});
```

Pass `mode` to `ConsentManagerProvider` and keep the other provider options.
The browser resolves the snapshot without a manifest request when it has the
geography the policy needs, or the policy does not depend on geography.
Supply known country and region through `inputs` or overrides to keep regional
resolution on the snapshot. When required geography is missing, it calls
backend `/init` and uses its resolved policy and translations. Those visitors
still wait for a backend round trip and can receive newer policy than the
build snapshot.

Policy and resolver code are part of the browser bundle. Rebuild after policy,
translation or vendor changes to update local resolutions. A failed or invalid
snapshot fetch stops the build; consent saves and IAB vendor-list requests
can still use the network.

<include src="../../shared/vite-build-manifest.mdx" />

For policy updates without a rebuild, omit the build plugin and keep the
original `hosted()` factory to resolve consent through the backend's `/init`.

## Verify consent

Build and preview the production bundle with `vite build` and `vite preview`,
then open the app in a private window with DevTools open on the Network tab:

1. The banner appears. No requests go to PostHog yet.
2. Select **Reject All**. Reload. The banner stays closed and PostHog requests
   stay absent.
3. Select **Privacy settings**, turn on **Analytics** (the `measurement`
   category) and save. PostHog loads.
4. Turn it off and save. The page reloads and PostHog does not load.

If the banner does not appear, see [troubleshooting](/docs/frameworks/svelte/troubleshooting).
[Verify consent](/docs/guides/verify-consent) has the release checklist.

## Other setups

**Offline mode** resolves policies in the browser and keeps choices in the
browser's cookie and local storage, with no backend and no consent records. Use it for local development
and tests. Not recommended for production environments.

{/* example: fragment */}

```ts
import { offline } from '@c15t/svelte';

const mode = offline();
```

With no arguments, `offline()` uses the recommended rules. They ask for
opt-in in Europe and unknown locations, use opt-out in US privacy states, and
show no banner where no consent law applies. Pass `offline({ policyRules })` to use your own.
[Data fetching](/docs/concepts/data-fetching#when-should-i-use-offline-mode)
explains the trade-offs.

**A self-hosted backend** uses the same `hosted({ url })` call with your own
URL. See [self-hosting](/docs/self-host/overview).

**Astro** can render these Svelte components as islands. Its integration uses
Svelte for the dialog by default. Pick the Astro row in
[choose your setup](/docs/concepts/choose-your-setup).
