---
title: Svelte quickstart
description: Add consent prompts and persistent privacy preferences to a Svelte 5 application.
---

```svelte
<script lang="ts">
  import {
    ConsentManagerProvider,
    ConsentBanner,
    ConsentDialog,
    ConsentDialogLink,
    hosted,
  } from '@c15t/svelte';
  import '@c15t/svelte/styles.css';
</script>

<ConsentManagerProvider options={{ mode: hosted({ url: '/api/c15t' }) }}>
  <ConsentBanner />
  <ConsentDialog />
  <ConsentDialogLink>Privacy settings</ConsentDialogLink>
</ConsentManagerProvider>
```

The active policy determines whether the banner requests a choice, displays a notice,
or stays hidden. A notice has a dedicated dismiss action. Dismissing it does not
record category choices. Keep the privacy link available so visitors can change
preferences before choosing and after closing the banner.

## Resolve rules locally

Use `offline({ policyRules })` when your application owns the rules and does not send
consent records to a backend.

```svelte
<script lang="ts">
  import { ConsentManagerProvider, ConsentBanner, offline } from '@c15t/svelte';

  const mode = offline({
    policyRules: [{
      id: 'site-default',
      match: { fallback: true },
      model: 'opt-in',
      prompt: 'choice',
      categories: ['marketing', 'measurement'],
    }],
  });
</script>

<ConsentManagerProvider options={{ mode }}>
  <ConsentBanner />
</ConsentManagerProvider>
```

Choose rules for your actual processing and jurisdictions. The adapter renders and
enforces the supplied rules; this example does not establish legal compliance.

## Read reactive state

Call `getConsentManager()` inside a child component of the provider. Read its getters
in markup or a Svelte derived expression rather than destructuring a snapshot once.

```svelte
<script lang="ts">
  import { getConsentManager } from '@c15t/svelte';

  const consent = getConsentManager();
  const marketingAllowed = $derived(consent.effectivePermissions.marketing);
</script>

<p>Marketing permission: {marketingAllowed ? 'allowed' : 'blocked'}</p>
```

`explicitChoice` contains original per-category receipts. `effectivePermissions`
contains the permissions after policy scope, expiration and privacy restrictions.
`promptRequirement` explains the interaction currently required. `noticeDismissal`,
`privacySignals`, `optOutDirectives`, `resolution`, `policyRule` and `restrictions`
remain separate fields. An existing receipt alone does not suppress a required prompt.

Preferences stay open while a save is pending or fails. A failed transport does
not revoke the local choice already recorded by that action. The draft remains
available for retry; a later save completion does not close a newly opened dialog
or hide a required notice.
