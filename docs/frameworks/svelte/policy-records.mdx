title: Svelte policy records and server rendering
description: Preserve receipt timestamps and policy decisions across SvelteKit server rendering and hydration.

## Prepare the request on the server

```ts
// src/routes/+layout.server.ts
import { prefetchInitialConsent } from '@c15t/svelte/server';

export async function load({ request, fetch }) {
  const prefetch = await prefetchInitialConsent({
    headers: request.headers,
    backendURL: 'https://consent.example.com',
    fetch,
    now: Date.now(),
  });
  return { prefetch };
}
```

```svelte
<!-- src/routes/+layout.svelte -->
<script lang="ts">
  import {
    ConsentManagerProvider,
    ConsentBanner,
    ConsentDialog,
    ConsentDialogLink,
    hosted,
  } from '@c15t/svelte';
  import '@c15t/svelte/styles.css';

  let { data, children } = $props();
</script>

<ConsentManagerProvider options={{
  mode: hosted({ url: 'https://consent.example.com' }),
  prefetch: data.prefetch,
}}>
  {@render children()}
  <ConsentBanner />
  <ConsentDialog />
  <ConsentDialogLink>Privacy settings</ConsentDialogLink>
</ConsentManagerProvider>
```

The server helper reads the raw choice, notice and standing privacy cookies through
the shared storage reader. It preserves their original timestamps and passes one
request clock to the client. A complete prepared policy renders immediately and
starts the kernel lifecycle after hydration without another initialization request.
Hydration does not write or renew a receipt. Pending initialization stays hidden
until the policy resolves.

For custom server policy resolution, use `readInitialConsentConfig({ headers, now })`
and combine its result with `initialPolicyResolution` from the shared policy resolver.
Pass the resulting object as `prefetch`. Do not convert cookies into a consent boolean
or a fresh set of grants. The server cannot read older localStorage-only notice
records; those visitors may see the notice again.

## Presentation and preferences

```ts
const presentation = {
  prompt: {
    direction: 'column' as const,
    primaryActions: ['accept', 'reject'] as const,
  },
  preferences: {
    defaults: { marketing: false },
  },
};
```

Pass this object as `options.presentation`. The banner and headless API use the same
pure `resolveConsentPresentation` function. Required actions omitted by a layout are
restored, and forbidden actions are removed. Accept and reject have equal default
prominence. Development diagnostics report host settings that give equivalent
actions different prominence. Notice prompts never trap focus or lock scrolling.

Preferences use unmasked explicit choices before host and policy defaults. A stored
marketing grant can remain selected while GPC blocks its effective permission.
Saving confirms only displayed optional categories. Necessary is always enabled.
If the policy changes materially while a draft is dirty, save is disabled until the
visitor uses **Review preferences**. Headless hosts can inspect `consent.draft.isStale`
and call `consent.draft.reset()` before another save.

## Observe actual events

```ts
const callbacks = {
  onChoiceRecorded({ confirmed, actionAt, snapshot }) {
    console.log('Confirmed categories', confirmed, actionAt, snapshot.explicitChoice);
  },
  onPermissionsChanged({ previous, snapshot }) {
    console.log('Permission change', previous, snapshot.effectivePermissions);
  },
};
```

Pass callbacks through `options.callbacks`. Each callback receives the matching
kernel event payload without its `type` field. Registering a callback, hydrating
storage, or dismissing a notice does not create a choice callback. Permission changes
can occur without a new choice, including expiration and privacy restrictions.

## Migrate older integrations

Replace `hasConsented` and synthetic consent records with the separate state fields.
Replace provider `policies` and `offlinePolicy` with `offline({ policyRules })`, and
move visual policy settings to `presentation`. Replace `onConsentSet` and
`onConsentChanged` with `onChoiceRecorded` and `onPermissionsChanged`. Replace
`showWhen="after-consent"` with persistent access, using the default `always` or
explicitly disabling a redundant trigger with `never`.
