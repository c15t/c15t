## Before you start

This guide sets up a server-rendered SvelteKit app. The root layout's server
`load` resolves each visitor's consent before the page renders, so the banner
is part of the first HTML and a returning visitor's choice applies from the
first paint. For prerendered pages, a static site or SPA mode, follow this
guide and then [rendering and deployment](/docs/frameworks/sveltekit/rendering).
The `examples/sveltekit` app in the c15t repository is the finished result.

`@c15t/svelte` supports SvelteKit 2 and 3 with Svelte 5. The examples use
SvelteKit 3. On SvelteKit 2, import `building` and `dev` from
`$app/environment` instead of `$app/env`, and write `#lib/` imports as `$lib/`
without the `.js` extension. SvelteKit 2 has no `src/env.ts`: import `env` from
`$env/dynamic/public` and read `env.PUBLIC_C15T_BACKEND_URL`. Its adapter
stays in `svelte.config.js`.

The guide uses [Inth](https://inth.com) for policies and consent records.
Create an Inth project, then:

1. Set its policy rules, including the `measurement` category for the
   vendor below.
2. Add your app's origin, such as `http://localhost:5173`, to its trusted
   origins.
3. Copy the project's backend URL. The build downloads the policy from it and
   the browser saves choices to it.

A self-hosted backend works the same way with your own URL; see
[self-hosting](/docs/self-host/overview).

The setup bundles your policy into the server at build time, the recommended
production setup. Rebuild after changing policies, translations or vendors.

## Bundle the policy at build time

Add `consentManifest` and `c15tPreload` to the plugins in `vite.config.ts`:

<include src="../../shared/examples/sveltekit/vite-config.mdx" />

`consentManifest` downloads your project's public policy from
`<backendURL>/manifest` when Vite starts, for `vite build` and `vite dev`. On
SvelteKit 3, `svelte-kit sync` runs it too. It writes the policy to
`src/lib/server/c15t-manifest.ts`, which the server bundle imports. Keep that
file out of Git. `vite.config.ts` runs before the app exists, so it reads
`PUBLIC_C15T_BACKEND_URL` with Vite's `loadEnv` instead of `$app/env/public`.
Keep its fallback the same as the one in `src/env.ts`.

`c15tPreload` lets `c15tHandle`, added below, preload the script loader on
pages that register scripts.

Declare the consent options once, in `src/lib/server/c15t.ts`. Modules under
`src/lib/server` never reach the browser:

<include src="../../shared/build-time-manifest-notes.mdx" />

The policy comes from the backend URL at build time. Changing
`PUBLIC_C15T_BACKEND_URL` on a built app moves consent saves and visit
reports, not the policy, so rebuild after you change it.

see [serve the manifest route](/docs/frameworks/sveltekit/rendering#serve-the-manifest-route).

## Resolve consent in the root layout load

<include src="../../shared/examples/sveltekit/layout-server.mdx" />

`loadConsent` reads the visitor's consent cookie, location headers and Global
Privacy Control, resolves their policy from the bundled snapshot, and returns
a plain, serializable object for the provider's `prefetch` prop. Rendering a
page makes no policy request to the backend. `loadConsent` never throws. If
resolution takes longer than `timeoutMs`, 500 ms by default, it returns the
stored choice without a policy, and the browser resolves the policy after
hydration.

While SvelteKit prerenders pages at build time, `building` is `true`, so
`shared: building` makes the load return no visitor's consent and no policy.
A prerendered page goes to every visitor, so it must not contain one
visitor's consent. The browser resolves consent on those pages through the
route below. [Rendering and deployment](/docs/frameworks/sveltekit/rendering#prerender-some-pages)
has the details.

## Add the consent route

Create `src/routes/api/c15t/[...path]/+server.ts` with the same options:

<include src="../../shared/examples/sveltekit/consent-route.mdx" />

`GET /api/c15t` resolves a visitor from the bundled policy, the same way the
layout load does. The browser calls it whenever it resolves consent itself,
such as on a prerendered page. The route exports only `GET`; choices are saved
to the backend directly.

## Render the provider in the root layout

<include src="../../shared/examples/sveltekit/layout.mdx" />

Pass `data.prefetch` through unchanged. The provider starts from it, so the
server and the browser render the same banner and the browser makes no second
request for the policy. `hosted()` saves choices to the backend URL, and
`initURL` sends the browser's own policy requests to `/api/c15t`. A policy
resolved from a manifest has no signed snapshot token, so
`assertDecisionInputs: true` sends the decision it was made against with each
save instead.

`ConsentBanner` shows the banner when the policy asks for one.
`ConsentDialog` is the preference dialog; it loads in its own chunk after the
page, before anyone opens it. `ConsentDialogLink` is the persistent way back to
preferences. Put it where visitors look for privacy settings, such as the
footer. `@c15t/svelte/styles.css` holds the stock styles for all three.

Keep the provider in the root layout so it stays mounted across client-side
navigation.

## Verify consent

Build the app with `vite build` and serve the production build with
`vite preview`, then open it in a private window with DevTools open:

1. View the page source. It contains `data-testid="consent-banner-root"`, so
   the banner is in the server HTML.
2. In the Network panel, no requests go to PostHog.
3. Select **Reject All** and reload. The page source no longer contains the
   banner, and PostHog requests stay absent.
4. Select **Privacy settings**, turn on **Analytics** (the `measurement`
   category) and save. PostHog loads.
5. Turn it off and save. The page reloads and PostHog does not load.
6. Navigate to another route and back. The choice holds without a new banner.

If the build fails or the banner is missing from the page source, see
[troubleshooting](/docs/frameworks/sveltekit/troubleshooting).
[Verify consent](/docs/guides/verify-consent) has the release checklist.
