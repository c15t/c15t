## Pick a rendering path

| Your app | Where consent resolves | Setup |
| --- | --- | --- |
| Server-rendered pages, recommended | Root layout load resolves from a build-time manifest | [Quickstart](/docs/frameworks/sveltekit/quickstart) |
| Policy changes must apply without a rebuild | Root layout load resolves from a runtime manifest cache | [Serve the manifest route](#serve-the-manifest-route) |
| Backend resolves every visit | Root layout load calls the backend's `/init` | Remove the plugin, the snapshot and the route, as in [bundle the manifest during builds](#bundle-the-manifest-during-builds) |
| A server app with some prerendered pages | Server for most pages, the browser on prerendered ones | [Prerender some pages](#prerender-some-pages) |
| A fully static site with `adapter-static` | The browser | [Build a static site](#build-a-static-site) |
| SPA mode, `ssr = false` | The browser | [Use SPA mode](#use-spa-mode) |

Each path uses the same provider and components. Only the root layout's
server load changes. The quickstart's code is the `examples/sveltekit` app in
the c15t repository. A static site and SPA mode resolve consent in the browser
the same way a prerendered page does.
[Data fetching](/docs/concepts/data-fetching) compares `/init`, the manifest
and browser resolution in general.

## Serve the manifest route

Use runtime manifest fetching when policy updates must apply without a
rebuild. Your server downloads the project's public policy manifest, caches
it, and resolves each visitor locally. Consent saves still go to the backend,
directly or through the
[consent proxy](#save-consent-through-your-own-origin).

Starting from the quickstart, remove the `consentManifest` plugin from
`vite.config.ts`, and the `c15t-manifest` import and the `manifest` line from
`src/lib/server/c15t.ts`. The quickstart's `/api/c15t` route then fetches the
manifest from `backendURL` at runtime. Without the quickstart's options file,
add a catch-all route at `src/routes/api/c15t/[...path]/+server.ts`:

<include src="../../shared/examples/sveltekit/route-handlers.mdx" />

`createSvelteKitConsentRouteHandlers` returns `GET`, which serves two paths:

| Request | Response |
| --- | --- |
| `GET /api/c15t` | The visitor's resolved policy, like the backend's `/init`. `Cache-Control: private, no-store`. |
| `GET /api/c15t/manifest` | The manifest, with the backend's `Cache-Control` and `ETag`. Answers `If-None-Match` with `304`. |

It also returns `init` and `manifest` handlers separately, if you prefer one
file per route. Point the root layout load at the route with `initRoute`:

<include src="../../shared/examples/sveltekit/manifest-layout-server.mdx" />

`loadConsent` calls the route through `event.fetch`, inside the same process,
with the visitor's location, language and GPC. Keep the root
`+layout.svelte` from the quickstart unchanged: the browser's `initURL` still
points at the route, and its saves still go to the backend URL.

This route file exports `GET` only, so a `POST` or `PATCH` to `/api/c15t`
gets a `405`. Keep `hosted({ url })` on the backend URL, as the quickstart
layout does, or turn on the proxy described in
[save consent through your own origin](#save-consent-through-your-own-origin).

Pass the absolute Inth URL as `backendURL`. A relative URL, such as
`/api/self-host` for a backend mounted in your app, is fetched with
`event.fetch` inside the app and is never resolved against the request's
`Host` header. One that points back at `/api/c15t` makes the route fetch
itself.

The route caches the manifest in memory for as long as its `s-maxage` allows.
After that, within the backend's `stale-while-revalidate` window, it serves
the stale copy while it refreshes in the background. Past that window, the
next request waits for a fresh copy. It also reports
each resolved visit to the backend so Inth still counts visitors it never
served `/init` to; pass `reportSessions: false` to turn that off.

### Save consent through your own origin

To keep every consent request on your site's origin, pass `proxy: true` and
export the write handlers from the same catch-all route:

{/* example: fragment */}

```ts title="src/routes/api/c15t/[...path]/+server.ts"
export const { GET, POST, PATCH, PUT, DELETE, OPTIONS } =
	createSvelteKitConsentRouteHandlers({
		backendURL: 'https://your-project.inth.app',
		proxy: true,
	});
```

Then point the provider at the route with `hosted({ url: '/api/c15t' })`.
With the proxy on, `GET` still resolves `init` and `manifest` in the process,
and the handlers forward other requests to `backendURL`. They forward only
`subjects`, `subjects/:id`, `init`, `manifest`, `health`, `status` and any
extra paths you list in `proxy: { paths }`, and answer anything else with
`404`. Cookies go upstream only when `proxy: { cookieNames }` names them. The visitor's address comes from
`event.getClientAddress()`, and `x-forwarded-host` and `x-forwarded-proto`
come from `event.url`, so configure your adapter's address header if it runs
behind a proxy. The proxy forwards to `backendURL`, never to a `manifestURL`.
An absolute URL is fetched over the network. A relative one, such as a route
elsewhere in your app, is fetched with `event.fetch` inside the app and is
never resolved against the request's `Host` header.

### Keep background work alive after the response

The handlers use only `fetch`, so they run on Node and edge adapters alike.
Some runtimes stop work once a response is sent, which would cut off the
background manifest refresh and the visit report. When the adapter exposes
`event.platform.context.waitUntil`, the handlers register that work there
automatically. Netlify does, as do Cloudflare and Vercel edge on SvelteKit 2.

SvelteKit 3's Cloudflare adapter no longer puts `waitUntil` on
`event.platform`, and its Vercel adapter has no edge runtime. On those, pass
the platform's own `waitUntil` as `onBackgroundRevalidate`:

{/* example: fragment */}

```ts title="src/routes/api/c15t/[...path]/+server.ts (partial)"
import { waitUntil } from 'cloudflare:workers'; // Vercel: '@vercel/functions'

export const { GET } = createSvelteKitConsentRouteHandlers({
	backendURL: 'https://your-project.inth.app',
	onBackgroundRevalidate: (promise) => waitUntil(promise),
});
```

Without it, those runtimes can cut the refresh and the visit report short.
Requests keep getting the cached manifest, but it can stay stale for longer,
and the backend misses those visits.

When passing a snapshot directly to `loadConsent`, add the same optional
`onBackgroundRevalidate: (promise) => waitUntil(promise)` callback to that
call. It keeps the session report alive after the response. `loadConsent`
uses `event.platform.context.waitUntil` when available and this callback
otherwise. The framework-free `resolveConsent` helper also accepts
`onBackgroundRevalidate`; it has no event from which to find a platform hook.

## Resolve request context once with c15tHandle

The quickstart installs `c15tHandle` in `src/hooks.server.ts`, which reads
the consent cookie and headers once per request for every load and endpoint.
Without it, each `loadConsent` call reads them itself:

<include src="../../shared/examples/sveltekit/hooks.mdx" />

It stores the result on `event.locals.c15t`, which `loadConsent` reuses, and
rewrites the location headers into one normalized form. Compose it with your
own handles through `sequence(c15tHandle(), yourHandle)` from
`@sveltejs/kit/hooks`. Pass `country`, `region` or `language` to force them,
and `cookieName` if you changed `storageConfig.storageKey`.

`c15tHandle` also writes a server-rendered banner's rules into the HTML
`<head>` as `<style>` elements, so the banner is styled before hydration.
Without it, a server-rendered banner shows unstyled until the page hydrates,
unless the provider sets `styles={false}` and the app imports
`@c15t/svelte/styles.css`.

Type `event.locals.c15t` in `src/app.d.ts`:

<include src="../../shared/examples/sveltekit/app-locals.mdx" />

If you have no `App.Locals` block of your own, add
`/// <reference types="@c15t/svelte/kit/locals" />` to `src/app.d.ts` instead.

Options passed to one `loadConsent` call, such as `country`, override the
handle's values for that call.

## Prerender some pages

A prerendered page is built once and sent to every visitor, so it cannot
contain one visitor's consent. SvelteKit runs the root layout load while it
builds those pages, and `building` from `$app/env` (`$app/environment` on
SvelteKit 2) is `true` then.
The quickstart's load passes `shared: building`, so it returns no visitor's
consent and no policy in that case. Prerendering a page needs only the page
option:

<include src="../../shared/examples/sveltekit/prerender.mdx" />

On a prerendered page the HTML has no banner. After hydration the browser asks
the quickstart's `/api/c15t` route for the policy, which the route resolves
from the bundled snapshot, then shows the banner or applies the stored choice.
Optional categories stay denied until then. Server-rendered pages in the same
app keep the banner in their HTML.

## Build a static site

With `adapter-static`, every page is prerendered and no server runs after the
build. Set the option in the root layout:

{/* example: fragment */}

```ts title="src/routes/+layout.ts"
export const prerender = true;
```

The browser resolves consent on every page. Server routes such as
`/api/c15t` do not exist after a static build, so it has to ask the backend
directly. Starting from the quickstart:

1. Delete `+layout.server.ts`, `src/lib/server/c15t.ts` and the `/api/c15t`
   route.
2. Remove the `consentManifest` plugin from `vite.config.ts`.
3. Remove `initURL` and `assertDecisionInputs` from `hosted()` in
   `+layout.svelte`. The browser then calls the backend's `/init`.

On a static host, the backend URL must be the absolute Inth URL.

## Use SPA mode

With `export const ssr = false` in the root `+layout.ts`, SvelteKit renders
every page in the browser. The provider and components from the quickstart
work unchanged; there is no server HTML, so the banner appears after the
browser resolves the policy.

With a static SPA fallback page and no server, make the changes in
[build a static site](#build-a-static-site). `data.prefetch` is then
`undefined`, and the provider resolves consent in the browser through the
backend's `/init`.

## Resolve consent in other server code

`resolveConsent` from `@c15t/svelte/server` does what `loadConsent` does
without a SvelteKit event, for endpoints or code outside a load:

{/* example: fragment */}

```ts
import { resolveConsent } from '@c15t/svelte/server';

const state = await resolveConsent({
	backendURL: 'https://your-project.inth.app',
	headers: request.headers,
});
```

It never throws. When the backend fails or takes longer than `timeoutMs`,
500 ms by default, it returns the stored choice without a policy. Pass
`manifest` to resolve from the build-time snapshot instead. In a load, use
`loadConsent`, which reads the request from the event.
Import `@c15t/svelte/kit` and `@c15t/svelte/server` only from server files
such as `+layout.server.ts`, `+server.ts` and `hooks.server.ts`; imported into
a component they add server code to the browser bundle.
