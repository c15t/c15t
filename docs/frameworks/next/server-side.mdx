The Next.js adapter returns plain, serializable kernel configuration from its
server helpers. Pass that configuration to `ConsentBoundary`; never share a
kernel instance between requests.

## Read Request State

`readInitialConsentConfig()` reads the consent cookie and request headers. It
does not call the backend.

```tsx title="app/layout.tsx"
import { ConsentBoundary } from 'c15t/next';
import { readInitialConsentConfig } from 'c15t/next/server';

export default async function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const config = await readInitialConsentConfig();

  return (
    <html lang="en">
      <body>
        <ConsentBoundary backendURL="/api/c15t" config={config}>
          {children}
        </ConsentBoundary>
      </body>
    </html>
  );
}
```

The client boundary initializes the hosted transport after hydration. Returning
visitors are hydrated from the persisted cookie, so the first client snapshot
matches the server render.

## Prefetch the Policy

Use `prefetchInitialConsent()` when the first HTML response should include the
resolved policy, translations, and UI state. It calls the backend `/init`
endpoint and degrades to request-only configuration if that call fails.

```tsx
import { ConsentBoundary } from 'c15t/next';
import { prefetchInitialConsent } from 'c15t/next/server';

export default async function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  const config = await prefetchInitialConsent({
    backendURL: 'https://your-instance.c15t.dev',
  });

  return (
    <ConsentBoundary
      backendURL="https://your-instance.c15t.dev"
      config={config}
    >
      {children}
    </ConsentBoundary>
  );
}
```

Both helpers use `next/headers`, so calling either opts the route into dynamic
rendering. For a static route, use `C15tPrefetch` to warm the browser request
instead.
