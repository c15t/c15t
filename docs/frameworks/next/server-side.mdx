## Use the helper for your router

| Router | Server helper import | Request context |
| --- | --- | --- |
| App Router | `c15t/next/server` | Next.js request cookies and headers |
| Pages Router | `c15t/next/pages` | `req` passed from `getServerSideProps` |
| Static export | No request helper | Browser initialization |

Follow [App Router](/docs/frameworks/next/app-router),
[Pages Router](/docs/frameworks/next/pages-router) or
[static export](/docs/frameworks/next/static-export) for complete files.

## Preserve the server result

With the recommended `manifestURL` config, `prefetchInitialConsent` resolves
policy locally from the cached manifest and restores records for a request. With
only `backendURL`, it fetches `${backendURL}/init`; a rewrite or local handler
determines what serves that URL. Forward
its result to `ConsentBoundary` without deriving new saved choices from allowed
categories. Keep server and browser backend configuration consistent.

Awaiting the helper allows resolved consent UI in the server HTML. Passing a
pending promise lets the rest of the page render while the prompt waits. Neither
path should emit a choice event just because hydration completed.

## Cache policy data without sharing visitor state

A manifest is cacheable policy configuration. Resolved init data and stored
records belong to a visitor. Do not put personalized responses or HTML into a
shared cache without an appropriate isolation design. Test request behavior
under more than one visitor and location.

The [data-fetching guide](/docs/frameworks/next/data-fetching) explains the
manifest/init routes, default cache interval, required location headers and
client retry behavior. Use the same `consentConfig` for prefetch and the
boundary so server and browser choose the same policy source.
