## Start with ConsentBoundary in Next.js

Use `ConsentBoundary` for the recommended
[manifest setup](/docs/frameworks/next/data-fetching). It wraps `ConsentProvider`
and selects the transport from `consentConfig` in `c15t.config.ts`.

| Boundary prop | Purpose |
| --- | --- |
| `config` | The prepared visitor state returned by `prefetchInitialConsent`, or `{}` for browser initialization |
| `consent` | The `defineConsentConfig` value containing `backendURL`, `manifestURL` and `initURL` |
| `scripts` | Top-level consent-managed script configurations |
| `options` | Additional provider options, including an explicit `mode` override |

Follow [App Router](/docs/frameworks/next/app-router) or
[Pages Router](/docs/frameworks/next/pages-router) for full files. Keep the boundary
mounted across navigation and import the stylesheet once at the app root.

Use `ConsentProvider` directly when you need to own the transport configuration.
This client wrapper deliberately uses regular backend `/init`. It is an
alternative to the manifest boundary, not another provider to mount inside it:

```tsx title="components/consent.tsx"
'use client';

import type { ReactNode } from 'react';
import {
  ConsentProvider,
  ConsentBanner,
  ConsentDialog,
  ConsentDialogLink,
  hosted,
} from 'c15t/next';

const backendURL = process.env.NEXT_PUBLIC_C15T_BACKEND_URL;
if (!backendURL) throw new Error('Set NEXT_PUBLIC_C15T_BACKEND_URL');
const mode = hosted({ url: backendURL });

export function Consent({ children }: { children: ReactNode }) {
  return (
    <ConsentProvider options={{ mode }}>
      {children}
      <ConsentBanner />
      <ConsentDialog />
      <ConsentDialogLink>Privacy settings</ConsentDialogLink>
    </ConsentProvider>
  );
}
```

Use the absolute public Inth or self-hosted endpoint. This regular `/init`
variant needs no local manifest/init handlers. An optional
[backend rewrite](/docs/frameworks/next/optimization#keep-browser-consent-requests-on-your-origin)
lets you use `/api/c15t` instead. For local-only records, use
[offline mode](/docs/frameworks/next/api-reference/data-fetching#offline-configuration).

## Provider responsibilities

The provider owns initialization, persistence, configured script loading and
subscriptions. Keep it mounted across client navigation. Its initial mode and
prefetch configuration belong to the runtime's creation, not a per-render
mechanism for switching visitors or backends.

| Option | Purpose |
| --- | --- |
| `mode` | Hosted, offline or custom transport factory |
| `scripts` | Consent-managed script configurations |
| `callbacks` | Choice, permission and error events |
| `theme`, `components` | Theme tokens and component slot attributes |
| `presentation` | Prompt and preferences layout behavior |
| `i18n` | Languages and message overrides |
| `storageConfig` | Browser record storage configuration |
| `enabled` | Set false only when intentionally bypassing consent enforcement |

`enabled: false` grants categories and allows gated loading while suppressing
consent UI. It is not a way to fix failed initialization or hide a banner in
production.

## Observe changes without inventing choices

`onChoiceRecorded` reports explicit accept, reject and save actions.
`onPermissionsChanged` also covers changes caused by policy, expiry or privacy
signals. Hydration and notice dismissal do not become explicit choices.

An externally owned runtime can be passed through `runtime`. Its owner must
start and dispose it. A provider borrowing that runtime must not initialize or
dispose a second copy. See [consent state](/docs/guides/consent-state) and
[deployment modes](/docs/guides/deployment-modes).
