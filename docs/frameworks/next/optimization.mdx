## Reuse cached policy data

The [App Router](/docs/frameworks/next/app-router) and
[Pages Router](/docs/frameworks/next/pages-router) guides use cached manifests
with Inth. A manifest contains public policy configuration that your app server
can reuse across requests. Each visitor's consent is still resolved separately.

A warm cache avoids repeated backend policy resolution. It does not eliminate
all requests. Your app may read its local manifest route, cold caches fetch
upstream data, and consent choices still reach Inth. IAB policies can also need
a Global Vendor List fetch.

Keep the local init route from your router guide so browser initialization can
use the same server resolver. Resolving the manifest in the browser instead
loads resolver code and its translations there, and does not supply your host's
geographic request headers. See the [data fetching guide](/docs/frameworks/next/data-fetching)
if you are still choosing a setup.

## Compare manifests with backend initialization

A warm manifest cache can reduce initialization latency by avoiding an upstream
backend request. The saving depends on backend latency, cache hits and where
consent resolution sits in rendering. It is not a fixed speedup for the whole
page.

| Fetching path | Work during initialization |
| --- | --- |
| Regular backend `/init` | Wait for the backend to resolve consent and return the result. |
| Cold manifest cache | Fetch public policy from the backend, cache it and resolve consent locally. |
| Warm manifest cache | Reuse cached policy and resolve consent locally; local route requests and rendering still take time. |

### A controlled local comparison

On 10 September 2026, the repository's `ssr` and `manifest-ssr` benchmarks ran
from the same fresh production build. Both awaited consent before rendering the
same UI and used the same policy fixture. The local backend added **150 ms of
artificial delay** to both `/init` and uncached `/manifest` requests.

| Path | TTFB, median / p95 | Hydrated banner probe, median / p95 |
| --- | --- | --- |
| Backend `/init`, 10 samples | 157.6 / 160.9 ms | 222.4 / 228.9 ms |
| Warm manifest cache, 10 samples | 7.4 / 15.2 ms | 70.9 / 144.3 ms |

The warm cache avoided roughly the injected backend delay in this test. It made
one upstream manifest request across 11 page loads and no upstream `/init`
requests. Both arms had zero browser init requests and no console or hydration
errors. The banner probe runs after hydration, so its timing is not the first
visible pixel.

The first manifest load took 252.4 ms TTFB and 389.6 ms at the banner probe.
That is one cold observation, including startup work, not a cold-cache median
or percentile. Direct init had two warmup loads; the manifest run separated its
first cold load from the following ten warm loads.

This was a local fixture test on Apple M5 Pro, macOS 26.6.2, Node 24.19.0,
Chromium 149.0.7827.55 and Next.js 16.2.10, using the workspace at `278fd8667`
with no CPU or network throttling. It does not measure Inth latency or establish
a production speedup. It also does not measure the streaming default from the
App Router guide.

The [recorded samples and environment](https://github.com/c15t/c15t/tree/ccfe906682ba06cef7b56a16cc8fd10728df77d3/benchmarks/reports/next-manifest-2026-09-10)
include the separate cold load and returning-visitor results. The table compares
new visitors only.

To reproduce from the repository with built workspace dependencies and the
benchmark's Playwright browser installed, use separate result directories:

```sh
cd benchmarks/nextjs-browser-bench
bun run build
BENCH_OUTPUT_DIR=/tmp/c15t-direct bunx tsx scripts/run-bench.ts --scenario ssr --iterations 10 --warmup 2 --profile none --init-latency-ms 150
BENCH_OUTPUT_DIR=/tmp/c15t-manifest bunx tsx scripts/run-bench.ts --scenario manifest-ssr --iterations 11 --warmup 0 --cold-manifest true --profile none --init-latency-ms 150
```

Local resolver benchmarks measure CPU work in microseconds. They exclude HTTP,
backend work and rendering; do not compare them directly with these browser
measurements or use them to claim an end-to-end speedup.

### Measure your deployment

To compare the two paths in your deployment:

1. Use the same c15t and Next.js versions, policy, visitor inputs and rendering
   path. Compare awaited SSR with awaited SSR, or browser initialization with
   browser initialization.
2. Measure cold manifest fills separately from warm-cache requests. Include cache
   refreshes and use enough independent cold starts to describe their variation.
3. Record TTFB, time until the resolved consent prompt appears, and backend request
   counts. A streaming page can return its first byte before consent is ready;
   faster TTFB alone does not prove an earlier prompt.
4. Keep CPU and network conditions consistent, report median and tail latency,
   and identify any injected backend delay. Check rejection and persistence too.

## Keep browser consent requests on your origin

A Next.js rewrite is an optional optimization. It can avoid a separate browser
DNS lookup and TLS connection to the consent backend when that connection would
otherwise be needed. Manifests and server rendering work without it.

The app server still connects to Inth, and the rewrite adds a proxy hop. Measure
your deployment to check the effect on latency. Vendor scripts, pixels and
iframes keep their own URLs; this rewrite only forwards c15t HTTP requests.
The same setup works with a self-hosted c15t backend.

### Add the backend rewrite

Set `C15T_BACKEND_URL` to the absolute endpoint supplied by your Inth project.
The endpoint is public configuration. Merge this fallback into your existing
Next.js configuration:

```ts title="next.config.ts"
import type { NextConfig } from 'next';

const upstreamURL = process.env.C15T_BACKEND_URL?.replace(/\/$/, '');
if (!upstreamURL) throw new Error('Set C15T_BACKEND_URL to the absolute Inth endpoint');

export default {
  async rewrites() {
    return {
      fallback: [{
        source: '/api/c15t/:path*',
        destination: `${upstreamURL}/:path*`,
      }],
    };
  },
} satisfies NextConfig;
```

Next.js serves the local manifest and init handlers first. Other consent
requests, such as `/api/c15t/subjects`, reach Inth through the rewrite.

### Use the local prefix in browser configuration

In the manifest setup from your router guide, change only `backendURL` to
`'/api/c15t'`. The shared configuration then looks like this:

```ts title="c15t.config.ts"
import { defineConsentConfig } from 'c15t/next';

export const consentConfig = defineConsentConfig({
  backendURL: '/api/c15t',
  manifestURL: '/api/c15t/manifest',
  initURL: '/api/c15t/init',
});
```

The manifest URLs remain explicit in the current API. A configuration with only
`backendURL` uses regular backend `/init` and can also use this rewrite. That
setup must not have a local manifest init handler intercepting `/api/c15t/init`.

Keep using `consentConfig` for prefetch and the boundary. Omit a separate
`ConsentBoundary` `backendURL` prop because it overrides the shared value.

### Keep route handlers pointed upstream

The ready-made App Router handlers read the absolute upstream URL from
`C15T_BACKEND_URL`. Keep these exports from the router guide:

```ts title="app/api/c15t/manifest/route.ts"
export { manifestGET as GET } from 'c15t/next/api';
```

```ts title="app/api/c15t/init/route.ts"
export { GET } from 'c15t/next/api';
```

Pages Router uses `createPagesApiHandlers()` with the same environment
configuration. Export `.manifest` and `.init` from the respective API files as
shown in the [Pages Router guide](/docs/frameworks/next/pages-router).

If you configure handlers with `createNextConsentRouteHandlers({ backendURL })`,
pass the absolute upstream URL. Passing the browser's local `consentConfig`
would make the manifest handler fetch itself. An explicit `C15T_MANIFEST_URL`
must also point upstream.

### Check rewrite precedence

An array-form rewrite or `afterFiles` runs after concrete routes; `fallback`
runs after all application routes. A matching `beforeFiles` rewrite or
middleware/proxy rewrite can intercept the local handlers instead. See
[Next.js rewrite order](https://nextjs.org/docs/app/api-reference/config/next-config-js/rewrites).

Use `/api/c15t/:path*` for the backend prefix. A bare `/api/c15t` source does not
match nested endpoints. If a self-hosted backend catch-all already handles that
prefix, it serves the remaining endpoints instead of the fallback rewrite.
Keep the manifest resolver's upstream URL separate to avoid a request loop.

A full [static export](/docs/frameworks/next/static-export) has no Next.js
rewrites or API handlers. Use a hosting-level proxy or direct public Inth URL.

## Configure manifest cache refresh

`createNextConsentRouteHandlers` uses the Next.js Data Cache plus an in-process
manifest cache. The in-process cache also covers Pages Router runtimes without
the Data Cache. It supports ETag revalidation and respects upstream cache
headers, including responses marked private.

The manifest fetch's Next.js revalidation interval defaults to 300 seconds.
Set `C15T_MANIFEST_REVALIDATE_SECONDS` to change it, or pass
`manifestRevalidateSeconds` to the handler factory. The upstream manifest's
cache policy also controls reuse, so changing the Next.js interval alone does
not override every cache layer. Choose refresh settings that fit how quickly
policy changes need to reach visitors.

The local init handler returns `Cache-Control: private, no-store` because its
result belongs to a specific request. Preserve that header and keep personalized
consent HTML out of shared caches.

## Avoid repeating startup work

Keep one boundary in the App Router root layout or Pages Router `_app.tsx`.
Remounting it during navigation creates another runtime and repeats startup
work. Keep the stylesheet and consent UI in that shared root too.

Choose when to resolve consent according to your page. Use
[server rendering](/docs/frameworks/next/server-side) for resolved initial HTML
or streaming, and [client-side initialization](/docs/frameworks/next/client-side)
when the browser should prepare consent.

Measure cold entry, a warm manifest cache and client navigation separately.
Check server requests as well as the browser Network panel. Confirm that
consent saves reach the backend and policy updates appear after the configured
refresh window. If you add a rewrite, also confirm browser consent requests
use your origin.
