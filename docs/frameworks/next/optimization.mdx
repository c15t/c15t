---
title: Next.js startup performance
description: Prepare policy data once and preserve the provider across navigation.
---

## Prepare dynamic routes

Use `prefetchInitialConsent` from `@c15t/nextjs/server` and await its result before
rendering `ConsentBoundary`. Carry the same records, policy and evaluation time
into hydration. A complete prepared response avoids another browser init request.
See [server-side consent](/docs/frameworks/next/server-side) for the complete example.

The former `fetchInitialData` promise and `ssrData` provider option are removed.
Policy resolution must be known before selecting the consent client boundary.
Keep that boundary mounted across client navigation instead of creating a new
kernel for every page.

## Client rendering and static routes

Use the hosted provider transport for client initialization. Preserve the policy
contract header through a same-origin proxy. Static manifests can avoid repeating
policy production; rebuild them whenever policy behavior changes. Reading request
headers on the server makes the route dynamic.

Prefetching must preserve request geography, detected GPC and canonical records.
Do not substitute a developer override or construct fresh receipts to reuse a
cache entry. Fingerprints are producer diagnostics and never a reason to add a
render-time hash or startup request.

## Verify in the application

Measure init requests, payload bytes, prompt readiness and hydration with the
actual deployment configuration. Compare matching server and browser inputs,
including repeat visits, notice dismissals and standing privacy directives.
Performance work must preserve the same processing and prompt behavior.
