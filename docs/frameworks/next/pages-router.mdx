## Choose how to manage consent

We recommend [Inth](/docs/guides/inth) for managed policy and consent records.
This guide uses cached manifests for policy resolution. Consent submissions
go to your backend. A [rewrite](/docs/frameworks/next/optimization#keep-browser-consent-requests-on-your-origin)
is an optional optimization when you want browser backend traffic on your origin.

| Mode | What you manage |
| --- | --- |
| Inth hosted | Configure policy and allowed app origins; Inth runs the backend and stores submissions. |
| [Self-hosted](/docs/self-host/quickstart) | Run the c15t backend and database. Use the same hosted transport with your backend endpoint. |
| [Offline](/docs/frameworks/next/api-reference/data-fetching#offline-configuration) | Bundle policy rules and keep choices in browser storage. No consent backend requests or backend records. Not recommended for production environments. |

This setup requires a Next.js server for the API routes, including
when individual pages use static generation. For a deployment without that
server, use [static export](/docs/frameworks/next/static-export).

## Choose when consent resolves

| Rendering path | Setup | Initial consent UI |
| --- | --- | --- |
| Server-rendered page | Call `prefetchInitialConsent` in `getServerSideProps` | The server can render the resolved prompt |
| [Browser initialization](/docs/frameworks/next/client-side) | Omit page prefetch; `_app.tsx` passes `config={{}}` | The browser initializes through the configured init URL |

The same app boundary supports both paths. A statically generated page can use
browser initialization as long as the deployment serves the API routes. Do not
use `getStaticProps` to read a visitor's cookies or location.

## Install c15t and configure your backend

[Create an Inth project](/docs/guides/inth), configure its policy rules and allow
your app's origin. Copy its backend endpoint for the upstream configuration.

If you chose self-hosting, complete the
[backend quickstart](/docs/self-host/quickstart) and use its public endpoint in
the steps below. Offline setups do not need an endpoint; use the
[offline example](/docs/frameworks/next/api-reference/data-fetching#offline-configuration).

<CommandTabs command="c15t" mode="install" />

Set `NEXT_PUBLIC_C15T_BACKEND_URL` to the absolute endpoint supplied by Inth or
your self-hosted backend, including any path prefix. This is a public endpoint,
not a secret. Configure the backend to allow your app's origin.

## Share the consent URLs

Create this file at the project root. The current API needs explicit
`manifestURL` and `initURL` to select this manifest setup.

```ts title="c15t.config.ts"
import { defineConsentConfig } from 'c15t/next';

const backendURL = process.env.NEXT_PUBLIC_C15T_BACKEND_URL;
if (!backendURL) throw new Error('Set NEXT_PUBLIC_C15T_BACKEND_URL');

export const consentConfig = defineConsentConfig({
  backendURL,
  manifestURL: '/api/c15t/manifest',
  initURL: '/api/c15t/init',
});
```

## Add the Pages API routes

The Pages Router adapter reads `C15T_BACKEND_URL`, falling back to the
`NEXT_PUBLIC_C15T_BACKEND_URL` configured above. If you set both, use the same
absolute backend endpoint.

```ts title="pages/api/c15t/manifest.ts"
import { createPagesApiHandlers } from 'c15t/next/pages';

export default createPagesApiHandlers().manifest;
```

```ts title="pages/api/c15t/init.ts"
import { createPagesApiHandlers } from 'c15t/next/pages';

export default createPagesApiHandlers().init;
```

The manifest route caches public policy data. The init route resolves it using
the visitor request. Consent submissions go to the absolute `backendURL`.

The following imports assume `pages/` is at the project root. Adjust them if you
use `src/pages/`.

## Keep one boundary in the app

```tsx title="pages/_app.tsx"
import type { AppProps } from 'next/app';
import {
  ConsentBanner,
  ConsentBoundary,
  ConsentDialog,
  ConsentDialogLink,
} from 'c15t/next';
import type { ConsentBoundaryProps } from 'c15t/next';
import { consentConfig } from '../c15t.config';
import 'c15t/next/styles.css';

type ConsentPageProps = {
  consentConfig?: ConsentBoundaryProps['config'];
};

export default function App({ Component, pageProps }: AppProps<ConsentPageProps>) {
  return (
    <ConsentBoundary config={pageProps.consentConfig ?? {}} consent={consentConfig}>
      <Component {...pageProps} />
      <ConsentBanner />
      <ConsentDialog />
      <ConsentDialogLink>Privacy settings</ConsentDialogLink>
    </ConsentBoundary>
  );
}
```

Without page prefetch, the boundary initializes through `/api/c15t/init` in
the browser. That route resolves the cached manifest using the visitor request.
Consent submissions go to `${backendURL}/subjects` on the configured backend.

## Prefetch for a server-rendered page

Use `c15t/next/pages` with the `req` from `getServerSideProps`. The App Router
helper reads a different request context and must not be used here.

```tsx title="pages/index.tsx"
import type { GetServerSideProps } from 'next';
import type { ConsentBoundaryProps } from 'c15t/next';
import { prefetchInitialConsent } from 'c15t/next/pages';
import { consentConfig } from '../c15t.config';

type PageProps = { consentConfig: ConsentBoundaryProps['config'] };

export const getServerSideProps: GetServerSideProps<PageProps> = async ({ req }) => {
  const prepared = await prefetchInitialConsent({ config: consentConfig, req });
  return { props: { consentConfig: prepared } };
};

export default function Home() {
  return <main>Your page</main>;
}
```

Repeat prefetch on pages that need request-specific initial HTML. Do not use
`getStaticProps` to resolve visitor cookies or geography: it runs without the
visitor's request. Keep the shared URL configuration consistent across pages.

## Verify entry and navigation

Load a server-rendered page directly, reject, and reload. Then navigate without
a full reload and reopen preferences. The mounted boundary should retain the
choice. Also test direct entry to a statically generated page; it uses browser
initialization through the local init route.

Confirm the server reads `/manifest` instead of the backend `/init` and choices
reach `${backendURL}/subjects`. See
[Optimization](/docs/frameworks/next/optimization) for caching, or compare
alternatives in [data fetching](/docs/frameworks/next/data-fetching). For a deployment with no Next.js server, use
[static export](/docs/frameworks/next/static-export) and remove local API routes.

## Use regular backend initialization instead

For a complete browser-only setup with hosted records, follow
[client-side initialization](/docs/frameworks/next/client-side). It needs no
local route handlers or server prefetch.

For the smallest hosted configuration, keep only `backendURL` in
`defineConsentConfig`:

```ts title="c15t.config.ts"
import { defineConsentConfig } from 'c15t/next';

const backendURL = process.env.NEXT_PUBLIC_C15T_BACKEND_URL;
if (!backendURL) throw new Error('Set NEXT_PUBLIC_C15T_BACKEND_URL');

export const consentConfig = defineConsentConfig({ backendURL });
```

This is an alternative to the manifest configuration. Remove the unused local
manifest/init route files. The existing prefetch and boundary now initialize
through `${backendURL}/init`; consent saves still use `${backendURL}/subjects`.
A backend-only config does not enable manifest mode automatically.

Compare the choices in [data fetching](/docs/frameworks/next/data-fetching), or
configure cache settings and optional rewrites in
[Optimization](/docs/frameworks/next/optimization).
