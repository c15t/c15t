## Before you start

This guide uses [Inth](https://inth.com) for policies and consent records. Your
Next.js server caches the project's public policy manifest and resolves consent
for each visitor. The browser sends consent choices to Inth.

A [self-hosted backend](/docs/self-host/quickstart) uses the same files with
its own URL. [Offline mode](/docs/frameworks/next/data-fetching-reference#offline-configuration)
keeps policy in your code and choices in the browser, with no consent records.
Not recommended for production environments.

This setup needs a Next.js server. For `output: 'export'`, follow
[static export](/docs/frameworks/next/static-export). For static, ISR or
`'use cache'` pages, Cache Components, or other rendering choices, start at
[rendering and deployment](/docs/frameworks/next/rendering).

Location-based policies need trusted location headers from your host. Without
them, c15t applies your unknown-location rule. See
[Forward geography headers](/docs/frameworks/next/geography-headers) before
you deploy.

## Install c15t and configure your backend

[Create an Inth project](https://inth.com), set its policy rules and add your
site's origin to its trusted origins. Copy the project's backend URL.

<CommandTabs command="c15t@alpha @c15t/integrations@alpha" mode="install" />

Set `NEXT_PUBLIC_C15T_BACKEND_URL` to the backend URL from your Inth project, such
as `https://your-project.inth.app`,
including any path prefix. The URL is public configuration, not a secret.

Add the c15t stylesheet to your global CSS. With Tailwind CSS 4, put it after
the Tailwind import so the c15t component layer follows Tailwind's:

```css title="styles/globals.css"
@import 'tailwindcss';
@import 'c15t/next/styles.css';
```

Without Tailwind, keep only the c15t import. Tailwind CSS 3 uses a separate
stylesheet; see [Customize](/docs/frameworks/next/customize#load-the-stylesheet).
Import the stylesheet from a global CSS file, not from a component. Next.js may
load a component's CSS before Tailwind's and change the layer order.

## Start consent resolution in the root layout

Call `resolveConsent` in the root layout without awaiting it, and pass the
pending result to the `Consent` wrapper:

<include src="../../shared/examples/nextjs/app-router-layout.mdx" />

`resolveConsent` reads the visitor's cookies and location headers and resolves
the policy from the cached manifest. Next.js renders the page without waiting
and sends the result later in the same response. Until the browser applies it
after hydration, the banner and dialog stay hidden, optional categories stay
denied, `ConsentGate` shows its placeholder and gated scripts do not load. The
browser makes no `/init` request.

A new visitor then sees the banner. A returning visitor with a valid stored
choice sees none, and the scripts that choice allows load. A choice that has
expired, was recorded under a different policy, or does not cover every
required category prompts again.

If the manifest request fails or takes longer than `timeoutMs`, 500 ms by
default, `resolveConsent` returns a baseline state without a policy. The page
has already rendered. The browser retries after hydration, and gated scripts
and embeds stay blocked until a policy resolves. Pass `onError` to report
these failures; see [troubleshooting](/docs/frameworks/next/troubleshooting).

The layout calls `next/headers`, so routes under it render per request. With
`cacheComponents: true` the layout stays synchronous, and Next.js keeps the
page in the prerendered static shell. See
[Cache Components](/docs/frameworks/next/rendering#use-cache-components).

## Render the banner in the server HTML

To send the banner with the HTML, await `resolveConsent` in an async Server
Component and mount it inside `Suspense`:

<include src="../../shared/examples/nextjs/app-router-awaited-layout.mdx" />

The server renders the consent subtree after the policy resolves, so the
banner arrives already decided and does not change after hydration. The page
content waits with it. Next.js streams an empty shell first and the page in a
later chunk of the same response. A slow manifest response keeps the page
blank for up to `timeoutMs`. If the request fails, the page renders without a
banner, optional categories stay denied, and the browser resolves the policy
after hydration.

The `Suspense` boundary is required with `cacheComponents: true`. Awaiting
request data in the root layout without it fails the build.
[Stream or await consent](/docs/frameworks/next/rendering#stream-or-await-consent-in-the-app-router)
compares the two layouts.

`c15t/next/styles.css` holds the tokens and the banner, trigger and
`ConsentGate` rules. The dialog's rules load with the dialog's own chunk,
after your global stylesheet, so they join the layer order Tailwind declared.

## Initialize in the browser

For static, ISR or `'use cache'` pages, keep the config and manifest route and
pass an empty state instead:

<include src="../../shared/examples/nextjs/browser-layout.mdx" />

The browser loads the manifest and resolves consent after hydration, so the
HTML is the same for every visitor. Without location from your server, the
policy follows your unknown-location rule. To mix these pages with
server-rendered ones, see
[static, ISR and cached pages](/docs/frameworks/next/rendering#render-static-isr-and-cached-pages).

## Use backend init instead of the manifest

Delete the `manifestURL` line from `c15t.config.ts` and delete
`app/api/c15t/manifest/route.ts`. The layouts stay the same. `resolveConsent`
and the browser now call `${backendURL}/init`, and consent choices still go to
`${backendURL}/subjects`. Every visit makes a backend request, which the
manifest avoids. For a browser-only setup with no server work, follow
[client-side initialization](/docs/frameworks/next/client-side).

A same-origin [rewrite](/docs/frameworks/next/optimization) is optional with
either source. [Optimization](/docs/frameworks/next/optimization) also covers
manifest cache refresh and measured performance.

## Verify the setup

Start the production build with `next build` and `next start`, then open the
site in a fresh browser session with DevTools open.

1. Under an opt-in policy, the banner appears and the Network panel shows no
   PostHog or X Pixel request.
2. Click **Reject all**, then reload. The banner stays closed and neither
   vendor loads.
3. Open **Privacy settings** in the footer and allow measurement only. PostHog
   loads and X Pixel stays blocked.
4. Open **Privacy settings** again and turn measurement off. The page reloads
   and PostHog does not load again.
5. The browser makes no `/init` request, and choices post to
   `${backendURL}/subjects`.

Test a new visitor and two locations. Requests without location headers
follow your unknown-location rule. [Script loading](/docs/frameworks/next/scripts)
explains each vendor's loading and revocation behavior, and
[the consent checks](/docs/guides/verify-consent) cover the release checklist.
