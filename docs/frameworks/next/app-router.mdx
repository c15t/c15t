## Before you start

This guide uses [Inth](https://inth.com) with cached manifests. Your Next.js
server reuses public policy data and resolves consent for each visitor. The
browser sends consent submissions to Inth.

You can use a [self-hosted backend](/docs/self-host/quickstart) with the same
configuration and your own endpoint. [Offline mode](/docs/frameworks/next/api-reference/data-fetching#offline-configuration)
uses bundled policy and browser storage without backend records. Not recommended
for production environments.

This setup needs a Next.js server. For `output: 'export'`, follow
[static export](/docs/frameworks/next/static-export). For a smaller setup with no
local API routes, use [client-side initialization](/docs/frameworks/next/client-side).
Same-origin [rewrites](/docs/frameworks/next/optimization) are optional.

Location-based policies need trusted location headers from your host. Without
them, c15t uses your unknown-location rule. Check the supported
[geography headers](/docs/frameworks/next/api-reference/data-fetching#geography-and-privacy-signals)
before deploying.

The default layout starts consent resolution on the server and passes the
pending result to the provider, so page content renders without waiting for
consent. The banner, dialog, gated scripts and embeds wait for the result. To
put the resolved banner in the server HTML instead,
[await consent inside `Suspense`](#render-the-banner-in-the-server-html),
which holds the whole page back with it. You can also initialize in the
browser. See [what server prefetch costs](#what-server-prefetch-costs) before
choosing.

## Install c15t and configure your backend

[Create an Inth project](https://inth.com), configure its policy rules and allow
your app's origin. Copy its backend endpoint for the upstream configuration.

If you chose self-hosting, complete the
[backend quickstart](/docs/self-host/quickstart) and use its public endpoint in
the steps below. Offline setups do not need an endpoint; use the
[offline example](/docs/frameworks/next/api-reference/data-fetching#offline-configuration).

With Tailwind CSS 4, add the prebuilt stylesheet to your global CSS after
Tailwind so its component layer follows Tailwind's:

```css title="app/globals.css"
@import 'tailwindcss';
@import 'c15t/next/styles.css';
```

For Tailwind CSS 3, use the [Tailwind 3 stylesheet recipe](/docs/frameworks/next/styling/overview#stylesheet)
instead. It loads `c15t/next/styles.tw3.css` between the `components` and
`utilities` directives to prevent Tailwind from purging c15t selectors.

The layouts on this page import `./globals.css`; without Tailwind the same
`@import` line goes at the top of whatever global stylesheet the layout loads.

Set `NEXT_PUBLIC_C15T_BACKEND_URL` to the absolute endpoint supplied by Inth or
your self-hosted backend, including any path prefix. This is a public endpoint,
not a secret. Configure the backend to allow your app's origin.

## Share the consent URLs

Create this file at the project root. Set `manifestURL` explicitly to select
manifest resolution.

```ts title="c15t.config.ts"
import { defineConsentConfig } from 'c15t/next';

const backendURL = process.env.NEXT_PUBLIC_C15T_BACKEND_URL;
if (!backendURL) throw new Error('Set NEXT_PUBLIC_C15T_BACKEND_URL');

export const consentConfig = defineConsentConfig({
  backendURL,
  manifestURL: '/api/c15t/manifest',
});
```

## Serve the manifest route

The built-in handler reads the absolute upstream URL from `C15T_BACKEND_URL`,
falling back to `NEXT_PUBLIC_C15T_BACKEND_URL` from the setup above. If you set
both, point them at the same backend.

```ts title="app/api/c15t/manifest/route.ts"
export { manifestGET as GET } from 'c15t/next/api';
```

The manifest handler caches public policy data. Server prefetch resolves it
using the visitor's request. Consent submissions go directly to `backendURL`.

The paths below assume `app/` is at the project root. Adjust imports if you use
`src/app/`.

## Start consent resolution in the root layout

Call `resolveConsent` in the root layout without awaiting it, and pass the
pending result to the `Consent` wrapper, which gives it to `ConsentRoot` as
`state`. The helper reads request cookies and geographic headers and resolves
policy from the manifest.

```tsx title="app/layout.tsx"
import type { ReactNode } from 'react';
import { resolveConsent } from 'c15t/next/server';
import { consentConfig } from '../c15t.config';
import { Consent } from '../components/consent';
import './globals.css';

export default function RootLayout({ children }: { children: ReactNode }) {
  const state = resolveConsent({ config: consentConfig });

  return (
    <html lang="en">
      <body>
        <Consent state={state}>{children}</Consent>
      </body>
    </html>
  );
}
```

Next.js renders the page without waiting for consent, and the resolved state
follows in the same response. Until the browser applies it after hydration,
the provider keeps a provisional policy: the banner and dialog stay hidden,
optional categories are denied, `ConsentGate` shows its placeholder and gated
scripts do not load. The provider then applies the server result without
another init request. A new visitor sees the banner. A returning visitor whose
request cookie carries a valid stored choice sees none, and the scripts that
choice allows load at that point. An expired choice, a choice recorded under a
different policy fingerprint, or one that no longer covers every required
category prompts again. Location rules apply when your host supplies trusted
geography headers.

The banner is not part of the server HTML with this layout; it mounts after
hydration. To send it with the HTML, use the
[awaited layout](#render-the-banner-in-the-server-html) and accept that the
page waits with it.

If the manifest request fails, `resolveConsent` resolves to a baseline state
without a policy and logs the failure outside production. The page has already
rendered. The browser retries policy resolution after hydration, and gated
scripts and embeds stay blocked until it succeeds. Pass `onError` to report
these failures; see [troubleshooting](/docs/frameworks/next/troubleshooting).

Keep the c15t stylesheet in `globals.css` rather than importing
`c15t/next/styles.css` from a layout or component. Tailwind CSS 4 declares its
cascade layers in that file; when the c15t stylesheet is bundled separately
and lands first, Tailwind's preflight sits above the c15t component layer and
strips the banner's padding, borders and button styles.

The layout stays synchronous with `cacheComponents: true`, so Next.js can
prerender the page into the static shell. A `ConsentGate` rendered in that
shell fails `next build` with an unstable `Date.now()` error because it reads
the clock while rendering. Wrap each `ConsentGate` in its own `Suspense`
boundary, with a fallback that reserves the embed's size. If `next dev`
reports an unstable `Date.now()` at the `resolveConsent` call, see
[troubleshooting](/docs/frameworks/next/troubleshooting#why-does-nextjs-report-an-unstable-datenow-during-prerendering).

## What server prefetch costs

`resolveConsent` reads request cookies and headers through
`next/headers`. Without `cacheComponents`, this makes routes under the layout
dynamically rendered. With `cacheComponents` enabled, Next.js can prerender
and cache the static shell outside `Suspense`. With the default layout that
shell includes the page content; with the awaited layout the page moves into
the consent subtree, which renders and streams per request.

The first request on a new server instance has an empty manifest cache and
waits for the upstream `/manifest` fetch. In the local benchmark with 150 ms of
simulated backend latency, the single cold sample measured a 252 ms time to
first byte. A build-time manifest seed to remove this cold start is planned in
[c15t/c15t#1096](https://github.com/c15t/c15t/issues/1096).

With a warm manifest cache in the same local benchmark (awaited SSR, new
visitors, 150 ms simulated backend latency), time to first byte was 7.4 ms
median and 15.2 ms at p95 across 10 samples, and the banner markup was present
in the first HTML. That benchmark layout awaits the helper without a `Suspense`
boundary, so it measures neither layout on this page, and its 28 ms banner
metric is a post-hydration visibility probe, not first paint. See the
[benchmark results](https://github.com/c15t/c15t/tree/ccfe906682ba06cef7b56a16cc8fd10728df77d3/benchmarks/reports/next-manifest-2026-09-10)
for conditions.

### Awaiting holds the page

With the [awaited layout](#render-the-banner-in-the-server-html), the page
content streams inside the consent boundary, after the shell. React reveals a
streamed boundary no sooner than 300 ms after the previous reveal or the first
frame the browser painted. If the browser paints before it parses the consent
chunk, or another boundary reveals first, the page appears up to 300 ms after
that point, even with a warm manifest cache. `<SpeedInsights />` from
`@vercel/speed-insights` is one such boundary: it wraps itself in `Suspense`.

A local production benchmark measured a documentation-sized page on Next.js
16.3.4 with `cacheComponents` and a `<SpeedInsights />`-style boundary. Values
are median first contentful paint over 9 interleaved samples:

| Condition | Visit | Default layout | Awaited layout |
| --- | --- | ---: | ---: |
| 4× CPU slowdown | New visitor, warm manifest | 92 ms | 396 ms |
| 4× CPU slowdown | Returning visitor | 92 ms | 388 ms |
| 4× CPU slowdown | New visitor, cold manifest, 200 ms backend latency | 92 ms | 396 ms |
| 4× CPU, 170 ms latency, 1.125 MB/s, static assets cached | New visitor, warm manifest | 252 ms | 560 ms |
| 4× CPU, 170 ms latency, 1.125 MB/s, empty HTTP cache | New visitor, warm manifest | 528 ms | 532 ms |

Whether the delay happens depends on when the browser paints relative to the
consent chunk, so it varies with the device, network and page. In the last
row the stylesheet finished with the end of the HTML and no sample was
delayed; in the other rows 7 to 9 of 9 awaited samples were. When the manifest
request hung, the awaited page stayed blank until the 10 second fetch timeout,
while the default layout rendered the page at once. Gated scripts and embeds
stayed blocked until policy resolved in every case.

The default layout pays with the banner, which mounts after hydration. Under
4× CPU slowdown it still appeared first, at 282 ms against 332 ms for the
awaited layout, whose banner was held back with the page. With the empty-cache
network profile, where the awaited page was not delayed, the awaited banner
was in the DOM at 464 ms and the streamed one at 739 ms; they became
interactive at 750 and 845 ms. The
[benchmark report](https://github.com/c15t/c15t/tree/v3/benchmarks/reports/next-consent-boundary-2026-09-25)
has every sample, the enforcement checks and the reproduction.

The resolved consent subtree contains one visitor's state. Do not put that
subtree, or the complete response containing it, in a shared cache. Public
manifests and the prerendered static shell can be cached separately. See
[cache policy data without sharing visitor state](/docs/frameworks/next/server-side#cache-policy-data-without-sharing-visitor-state).

When the site must stay fully static, use
[client-side initialization](/docs/frameworks/next/client-side).

## Render the banner in the server HTML

To send the resolved banner with the HTML, await `resolveConsent` in an async
Server Component and mount that component inside `Suspense`:

```tsx title="app/layout.tsx"
import { Suspense } from 'react';
import type { ReactNode } from 'react';
import { resolveConsent } from 'c15t/next/server';
import { consentConfig } from '../c15t.config';
import { Consent } from '../components/consent';
import './globals.css';

async function ResolvedConsent({ children }: { children: ReactNode }) {
  const state = await resolveConsent({ config: consentConfig });

  return <Consent state={state}>{children}</Consent>;
}

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <Suspense fallback={null}>
          <ResolvedConsent>{children}</ResolvedConsent>
        </Suspense>
      </body>
    </html>
  );
}
```

The server renders the consent subtree only after policy has resolved, so the
banner arrives already decided and does not change after hydration. The page
content waits with it: `{children}` sits inside `ResolvedConsent` and the
fallback is `null`, so Next.js streams an empty shell first and the page in a
later chunk of the same response, subject to the reveal delay described in
[what server prefetch costs](#awaiting-holds-the-page). A slow manifest
response leaves the whole page blank until the helper returns or its 10 second
fetch timeout fires and the baseline renders. If the manifest request fails,
the page renders with the baseline state and the browser resolves policy after
hydration, so a new visitor sees the prompt appear late.

The `Suspense` boundary is required with `cacheComponents: true`: awaiting
request data directly in the root layout without it fails the build. Without
`cacheComponents`, you can drop the boundary and make the root layout async.
The page and banner then arrive together in the first chunk, with no reveal
delay, but the response starts only after consent resolves: in the same
benchmark a cold manifest with 200 ms of backend latency raised time to first
byte from 11 ms to 216 ms.

## Verify the manifest path

For an opt-in policy, reject and confirm neither configured vendor loads. Allow
measurement only: PostHog can load, while X Pixel stays blocked. Revoke
measurement from Privacy settings and check PostHog's capture is disabled.
See [script loading](/docs/frameworks/next/script-loader) for vendor-specific
loading and revocation behavior.

Inspect server requests and confirm that consent resolution reads the manifest
instead of calling Inth `/init`. Warm requests should reuse policy data according
to its cache headers. Consent choices should post to `${backendURL}/subjects`.

Test a new visitor, a returning rejection and two locations. Missing geographic
headers must follow your unknown-location rule. See
[fetching reference](/docs/frameworks/next/api-reference/data-fetching) for
location headers and [Optimization](/docs/frameworks/next/optimization) for cache
settings. If resolution fails, use
[Troubleshooting](/docs/frameworks/next/troubleshooting), then run
[the consent checks](/docs/guides/verify-consent).

## Initialize in the browser

Keep the shared config and manifest route. Remove the `resolveConsent`
import and call, and render the wrapper with an empty state:

```tsx title="app/layout.tsx"
import type { ReactNode } from 'react';
import { Consent } from '../components/consent';
import './globals.css';

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <Consent state={{}}>{children}</Consent>
      </body>
    </html>
  );
}
```

The browser loads the manifest and resolves policy locally, so the initial
HTML has no resolved prompt. Without supplied location, geography is unknown.
For browser initialization with request geography, see the
[optional local init route](/docs/frameworks/next/api-reference/data-fetching#do-i-need-the-local-init-route).

## Use regular backend initialization instead

For a complete browser-only setup with hosted records, follow
[client-side initialization](/docs/frameworks/next/client-side). It needs no
local route handlers or server prefetch.

For the smallest hosted configuration, keep only `backendURL` in
`defineConsentConfig`:

```ts title="c15t.config.ts"
import { defineConsentConfig } from 'c15t/next';

const backendURL = process.env.NEXT_PUBLIC_C15T_BACKEND_URL;
if (!backendURL) throw new Error('Set NEXT_PUBLIC_C15T_BACKEND_URL');

export const consentConfig = defineConsentConfig({ backendURL });
```

This is an alternative to the manifest configuration. Remove the unused local
manifest route. The existing `resolveConsent` call now initializes
through `${backendURL}/init`; consent saves still use `${backendURL}/subjects`.
A backend-only config does not enable manifest mode automatically.

Compare the choices in [data fetching](/docs/frameworks/next/data-fetching), or
configure cache settings and optional rewrites in
[Optimization](/docs/frameworks/next/optimization).
