## Manual Installation

<Steps>
  <Step>
    ### Install package

    <PackageCommandTabs mode="install" command="c15t" />

    The single `c15t` package includes every framework entry point, including `c15t/tanstack-start`. Prefer installing the scoped packages individually? See [Granular Installs](/docs/granular-installs).
  </Step>

  <Step>
    ### Import styles

    Import the prebuilt component stylesheet in your app-level CSS entrypoint. This is required for styled components to render correctly.

    ```css title="src/styles.css"
    @import "c15t/tanstack-start/styles.css";
    ```

    <import src="../../shared/react/styling/stylesheet-entrypoint.mdx#why-global-css" />

    <Callout type="info">
      If you are using the headless API or fully custom styling, you can skip this import.
    </Callout>
  </Step>

  <Step>
    ### Mount the consent server route

    One splat route gives the browser a same-origin `manifest` endpoint and an `init` endpoint. The `init` endpoint resolves the policy for the visitor's country, language, and Global Privacy Control signal from a cached copy of your backend's consent manifest, so the browser never waits on a cross-origin request.

    ```ts title="src/routes/api/c15t/$.ts"
    import { createFileRoute } from '@tanstack/react-router';
    import { createConsentServerRoute } from 'c15t/tanstack-start/api';

    export const Route = createFileRoute('/api/c15t/$')({
      server: {
        handlers: createConsentServerRoute({
          backendURL: 'https://your-instance.c15t.dev',
        }),
      },
    });
    ```

    You can leave `backendURL` out and set the `C15T_BACKEND_URL` environment variable instead.
  </Step>

  <Step>
    ### Resolve consent in the root route loader

    A server function reads the request's cookies and geo headers on the server and returns a serializable consent config. The loader stores it, and `ConsentBoundary` reads it back with `Route.useLoaderData()`.

    ```tsx title="src/routes/__root.tsx"
    import { createRootRoute, HeadContent, Outlet, Scripts } from '@tanstack/react-router';
    import { createServerFn } from '@tanstack/react-start';
    import { ConsentBanner, ConsentBoundary, ConsentDialog } from 'c15t/tanstack-start';
    import { consentLoaderOptions, createConsentConfigHandler } from 'c15t/tanstack-start/server';

    const backendURL = 'https://your-instance.c15t.dev';

    const getConsentConfig = createServerFn({ method: 'GET' }).handler(
      createConsentConfigHandler({ backendURL })
    );

    export const Route = createRootRoute({
      ...consentLoaderOptions,
      loader: () => getConsentConfig(),
      component: RootComponent,
    });

    function RootComponent() {
      const config = Route.useLoaderData();

      return (
        <html lang="en">
          <head>
            <HeadContent />
          </head>
          <body>
            <ConsentBoundary config={config} backendURL={backendURL}>
              <ConsentBanner />
              <ConsentDialog />
              <Outlet />
            </ConsentBoundary>
            <Scripts />
          </body>
        </html>
      );
    }
    ```

    The handler must be passed to a `createServerFn()` call in your own module. TanStack Start's compiler splits server code out of the client bundle at that call site, so the package cannot declare the server function for you.

    <Callout type="info">
      Hosted mode is the recommended production setup because the backend resolves jurisdiction and policy, keeps durable consent records, and lets c15t recover from temporary network failures by re-syncing later. Leave `backendURL` off `ConsentBoundary` for offline mode with browser-only storage.
    </Callout>
  </Step>

  <Step>
    ### Optional: normalize headers for every request

    Register the request middleware once so server routes and server functions all see the same `x-c15t-country`, `x-c15t-region`, and `sec-gpc` headers, whichever CDN populated them.

    ```ts title="src/start.ts"
    import { createStart } from '@tanstack/react-start';
    import { consentRequestMiddleware } from 'c15t/tanstack-start/middleware';

    export const startInstance = createStart(() => ({
      requestMiddleware: [consentRequestMiddleware()],
    }));
    ```

    During local development no CDN header exists, so pass `consentRequestMiddleware({ country: 'DE' })` to see the banner.
  </Step>

  <Step>
    ### Verify it works

    Start your development server and confirm:

    1. A **consent banner** is already in the server-rendered HTML on the first request
    2. Clicking **"Customize"** opens a dialog with toggles for each consent category
    3. After accepting or rejecting, the banner dismisses and your choice persists across page reloads with no banner flash
  </Step>
</Steps>

## How the first paint stays correct

- The root loader runs on the server for the initial request. The server function reads the `c15t` cookie and the geo headers, resolves init from the cached manifest, and returns a plain object. Returning visitors hydrate with their stored consent, so no banner is rendered for them.
- The config travels only through loader data. The server and the browser each build their own kernel from the same serialized value, which is what keeps hydration free of mismatches.
- On client-side navigation the loader does not re-run: `consentLoaderOptions` sets `staleTime` to infinity and `shouldReload` to `false`.
- When a route opts out of server rendering (`ssr: false`, `ssr: 'data-only'`, or `defaultSsr: false` on the router), the loader runs in the browser and the server function becomes an HTTP call to your Start server, which still reads the real request headers.
- The server helper never fetches the app's own `/api/c15t` route during SSR. It reads the manifest straight from `backendURL` through an in-process cache, and if that fails it returns the baseline config so the browser runs init instead.

See [Server-Side Data Fetching](/docs/frameworks/tanstack-start/server-side) for prerendered builds, custom loaders, and the full server API.
