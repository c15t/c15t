## Configure cleanup

List the cookies and storage keys each optional category owns. When that
category is denied, c15t deletes them:

```ts title="src/consent-cleanup.ts"
import type { ClearOnRevocationConfig } from 'c15t';

export const clearOnRevocation: ClearOnRevocationConfig = {
  measurement: {
    cookies: ['_ga', '_ga_*'],
    localStorage: ['analytics:*'],
  },
  marketing: {
    cookies: ['_fbp'],
    sessionStorage: ['campaign-id'],
  },
};
```

Pass `clearOnRevocation` where you already pass `scripts`:

| Framework | Registration point |
| --- | --- |
| Next.js, TanStack Start | `clearOnRevocation` prop on `ConsentRoot` |
| React | `ConsentProvider options={{ ...options, clearOnRevocation }}` |
| Nuxt, Vue | `clearOnRevocation` in the c15t config |
| Svelte, SvelteKit | `clearOnRevocation` in the `ConsentManagerProvider` options |
| Astro | `clearOnRevocation` in the integration options, or in the client entrypoint's options |
| JavaScript | `createConsentRuntime({ ...options, clearOnRevocation })` |

Without `clearOnRevocation`, c15t deletes nothing. The option is read once when
the provider starts; remount the provider to change it. For a shared runtime,
configure the runtime owner, not a provider that borrows it.

## Name cookies and keys

Use an exact name, or a prefix followed by `*`. `_ga_*` matches `_ga_ABC123`
but not `_ga`, so list both. Regular expressions, a `*` anywhere but the end,
and a bare `*` are not supported. Cookie names are matched as written, without
URL decoding. `necessary` cannot be configured.

By default c15t tries the current host and its parent domains, and the current
path and its parents. For a cookie set on a specific scope, use an object:

```ts
const cookies = [
  { name: 'analytics-id', domain: 'example.com', path: '/' },
  { name: 'checkout-metrics', domain: '', path: '/checkout' },
  { name: 'partitioned-metrics', partitioned: true },
];
```

An empty `domain` means a host-only cookie. A `domain` or `path` you set
replaces the automatic attempts for that field. Partitioned cookies need
`partitioned: true`. A prefix only finds cookies the current page can read, so
use an exact name for a cookie on another path.

c15t never deletes its own consent records, even when a pattern matches them.

## When cleanup runs

- On the first page load after the policy resolves, for every denied category.
  This covers a new opt-in visitor and a returning visitor whose choice
  expired.
- Whenever a category changes from allowed to denied, after a saved refusal,
  expiry, a policy change or a Global Privacy Control signal.

Cleanup does not run during server rendering, while the policy is still
loading, on draft switch changes in the dialog, or when the provider unmounts.
It runs once per change and does not poll. Under an opt-out policy, an expired
choice that stays allowed deletes nothing. If a resolved policy later falls
back to denial after a failed request, cleanup deletes the data, and a
successful retry cannot restore it.

## Browser limits

c15t can delete first-party cookies that JavaScript can read, and keys in the
current origin's `localStorage` and `sessionStorage`. It cannot delete
`HttpOnly` cookies or another origin's data; expire those from your server. A
vendor SDK still running on the page can write its cookies again, which is one
reason c15t reloads the page after a revocation. Deletion failures do not block
the consent update. See
[MDN on cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).

## Attach cleanup to your own kernel

If you assemble c15t modules yourself, attach cleanup in the browser after
persistence and the script loader:

```ts
import { createClearOnRevocation } from 'c15t/modules/clear-on-revocation';

const cleanup = createClearOnRevocation({
  kernel,
  config: { measurement: { cookies: ['_ga', '_ga_*'] } },
  storageConfig,
});

// Stop watching consent when your integration is torn down.
cleanup.dispose();
```

`kernel` is your consent kernel. Pass the same `storageConfig` as persistence
so custom consent record keys stay protected. If the policy has already
resolved, attaching can delete data for denied categories at once. Do not
attach it when a provider or runtime already has `clearOnRevocation`.

## Verify cleanup

1. Allow measurement and let Google Analytics run. In DevTools Application,
   Cookies shows `_ga` and a `_ga_<id>` cookie.
2. Open Privacy settings, turn measurement off and save. c15t reloads the
   page. Both cookies are gone, and `analytics:*` keys are gone from Local
   storage.
3. Reload. The cookies do not come back, because Google Analytics no longer
   loads.
4. If you listed a cookie with an explicit `domain` or `path`, repeat step 2
   and check that the cookie is gone from that scope too.
