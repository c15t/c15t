Vector identifies the people and companies visiting your site and builds
advertising audiences from their activity. The c15t `vector` helper keeps
Vector off the page until `marketing` consent is granted. Vector has no
documented stop API, so on withdrawal c15t reloads the page to stop it.

## Configure Vector

Copy the pixel ID from **Settings > Pixel** in your Vector account, where the
install snippet calls `vector.load`. Vector's own consent example requires
advertising consent, so this helper uses the `marketing` category. Remove the
direct snippet and any tag manager copy so they can't bypass c15t.

## Options

| Option | Default | Behavior |
| --- | --- | --- |
| `pixelId` | Required | Pixel ID from your account snippet. Whitespace is trimmed. A missing or blank ID logs `vector: missing or invalid pixelId` and skips loading. |
| `scriptUrl` | `https://cdn.vector.co/pixel.js` | Custom SDK URL. Blank values use the default. |

## Loading and revocation

After consent, the helper creates `window.vector` with a queue for `load`,
`identify` and `on`. Calls use Vector's nested argument format,
`[methodName, argsArray]`, and preserve callback references. The helper queues
`load(pixelId)` before inserting the asynchronous SDK script. Existing SDK
methods are preserved. The helper sends no identification calls itself.

The loader stays registered across withdrawal and regrant to avoid duplicate
execution on the same page. Vector has no documented complete shutdown API.
Keep c15t's default page reload on revocation enabled. With reload disabled,
running code, pending loads and partner activity can continue until navigation.
The reload doesn't clear Vector's storage.

The helper does not call the undocumented `block` or `removeVisitor` methods.
Form listening and IP-to-company lookup depend on account settings. Vector's
IP-to-company consent hooks cover only that lookup and cannot replace gating
the whole pixel.

## Requests, cookies and storage

Vector's CSP guide lists `cdn.vector.co`, `api.vector.co` and
`a.usbrowserspeed.com`. The current SDK also includes LiveIntent and can contact
`idx.liadm.com`. Check requests for your account before setting CSP rules.

The current SDK prefers local storage, with session storage, cookies and memory
as fallbacks. Pixel state can include
`vector_pixel_<pixelId>_visitor_id`, `vector_pixel_<pixelId>_visitor_uuid`,
`vector_pixel_<pixelId>_synced_at` and
`vector_pixel_<pixelId>_last_identified_id`. Legacy and global keys also exist.

The `vector_visitor_id` cookie depends on the account's `pixelCookieFallback`
setting. The fetched SDK requests a lifetime of 3,650 days, with
`SameSite=None; Secure`; browsers may shorten that lifetime. Partner state can
include `_lc2_fpi`, `_lc2_fpi_js`, `_li_dcdm_c` and local-storage `_li_duid`.
Vector can read the existing `hubspotutk` cookie. This list describes the fetched
SDK, not a stable or exhaustive storage contract.

## Verify Vector

Use your own pixel ID on a domain allowed by your Vector account. In a fresh
browser profile, deny optional consent, then grant only measurement consent.
Confirm that no Vector global, SDK request or vendor storage appears. Grant
marketing consent and confirm that `pixel.js` loads once. Withdraw consent and
confirm the page reloads and blocks Vector on the new page. Check Network,
cookies, local storage and session storage.

c15t's live vendor probe uses a placeholder pixel ID. It confirms that the
downloaded SDK replaces the queue, replays the nested calls and registers the
pixel. It blocks settings, identity and collection requests, so the SDK can log
a JSON error for the empty settings response. Vector checks the requesting
domain before it returns settings, so the probe can't verify account settings
or visitor identification. Test those with your own pixel ID on an allowed
domain.
