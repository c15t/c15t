## How c15t follows another CMP

Give c15t a `consentSource` when another consent management platform (CMP)
should keep showing the banner and storing choices. The CMP stays in charge of
its banner, preference center, records, expiry, privacy signals and category
mapping. c15t reads the CMP's current permissions and uses them to load
scripts, embeds and network rules. It records no second choice.

Optional categories start denied, including during server rendering. They stay
denied until the CMP reports a decision, and go back to denied if the CMP
cannot be read. Load the CMP itself outside c15t, or register its loader with
`alwaysLoad: true`, so it does not wait for its own consent.

## Write the consentSource adapter

The adapter is an object with three functions. Its type,
`ExternalConsentSource`, is exported from `c15t/runtime`:

```ts title="src/consent-source.ts"
import type { ExternalConsentSource } from 'c15t/runtime';
import { provider } from './existing-cmp';

export const consentSource: ExternalConsentSource = {
  getPermissions: () => provider.getCategoryPermissions(),
  subscribe: (notify) => provider.subscribe(notify),
  openPreferences: () => provider.openPreferences(),
};
```

`provider` stands for your own wrapper around the CMP's API; c15t does not
export it.

| Function | What it must do |
| --- | --- |
| `getPermissions` | Return `measurement`, `marketing`, `functionality` and `experience` as booleans, mapped from the CMP's categories. Return `null` until the CMP is ready. Missing categories are denied; `necessary` is always `true`. |
| `subscribe` | Call `notify` when the CMP initializes, and on every change, withdrawal and expiry. Return a function that removes the listener. |
| `openPreferences` | Open the CMP's preference center. |

Keep browser access inside these functions, so importing the adapter during
server rendering is safe. If `subscribe` throws, c15t reports the error
through `callbacks.onError` and starts with optional categories denied. It then
ignores that source until you recreate the provider.

## Pass consentSource to your framework

Register `consentSource` and your `scripts` on the same provider. Do not create
a second c15t runtime next to an existing provider.

| Framework | Registration point |
| --- | --- |
| React | `ConsentProvider options={{ mode, consentSource, scripts }}` |
| Next.js / TanStack Start | `ConsentRoot options={{ consentSource }}` with `scripts` as a top-level prop; `ConsentProvider` also accepts the React options |
| Vue | `app.use(c15tVue, { consentSource, scripts })` |
| Nuxt | `app.config.ts` → `c15t: { consentSource, scripts }` |
| Svelte / SvelteKit | `ConsentManagerProvider` options or corresponding top-level props |
| Astro | `consentSource` in the default export of the `clientEntrypoint` module |
| Browser client | `createConsentClient({ consentSource, scripts })` |
| Headless JavaScript / Solid | `createConsentRuntime({ mode, consentSource, scripts })` |

For example, in a React client component:

{/* example: fragment */}

```tsx
<ConsentProvider options={{ mode: offline(), consentSource, scripts }}>
  {children}
</ConsentProvider>
```

`mode` is still required by the provider, but with a `consentSource` c15t skips
its backend initialization and storage. Do not render c15t's banner or dialog.
c15t's preference links, hooks and `kernel.set.activeUI('dialog')` call
`openPreferences` instead, and `kernel.commands.save()` rejects rather than
recording a second choice. Errors from `openPreferences` reach
`callbacks.onError`.

Framework notes:

- **Next.js**: create the source in a client component. Functions cannot pass
  from a Server Component. A client-side `ConsentProvider` avoids a server
  consent fetch that an external source does not use.
- **Nuxt**: put the functions in `app.config.ts`, not in public runtime
  config, which must be serializable. With a source configured, the module
  skips its consent fetch.
- **Solid and headless JavaScript**: create the runtime once, call `start()`
  on mount and `dispose()` on cleanup. The other frameworks' providers do this
  for you. A provider given an existing `runtime` borrows it, so configure
  `consentSource` on the runtime.

## What happens when the CMP withdraws consent

When the CMP turns off a category that was allowed, c15t reloads the page, the
same as when a visitor revokes consent in c15t's own dialog. Removing a script
element does not stop code that already ran, so the reload starts a page with
only permitted code. The reload runs after synchronous consent callbacks and
`onBeforeConsentRevocationReload`. Disposing the provider cancels a pending
reload.

c15t cannot tell a withdrawal from an expiry or a reset in the CMP, so any
notification that turns off an allowed category reloads. Save the new decision
in the CMP before calling `notify`, or the reloaded page reads the old one. Set
`reloadOnConsentRevoked: false` to handle withdrawal yourself; c15t still
updates its gates and calls script `onConsentChange` callbacks.

## Verify the CMP connection

1. In a private window, load the page. The CMP's banner appears and c15t
   renders none. In DevTools Network, no gated vendor loads.
2. Accept analytics in the CMP. Measurement scripts registered with c15t load
   without a reload.
3. Reload. The same scripts load, read from the CMP's stored decision.
4. Open preferences from a c15t preference link. The CMP's preference center
   opens.
5. Withdraw analytics in the CMP. c15t reloads the page and measurement scripts
   no longer load.
6. Block the CMP's script and reload. Every optional category stays denied.

Check your CMP's category mapping and any tag-manager container too. c15t's
gates do not validate those settings.
