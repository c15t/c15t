The c15t `insiderTag` helper waits for `marketing` consent before creating
`InsiderQueue` or requesting Insider's `ins.js`. It queues
the supplied current user attributes with `gdpr_optin: true`, optional currency,
the current page definition, and `init` before the
loader starts. On revocation it sends `gdpr_optin: false`, a neutral
`{ type: 'other' }` page, and `init`, then removes the loader. Keep c15t's
default reload-on-revocation behavior enabled to stop code the SDK already ran.

## Configure Insider

Ask Insider for your public `partnerName` and `partnerId`, and confirm that
Web SDK integration is enabled for your account. Replace any existing Insider
tag or tag-manager installation so it cannot load outside c15t's consent gate.
Remove any code that defines or populates `window.insider_object` too. Insider
does not support running that legacy integration alongside `InsiderQueue`.
Insider says to keep the tag off pages containing sensitive information, such
as payment pages with credit card data.

## Options

| Option | Default | Behavior |
| --- | --- | --- |
| `partnerName` | Required | Public partner name from Insider. Trimmed, lowercased, and checked as a single DNS label for `<partnerName>.api.useinsider.com`. A missing, blank, or invalid value logs an error and skips the integration. |
| `partnerId` | Required | Public partner ID from Insider. Trimmed and encoded as one query value. A missing or blank value logs an error and skips the integration. |
| `user` | Omitted | Complete current user attributes for the final grant push, including checkout identifiers and account-specific `custom` data. The helper controls `gdpr_optin` and sends no supplied attributes on denial. |
| `currency` | Omitted | Current currency string, such as `'GBP'`. Queued as `{ type: 'currency', value: 'GBP' }` before the page and `init`. A supplied value must be a non-blank string or the helper throws `TypeError`. No code whitelist or case conversion is applied. |
| `pageType` | `{ type: 'other' }` | Complete page push, including any required `value` fields. A purchase requires the per-order guard described below. |
| `category` | `'marketing'` | Consent condition required before creating the queue or loading the tag. Accepts a category or an `and`/`or`/`not` condition. |

For an account classified as personalization, you can replace the default
condition with `category: 'experience'`. The same condition controls both
loading and the `gdpr_optin` value sent on revocation.

## Supply the current user and currency

Insider uses the last successful `user` push when `init` runs. Pass the complete
current user's attributes in `user`; a separate earlier queue entry is not a
way to supply them to the helper. The helper merges these attributes into its
final grant push and sets `gdpr_optin: true` after them, so caller data cannot
override effective consent. It never recovers identity from historical queue
entries. Without `user`, it sends only `{ gdpr_optin: true }` on grant.

Use Insider's attribute names and types. For example, `email`, `phone_number`
and `uuid` are strings; `age` is a number; `email_optin` is a boolean; and
`custom` contains account-specific attributes. Keep custom identifiers inside
`custom`, configure them in Insider's Identity Resolution Management settings,
and send their values as strings. Follow the Web SDK guide for field formats,
including E.164 phone numbers. Nested objects pass through without flattening;
the helper does not validate their support or schema in your account. Use
JSON-serializable data matching Insider's definitions.

Insider documents that logging out does not reset the browser's Insider ID.
For a guest purchase, supply the current guest's available checkout identifiers,
such as email and phone number, in `user` before purchase initialization. Do
not reuse the previous customer's identifiers or invent an ID from an order.
Insider's matching and merging still depend on those identifiers and your
account settings; the option alone does not guarantee correct unification.

<include src="../shared/examples/javascript/insider-current-user.mdx" />

Build this configuration from the current checkout or session data, current
storefront currency, and guarded page definition before registering it with
your consent adapter. Keep the returned scripts stable while those values are
current. User attributes, including nested data, are snapshotted when the helper
is called; later mutations to the supplied object do not update that configuration.
The helper does not watch login, logout, checkout, currency, or route
changes. Rebuild stale configuration through the app's session and order logic
before a fresh registration or page load. Recreating an already active helper
does not itself send new user data or restart it.

Multi-currency sites must supply the currency used for the configured prices.
The helper queues `user`, then optional `currency`, then the page, then `init`.
Insider preserves user data and currency between initializations. Omitting
`currency` sends no currency update, so an earlier or account-default value can
remain active. For a single-currency site, confirm with Insider that omitting
the currency push is appropriate. The helper neither converts prices nor
clears Insider's stored identity or currency.

## Define the page context

`pageType` is an object with the SDK's exact `type` and `value` fields. Insider
documents these six page definitions. It does not call basket pages `basket`
or order confirmation pages `confirmation`.

| `type` | `value` |
| --- | --- |
| `'home'` | Optional `{ custom }` event parameters. |
| `'other'` | Optional `{ name, custom }` for any other page. |
| `'category'` | `{ breadcrumb: string[] }` for a listing page. Insider requires the category hierarchy for many use cases. |
| `'product'` | Product data with `id`, `name`, `taxonomy`, `unit_price`, `unit_sale_price`, `url`, and `product_image_url`. |
| `'cart'` | `{ total, items, shipping_cost? }`. Each item needs the product fields and `quantity`. |
| `'purchase'` | `{ order_id, total, items, shipping_cost? }`. Each item needs the product fields and `quantity`. Only for a newly completed order after the per-order guard permits it. |

Products also accept the optional string fields `brand`, `description`, `gtin`,
`sku`, `identifier_exists`, `locale`, `google_title`, `gender` and
`omnibus_price`, plus `groupcode`, `color`, `size`, numeric `stock` and
account-specific `custom` data. Cart and purchase items accept these fields too.
Insider's Web SDK guide specifies strings for `identifier_exists` and
`omnibus_price`.

Page values must be JSON-serializable. The helper passes custom data as literal
JSON, including objects with `kind: 'c15t.runtime-value'` and `value: 'date'` or
`'timestamp'`. It does not interpret those objects as runtime instructions.
Normal JSON serialization rules apply, so a JavaScript `Date` becomes a string
and object properties with `undefined` values are omitted. Queue consumers
receive a copy; their mutations do not change the supplied page data.
The helper's server-start code uses the same JSON conversions.

The helper queues the page object followed by `init`. Insider documents that
every `init` updates the profile and triggers a page-view event for the last
defined page.

The helper defines the initial page only. It does not watch client-side route
changes. For single-page navigation, follow Insider's
[Web SDK guide](https://academy.insiderone.com/docs/insider-web-sdk-integration-guide)
to push the new page definition followed by `init`, only while the configured
consent condition and the Insider vendor switch are allowed. Push complete
current user attributes and the current currency before the page and `init`
when that context changes. Your app owns these updates and the handling of stale
identity, currency and cart context. Keep manual `user` pushes consistent with
current consent. Insider treats an omitted `gdpr_optin` as `true`.

### Prevent duplicate purchases

**A purchase configuration requires a durable per-order guard in your app.**
The helper does not deduplicate `order_id`. Configuring `purchase` whenever the
confirmation URL renders would enqueue the order again on every permitted
load. Insider's [confirmation-page guide](https://academy.insiderone.com/docs/integrate-insider-into-your-confirmation-page)
forbids repeating the purchase after refresh, Back navigation, another page
visit, or opening the confirmation URL in a new tab.

Use an atomic claim in your order backend, keyed by the completed order ID,
before exposing a purchase payload to the page. Only the request that claims
that order may build `pageType: { type: 'purchase', value: ... }`. Return
`{ type: 'other' }` for subsequent requests. An in-memory flag or a check of the
current URL cannot protect against a reload or a second tab. Only confirmed,
successful orders qualify, and the confirmation page must contain no payment
card data.

Do not reuse a claimed purchase configuration when recreating the helper or
reinitializing it after withdrawal. Keep the default reload on revocation and
rebuild the page configuration through the same order guard. Apply that guard
to manual SPA purchase pushes too. If your app cannot enforce this rule, use
`other` instead of configuring a purchase.

This limits purchase attempts; it does not guarantee delivery. A claimed order
may never reach Insider if the visitor denies consent or the loader fails.
The guard must not itself create Insider globals or send Insider requests
before effective consent. c15t still gates the configured purchase and loader.
The `user` and `currency` options do not provide at-most-once purchase handling.

## Loading and revocation

The loader URL is
`https://<partnerName>.api.useinsider.com/ins.js?id=<partnerId>`. c15t inserts
it asynchronously into `<head>` after consent. Before the first grant, this
helper creates no Insider global, request, cookie, or Web Storage entry.
That guarantee requires removing other Insider installations and applies to
this helper's work.

If the category or the Insider vendor switch is revoked after installation,
the helper pushes `{ type: 'user', value: { gdpr_optin: false } }`, then
`{ type: 'other' }`, then `{ type: 'init' }` through `InsiderQueue.push`.
The neutral page replaces the SDK's last page definition before the withdrawal
`init`, so that init does not replay a purchase. The helper replaces the page
on every withdrawal, including when your app manually pushed a purchase during
SPA navigation. c15t sends these updates; you do not need to call the queue
yourself.

The denial user payload contains only `gdpr_optin: false`. The helper does not
resend caller attributes or currency on withdrawal, even if `user` contains
`gdpr_optin: true`. This avoids forwarding new checkout or identity data after
withdrawal. It does not clear identity or currency already held by Insider.

This updates the user's consent through the same `user` and `init` lifecycle
used on grant. It is not an SDK unload or a promise that all requests stop.
Insider says `gdpr_optin: false` prevents campaigns except cookieless cases
and prevents Insider messages. It does not document a shutdown or unload
method in the integration guide. The final `init` can trigger an Other Page
View, so the helper does not promise zero traffic after revocation on the
running page. Replacing the page does not deduplicate purchases or remove
earlier queued purchase entries. The durable per-order guard and guarded
configuration rebuild on reload or regrant are still required.

c15t removes the loader, but a download already in flight can still finish,
and code that already ran can keep listeners or timers. If consent is revoked
before the SDK starts, the queue still contains the earlier grant and `init`
before the denial update. A late SDK may process those earlier entries first.
Removing the loader does not prove that the SDK discarded them. Keep
`reloadOnConsentRevoked` enabled. On the next page with denied consent, c15t
creates no queue and loads no Insider tag. The reload does not wait for Insider
to acknowledge the consent update and does not delete existing vendor storage.

## Cookies and storage

The helper writes no cookies, localStorage, or sessionStorage itself. After
consent, Insider's tag can use all three. The public loader contains cookie
and Web Storage code and storage names including `spUID`, `ins-current-currency`,
and `ins-cart-product-list`. These names come from the loader source; they
are not a browser-observed inventory or a promise that every account writes
them. Campaigns, account settings, and SDK updates can change the storage used.

Inspect your account in DevTools Application after a grant and again after a
revocation. Record cookie names, domains, paths and expiries, plus localStorage
and sessionStorage keys. Configure c15t's clear-on-revocation rules from that
inventory. This helper does not guess storage prefixes to delete, and browser
JavaScript cannot remove HttpOnly or inaccessible third-party cookies.

## Verify Insider

Use an opt-in policy in a fresh private window and filter Network by
`useinsider.com`. Before grant, including after a rejection and reload, there
should be no Insider request and `window.InsiderQueue` should be undefined.
After grant, check the partner-specific `ins.js` request. Verify the final user
push contains the current identifiers, followed by the supplied currency, page,
and `init`. In your Insider account, verify the resulting profile, page context,
and price currency, including a guest checkout after a previous customer's
logout. Queue contents alone do not prove profile matching or delivery. Test both category
revocation and the Insider vendor switch. The next denied page should make no
Insider request. Check existing storage separately; a removed loader does not
prove cleanup.

A placeholder partner can return HTTP 200 with an HTML error body. That response
proves the endpoint answered; it does not prove the SDK ran or that an account
accepted your events.
