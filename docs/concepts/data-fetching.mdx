## Compare the fetching paths

Where policy resolves and where choices are saved are separate from who runs
the backend. Inth and a [self-hosted backend](/docs/self-host/quickstart) speak
the same protocol, so every path below works with either. Only `offline()`
removes backend requests. For a recommendation by framework, start with
[choose your setup](/docs/concepts/choose-your-setup).

| Fetching path | Where policy resolves | Where choices are submitted | Choose it when |
| --- | --- | --- | --- |
| Build-time manifest, recommended | Your server or browser resolves a bundled policy snapshot with each visitor's inputs | Inth or your c15t backend | Your framework supports a build integration and policy changes can ship with a rebuild |
| Cached manifest on your server | Your application resolves public policy data with each request's location and signals | Inth or your c15t backend | Policy changes must reach the app without rebuilding, or builds cannot access the backend |
| Regular backend `/init` | The consent backend | The same backend | You want the fewest moving parts, need backend-owned request resolution, or have no application server |
| Manifest in the browser | The browser, using supplied or unknown location | Inth or your c15t backend | You deliberately want client resolution and have planned geography, bundle size and policy refresh |
| Offline | The browser or local runtime, using bundled rules | No backend submission | Local development and tests. Not recommended for production environments. |
| Custom transport | Your implementation | Your implementation | An existing service cannot use the c15t backend protocol |

## What is a consent manifest?

A manifest is a versioned policy document served by `GET /manifest`. It contains
policy rules, translation configuration and related consent configuration. It
is public configuration, not a visitor's saved choices. A resolver combines the
manifest with country, region, language and privacy signals to produce an init
result for one visitor.

Reusing the public document avoids asking the consent backend to resolve policy
for every application request. Cache misses and revalidation still fetch the
manifest, and consent writes still need the backend. Measure the deployed
request path before promising a latency improvement.

Do not put secrets, visitor identifiers or consent records into a manifest.
Keep personalized init responses out of shared caches. Changing a policy also
requires a refresh strategy for cached or build-time manifests.

## How manifest mode counts visitors

The backend counts visitors from `/init` requests, and manifest resolution
skips them. To keep the count, the server adapters send a session report after
each resolution: the host posts to the backend's `POST /sessions` from the
server, after the response. The browser sends nothing, and the report stores
no identity; the visitor's IP address and user agent are forwarded under the
backend's usual IP handling. Static output resolves in the browser and sends
no report. Set `reportSessions: false` on an adapter to turn it off.

## Link an init to the save that follows

Each page load gets a journey id: a random UUID that rides on requests c15t
already makes. The browser sends it as query parameters, so a backend needs no
CORS change to accept it.

| Request | Parameters |
| --- | --- |
| `GET /init` | `c15tJourney`, `c15tJourneyScope`, `c15tStored` (`1` when the browser had a stored choice) |
| `POST /subjects` | `c15tJourney`, `c15tJourneyScope` |

The backend's `/init` and every adapter's init route copy the journey into
their session report as `journey: { id, scope, storedChoice, prompt, domain }`.
`domain` is the page's hostname, from the request's `Origin` or host.
`prompt` is `due` when the policy prompts and no choice was stored, `stored`
when a stored choice was used, and `not-required` when the policy shows no
prompt or the resolution failed. A resolution that matched no policy, or ran
with none configured, still shows the fallback opt-in banner, so it counts as
`due` or `stored`. A report and the save with the same `journey.id` belong to
one visitor's page load.

Where the journey starts:

- A server render starts it, puts it on its `/init` (with the page's `Origin`)
  or its session report, and hands the id to the browser in the state. When
  the render resolves the page without one (`journey: false`,
  `reportSessions: false`, a manifest render with no absolute backend to report
  to, or a prefetch), the state says `journey: null` and the browser sends
  none.
- A request sent before the runtime starts, React's early `/init` or the
  inline prefetch script, starts it and records it on the page.
- Otherwise the runtime starts it when it starts.

The runtime continues the first of these that exists, so a save carries the id
of an `/init` or report that came before it. Manifest mode that resolves init in the
browser makes no request at all, so a page resolved that way has no journey:
its saves carry none. A save queued while offline and
sent again later, on this page or another, carries no journey. When an init
route has to ask the backend's own `/init`, it forwards the journey with the
page's `Origin`; the backend falls back to the request's host when a browser
sends no `Origin`.

The id is not the subject id, is never written to a cookie, and is not derived
from anything about the visitor. Choose how long it lives with the provider's
`journey` option:

| Value | Behavior |
| --- | --- |
| `'page'` (default) | One id per page load, kept in memory. |
| `'tab'` | The id is kept in `sessionStorage` while a prompt is due, so a visitor who moves to another page before choosing keeps it. It is removed once a choice is recorded, or once a page resolves to no prompt. Unusable storage falls back to `'page'`. |
| `false` | No journey parameters. |

`'tab'` works best when the browser resolves init itself. A server render
cannot read `sessionStorage`, so it starts a new id on every page. When the tab
already has an id, the browser keeps it over the server's: an earlier page's
`/init` or report carried it, so the save still links to a report, while this
page's render report carries an id no save uses.

Where to set it:

| Package | Browser | Server render |
| --- | --- | --- |
| `@c15t/core` | runtime `journey` | `resolveRequestConsent({ journey })` |
| `@c15t/react` | provider `journey` | none |
| `@c15t/nextjs` | `defineConsentConfig({ journey })`, read by `ConsentRoot` | the same config, or `resolveConsent({ journey })` |
| `@c15t/tanstack-start` | `ConsentRoot` `options.journey` | `resolveConsent({ journey })`; pass both the same value |
| Vue, Svelte, Astro, script tag | `'page'` only for now | `'page'` only for now |

The Vue, Svelte and Astro server renders start a `'page'` journey, which is
what their browsers keep, so the two agree. Their `reportSessions: false` turns
it off on both sides. Pass the same value to `buildPrefetchScript({ journey })`
when you use the inline prefetch script.

A `fetch` you pass to `hosted()` sees the query string, so match on the path
rather than the full URL.

## What does regular `/init` do?

`hosted({ url })` uses `${url}/init` for initialization and `${url}/subjects` for
consent submissions. The name `hosted` describes the transport protocol; the URL
can belong to Inth or your own c15t backend.

```ts title="src/consent-mode.ts"
import { hosted } from 'c15t';

export function createConsentMode(backendURL: string) {
	return hosted({ url: backendURL });
}
```

Pass the factory to your adapter's `mode` option. For request rendering, use the
adapter's server helper and forward its prepared result to the browser. For
static output, initialize in the browser with a reachable external URL.

A regular backend `/init` request lets the backend resolve the visitor context.
A same-origin URL named `/api/c15t/init` can instead resolve from a cached
manifest in your application. The URL name alone does not tell you which path
runs.

## How do transports and proxies differ?

A transport implements initialization, saving and optional record operations.
A proxy changes where HTTP requests travel. It does not change the policy
resolver or make personalized responses safe to cache.

For a same-origin init route that resolves a manifest, the hosted transport can
separate policy reads and record writes. With a backend rewrite mounted at
`/api/c15t`, a client mode can use:

```ts title="src/consent-mode.ts"
import { hosted } from 'c15t';

export const mode = hosted({
	url: '/api/c15t',
	initURL: '/api/c15t/init',
	assertDecisionInputs: true,
});
```

The route must return the c15t init response contract. `assertDecisionInputs`
binds saves to the resolved policy when init did not return a signed policy
snapshot token. The backend can then reject a stale policy decision. Next.js
sets this option for you when `ConsentRoot` receives a `config` with
`initURL`.

The init route resolves policy; the backend rewrite forwards `/api/c15t/subjects`
and other record endpoints. Configure both if you choose this optional proxy
variant. The
[Next.js rewrite recipe](/docs/frameworks/next/optimization#keep-browser-consent-requests-on-your-origin)
shows the configuration. A direct absolute backend URL works
without a rewrite.

This optional optimization keeps c15t requests on the app's origin and avoids a separate browser DNS lookup
and TLS connection to the consent backend. The app server still connects to
the upstream backend for manifest refreshes and consent writes. Vendor scripts
and vendor requests keep their own origins.

The rewrite destination and the init route use the absolute upstream endpoint,
such as `https://your-project.inth.app`. The browser uses `/api/c15t` without
needing the upstream URL. A static export cannot serve a Next.js route or
rewrite at runtime; use the absolute Inth URL or a proxy provided by the static
host instead.

## When should I use offline mode?

Not recommended for production environments. Use Inth or a self-hosted backend
for production policy and consent records.

`offline()` resolves bundled policy rules without an init request and acknowledges
saves locally. The runtime's persistence module stores the choice in browser
storage. There is no backend audit history, cross-device record service or IP
geolocation supplied by this transport.

Use your adapter's offline factory so its translations and provider context are
included. This React and Next.js example replaces the hosted mode in an existing
client provider:

```ts title="src/consent-mode.ts"
import { offline } from 'c15t/react';

export const mode = offline();
```

With no `policyRules`, the current offline transport uses the recommended rule
pack. Supplying `policyRules` replaces that pack. Unknown country and region are
real resolution inputs; offline mode does not discover a visitor's location.
Use [policy rules](/docs/concepts/policies) to understand
matching and defaults, and test the missing-location case.

Offline mode is an explicit architecture choice, not an automatic fallback for
a failed Inth request. If hosted initialization fails before a policy resolves,
optional permissions remain denied and the stock prompt stays hidden. Observe
initialization failures instead of silently changing policy sources.

## Can I provide my own transport?

`custom(transport)` accepts a `KernelTransport` with the v3 `init` and `save`
contract. It does not accept v2 endpoint handlers such as `setConsent`. Keep
policy resolution, record acknowledgments and failure behavior consistent with
the kernel contract. Prefer a built-in transport when your backend supports it.

## Verify the selected path

Inspect browser and server requests separately. A server manifest fetch will
not appear in the browser's Network panel. With a build-time snapshot, start a
fresh production server and confirm it makes no upstream `/manifest` request.
After a policy edit, rebuild and confirm the new policy appears. On a runtime
manifest path, check that
page requests do not call the backend `/init`, a visitor's choice still reaches
the backend's `/subjects`, and policy changes become visible after the configured
refresh. With a same-origin consent proxy, the browser should call only
`/api/c15t` paths for consent HTTP traffic; inspect server logs to verify their
upstream destinations.

Test different locations, missing location headers, GPC, returning choices and
backend failure. See [verification](/docs/guides/verify-consent).
