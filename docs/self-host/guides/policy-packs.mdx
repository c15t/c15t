## Configure the manifest

```ts
import { c15tInstance } from '@c15t/backend';
import { policyRulePresets } from '@c15t/schema';

const backend = c15tInstance({
  database: { dialect: 'sqlite', filename: ':memory:' },
  manifest: {
    policyRules: [
      policyRulePresets.europeOptIn(),
      policyRulePresets.californiaOptOut(),
    ],
  },
});
```

Use your existing database and instance options alongside `manifest`. Rules own
behavior, and host `presentation` owns layout. The allowed models are opt-in,
opt-out and IAB. Only opt-out permits notice or no first-layer prompt. See the
[preset reviews](/docs/frameworks/javascript/concepts/policy-packs#policy-rules)
for assumptions, source dates and review reminders.

## Versioned responses

The manifest uses `schemaVersion: 2`, with normalized `rule` and precomputed
fingerprints per pack. `/init` returns `policyResolution` with contract version 1.
Clients send `x-c15t-policy-contract: 1`; `x-c15t-version` is telemetry only.
Unsupported contract declarations fail safely. Preserve the contract header
through proxies and permit it through CORS.

`matched` contains a rule. `unconfigured`, `no-match` and `failed` contain explicit
`policy: null`, clearing stale policy-derived state and selecting the safe opt-in
choice fallback. Missing fields are invalid, not no-match. An empty pack never
means allow-by-default. Invalid rules produce `policyFailure`; inspect and fix
that startup diagnostic before deployment. The manifest ETag tracks its revision.

## Cached old clients

The backend's legacy response is a safe opt-in compatibility projection. That
cannot repair code already cached in a visitor's browser. Tests with the original
client and its hosted and manifest transports found that fresh clients deny,
but old clients with stored grants retain them even under GPC. Invalidate and
redeploy those clients before relying on new prompt or privacy semantics.

External hosted producers must deploy the matching contract and privacy endpoint.
Local package support does not establish that a hosted deployment has done so.
No notice-dismissal endpoint or proof capability exists in this version.

### Receipts on the write path

`POST /subjects` accepts the receipts a v3 client confirms (`choice`) and stores them on the consent row as sent. Migration `3-consent-receipts-and-privacy-directives` adds the `consent.choice` column, the `subject.identityAuthority` column and the `privacyDirective` table; run `@c15t/cli self-host migrate` (or `createMigrator`) before deploying this version. See the [API reference](/docs/self-host/api/endpoints) for the read and privacy-directive routes.

## Privacy directives and identity

Anonymous GPC directives remain local until a real server subject exists.
Identification must not manufacture consent to establish that subject. The
transport queues pending association and privacy work; clear or disposal cancels
it. Successful local identification is not proof of remote persistence. Trusted
server identity linkage is required for associated-profile propagation.
