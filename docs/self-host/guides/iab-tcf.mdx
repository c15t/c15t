## Configure an IAB policy

IAB support needs both an IAB policy in the manifest and the client IAB add-on.
The server options alone do not install a TCF UI or generate a TC String in the
browser.

```ts title="c15t-backend.config.ts"
import { defineConfig, policyRulePresets } from '@c15t/backend';
import { createMemoryCacheAdapter } from '@c15t/backend/cache';

const url = process.env.DATABASE_URL;
if (!url) throw new Error('Set DATABASE_URL');

export default defineConfig({
  database: { dialect: 'postgres', url },
  trustedOrigins: ['https://app.example.com'],
  manifest: {
    policyRules: [policyRulePresets.europeIab()],
    iab: { enabled: true },
  },
  // The matched IAB rule asks for a list; this says where it comes from and
  // which vendors it may name.
  gvl: { cache: createMemoryCacheAdapter(), vendorIds: [3, 7, 41] },
});
```

Set `manifest.iab.cmpId` to the CMP ID your deployment is entitled to use. IAB
Europe assigns one when a company registers as a CMP
([register.consensu.org/CMP](https://register.consensu.org/CMP)); publishers
using a registered CMP do not need their own. Every TC String names the CMP that
wrote it, so a copied or placeholder ID attributes your users' consent records
to another provider and is not a staging-only shortcut.

Left unset, `/init` returns no CMP ID and the browser add-on does not mount, so
nothing writes a TC String. Set to a value outside the encodable range, an
integer from 2 to 4095, and `@c15t/iab` throws instead of encoding a string that
names no registered CMP.

Review the policy's location coverage and add other reviewed regional rules as
needed.

## Understand the two GVL paths

`manifest.iab` publishes IAB metadata and a GVL endpoint reference for clients
resolving a manifest locally. `gvl` configures the backend's own list loading
when `/init` resolves a matched IAB policy. Enabling one does not configure the
other's endpoint or cache automatically.

Both endpoint defaults are `https://gvl.inth.app`. If you operate a different
compatible endpoint, set `manifest.iab.endpoint` for manifest consumers and
`gvl.endpoint` for server initialization.

The backend requests the endpoint itself: the upstream publishes one document at
its root, and a per-language path such as `/de.json` answers 404. When
`gvl.vendorIds` is set and holds 500 ids or fewer, the scope travels as a
`?vendorIds=` query filter, so a scoped deployment fetches its own vendors
rather than all of them. Measured against the public list, a 32-vendor scope is
about 11 KB compressed against about 101 KB for the whole document. Above 500
ids the filter is withheld -- the query string would outrun the request-line
limit a CDN enforces and fail the whole consent surface -- and the full document
is narrowed by the same allowlist server-side instead, so a vendor outside the
scope is never served whoever did the filtering.

A matched IAB rule is what needs a list, so a matched IAB rule is also what
decides that `/init` carries one. There is no second switch to remember:
everything in the `gvl` block is read by server-side list loading and nothing
else, so writing the block is the opt-in. `gvl.enabled: false` is how you decline
while keeping the scope and cache in place, for a deployment that loads the list
somewhere else. If your rules resolve as IAB and there is no `gvl` block at all,
the backend serves no list and prints one line at startup saying so, because a
banner that names no vendors never complains about it on its own.

`gvl.vendorIds` is a ceiling and never a default. The backend does not fetch a
wider list than you configured in order to fill one in, and the allowlist is
applied to whatever comes back, so a vendor outside your scope is not handed to
clients whether the endpoint filtered or not. Leave it out and you are asking for
every vendor the published list carries.

A native app can ask for less. It declares the vendors it ships on each init
request:

```bash
curl -i 'http://localhost:3000/api/c15t/init' \
  -H 'x-c15t-country: DE' \
  -H 'x-c15t-vendors: 8, 46, 153'
```

For a request that resolves a matched IAB policy, the `gvl` in the response is
the intersection of that list and `gvl.vendorIds`. A vendor the app declares but
you never configured is not served. A request with no header, or with a header
the backend cannot read, gets the configured scope. The cap is 500 ids, and a
longer list is ignored rather than truncated.

The narrowing happens per request and after the cache lookup. Your upstream
fetch count stays whatever `gvl.endpoint` and `gvl.vendorIds` describe, however
many different scopes the devices in front of the backend declare.

Use a [cache adapter](/docs/self-host/guides/caching) to reuse fetched lists.
`gvl.ttlMs` defaults to one day. A failed upstream fetch or invalid document
produces a null GVL instead of failing the entire initialization request.
Verify how the client handles that state before deployment.

## Verify both initialization paths

Inspect `/manifest` for IAB metadata and the selected rule. Call `/init` with a
location covered by that rule and confirm the policy model is `iab` and the
response carries the `gvl` field. It is the only copy a device gets: nothing on a
phone fetches a list, so an absent field there is a disclosure surface with
nothing in it rather than a round trip the client can make up for. Test a
location outside the IAB rule so that the ordinary consent flow still works and
fetches nothing. Send a declared vendor scope too, and check that the `gvl` in
the response names those vendors and nothing the configuration excluded.

Connect the browser using the [IAB add-on guide](/docs/frameworks/react/iab/overview). Keep a
persistent way to revisit vendor and purpose choices. A preset and a served GVL
are technical configuration, not proof that an application satisfies TCF rules.
