All endpoints are relative to your configured `basePath` (e.g. `/api/c15t`).

## Policy contract header

Every response carries `x-c15t-policy-contract: 1`, the policy wire contract this backend produces. Clients send the same header to declare the contract they read. The `@c15t/core` transports send it on every request. A client that declares a contract this backend does not produce receives `policyResolution` as `failed` with reason `unsupported-contract`; a client that sends no header receives the backend compatibility response. That projection cannot repair stored grants in cached old code; invalidate and redeploy old clients before relying on new semantics. The header is on the CORS allowlist and exposed to browsers.

`x-c15t-version` stays telemetry only. Nothing is inferred from it.

<Callout type="info">
  The backend auto-generates interactive API docs at `{basePath}/docs` using your OpenAPI spec. Visit this URL in a browser to explore endpoints with a visual UI.
</Callout>

## GET /init

Returns the initial consent state for a client. This is the first call made by the frontend SDKs.

**Response:**

```json
{
  "jurisdiction": "GDPR",
  "location": {
    "countryCode": "DE",
    "regionCode": "BY"
  },
  "translations": {
    "language": "de",
    "translations": { "...": "..." }
  },
  "branding": "c15t",
  "gvl": null,
  "policyResolution": {
    "version": 1,
    "status": "matched",
    "policyId": "eu_opt_in",
    "matchedBy": "country",
    "policy": { "...": "..." },
    "fingerprints": { "policy": "…", "choice": "…", "notice": "…" }
  },
  "policySnapshotToken": "…"
}
```

| Field | Description |
| --- | --- |
| `jurisdiction` | Detected regulation (`GDPR`, `UK_GDPR`, `CCPA`, etc.) |
| `location` | Geo-location from IP address |
| `translations` | Server-side translations based on `Accept-Language` |
| `branding` | Branding configuration |
| `gvl` | Global Vendor List (if IAB TCF is enabled) |
| `policyResolution` | The v3 outcome: `unconfigured`, `matched`, `no-match` or `failed` (with a `reason`). `policy` is `null` for every status except `matched`. Always present |
| `policySnapshotToken` | Signed evidence of the decision, when `policySnapshot.signingKey` is configured. Sent back on `POST /subjects` |

The response is `Cache-Control: no-store` and varies on `x-c15t-policy-contract`.

## POST /subjects

Records a consent event. This is an append-only operation — every call creates a new consent record, and a replay of the same submission returns the record it already created.

**Request:**

```json
{
  "type": "cookie_banner",
  "subjectId": "sub_abc123",
  "domain": "example.com",
  "preferences": {
    "necessary": true,
    "measurement": true,
    "marketing": false
  },
  "choice": {
    "version": 3,
    "categories": {
      "marketing": {
        "value": false,
        "confirmedAt": 1707648000000,
        "basis": { "kind": "choice-v1", "fingerprint": "…" }
      }
    }
  },
  "givenAt": 1707648000000,
  "policySnapshotToken": "…",
  "metadata": {}
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `type` | string | Yes | `cookie_banner`, `privacy_policy`, `dpa`, `terms_and_conditions`, `marketing_communications`, `age_verification`, `other`. Legal-document types (`privacy_policy`, `dpa`, `terms_and_conditions`) also accept suffixed variants, e.g. `terms_and_conditions_b2b`, so multiple policies of one family can be active at once |
| `subjectId` | string | Yes | Client-generated subject identifier |
| `domain` | string | Yes | Domain where consent was given |
| `preferences` | object | No | The subject's explicit category values (for `cookie_banner` type). Granted categories fill `purposeIds`, as in 2.x |
| `choice` | object | No | v3 receipts for exactly the categories this act confirmed, each with the client's own `confirmedAt` and policy `basis`. Stored as sent |
| `givenAt` | number | Yes | Epoch milliseconds when the subject acted |
| `policySnapshotToken` | string | No | The token `/init` issued. Verified when present |
| `policyId`, `fingerprint`, `country`, `region`, `language`, `gpc` | mixed | No | Manifest-mode decision assertion. Recomputed through the same resolver `/init` uses |
| `metadata` | object | No | Arbitrary metadata |
| `externalSubjectId` | string | No | External user ID for cross-device linking |
| `identityProvider` | string | No | Identity provider name |

Timestamps are recorded as sent, never adjusted. `givenAt` and every `confirmedAt` must be a safe non-negative epoch millisecond integer no later than the server clock; a later value is a `400`, so a client clock ahead of the server is visible rather than silently rewritten.

A save without `choice` is the 2.x shape. The values in `preferences` are stored as `legacy-v2` receipts timed at `givenAt`, so a refusal such a client submitted survives. A save with `choice` stores the receipts it carries and nothing for categories it did not mention, so a partial save never renews a category the subject did not touch. A receipt that grants a category outside the resolved policy's scope is refused (`CHOICE_OUT_OF_SCOPE`); a refusal outside scope is kept.

**Decision evidence.** With `policySnapshot.signingKey` configured and a matching policy, a submission must carry the token `/init` issued: an invalid token is `409 POLICY_SNAPSHOT_INVALID`, a missing one is `409 POLICY_SNAPSHOT_REQUIRED`. Without a token, asserted manifest-mode inputs are recomputed; a mismatch or a partial set is `422 STALE_POLICY`. The decision is recorded on `runtimePolicyDecision` and linked from the consent.

**Response:**

```json
{
  "ok": true,
  "subjectId": "sub_abc123",
  "consentId": "cns_…",
  "domainId": "dom_…",
  "domain": "example.com",
  "type": "cookie_banner",
  "givenAt": "2024-02-11T10:40:00.000Z",
  "appliedPreferences": { "necessary": true, "measurement": true, "marketing": false }
}
```

A replay with the same identity but different `preferences` or `choice` is `400 CONFLICT`: the record is not silently rewritten.

## GET /subjects/:id

Retrieves consent status for a subject. The subject id is the capability; the route is unauthenticated, like the save.

**Query Parameters:**

| Parameter | Description |
| --- | --- |
| `type` | Comma-separated consent types to filter (e.g. `cookie_banner,privacy_policy`) |

**Response:**

```json
{
  "subject": { "id": "sub_abc123", "externalId": "user_12345", "identityProvider": "auth0" },
  "consents": [
    {
      "id": "cns_…",
      "type": "cookie_banner",
      "givenAt": "2026-02-11T12:00:00.000Z",
      "preferences": { "necessary": true, "measurement": true },
      "choice": { "version": 3, "categories": { "...": "..." } }
    }
  ],
  "isValid": true,
  "subjectChoice": {
    "version": 3,
    "categories": {
      "marketing": { "value": false, "confirmedAt": 1707648000000, "basis": { "kind": "choice-v1", "fingerprint": "…" } },
      "measurement": { "value": true, "confirmedAt": 1707561600000, "basis": { "kind": "legacy-v2" } }
    }
  },
  "privacyDirectives": [
    { "id": "pdr_…", "authority": "subject", "source": "gpc", "categories": ["marketing"], "recordedAt": 1707648000000, "signalHeader": true }
  ]
}
```

| Field | Description |
| --- | --- |
| `consents[].preferences` | Granted codes, as 2.x reported them |
| `consents[].choice` | The receipts that submission confirmed, exactly as sent. Absent on rows written before receipts existed |
| `subjectChoice` | The latest receipt per category across the cookie-banner consents, with each receipt's original time and basis. A row written by the 2.x backend contributes a `legacy-v2` grant for each code it holds and nothing for the rest: an absent code is historical omission, not a refusal |
| `privacyDirectives` | The standing privacy directives that apply to this subject. See below |

The `@c15t/core` hosted transport reads this route through `loadSubjectRecord(subjectId)` and hands the kernel hydration records with these facts intact.

## PATCH /subjects/:id

Links a subject to an external user ID for cross-device consent resolution. Who asserts the link is recorded: `api` when the request carries a valid API key, `browser` otherwise. Only an `api` link lets the subject read identity-level privacy directives. Links recorded before this distinction existed are untrusted.

The c15t transports call this route only for a subject that already exists on the server. A client identified before its first save carries the identity on `POST /subjects` instead, and the subject is created already linked (`browser` authority).

**Request:**

```json
{
  "externalId": "user_12345",
  "identityProvider": "auth0"
}
```

**Response:**

```json
{
  "subject": {
    "id": "sub_abc123",
    "externalId": "user_12345",
    "identityProvider": "auth0"
  }
}
```

## POST /subjects/:id/privacy-directives

Records a standing privacy directive for a subject from a user-agent signal (Global Privacy Control). A directive is a privacy request, not a consent: it writes no consent row, no runtime decision and no `consent_given` audit entry, and a later consent save never removes it. The `@c15t/core` transports call this route through `recordPrivacyOptOut`, never the consent-saving route.

**Request:**

```json
{ "source": "gpc", "categories": ["marketing", "measurement"], "recordedAt": 1707648000000 }
```

`categories` are optional categories (`necessary` is refused); `recordedAt` may not be later than the server clock. The directive reaches this subject only. Whether the request itself carried `Sec-GPC: 1` is recorded as `signalHeader`. No client IP or user agent is stored for a directive.

**Response:**

```json
{ "ok": true, "created": true, "directive": { "id": "pdr_…", "authority": "subject", "source": "gpc", "categories": ["marketing", "measurement"], "recordedAt": 1707648000000, "signalHeader": true } }
```

## GET /subjects/:id/privacy-directives

The directives that apply to a subject: its own, plus identity-level directives (below) when the subject's link to that identity was asserted through an authenticated request. A link a browser asserted through the public `PATCH /subjects/:id` never exposes another person's identity-level directives and never carries a directive onto another profile.

## POST /privacy-directives (Authenticated)

Records a directive for an external identity, so it applies to every subject holding a trusted link to `(externalId, identityProvider)` in this tenant. This is the only path that reaches beyond one subject.

**Request:**

```json
{ "externalId": "user_12345", "identityProvider": "auth0", "source": "gpc", "categories": ["marketing"], "recordedAt": 1707648000000 }
```

The response adds `subjects`, the number of subjects currently linked to that identity.

## GET /privacy-directives (Authenticated)

`?externalId=&identityProvider=` returns the identity-level directives for an identity, for a host that projects a person's standing privacy requests into its own session rather than through a browser-asserted link.

## GET /subjects (Authenticated)

List subjects by external ID. Requires an API key.

**Headers:**

```
Authorization: Bearer sk_live_abc123
```

**Query Parameters:**

| Parameter | Description |
| --- | --- |
| `externalId` | The external user ID to search |

**Response:**

```json
{
  "subjects": [
    { "id": "sub_abc123", "externalId": "user_12345" }
  ]
}
```

<Callout type="warn">
  This endpoint requires API key authentication. Configure API keys in the `apiKeys` option. The key is passed via the `Authorization: Bearer` header using timing-safe comparison.
</Callout>
