# c15t v3 — What It Is and Why

> Source-of-truth summary of the v3 re-architecture for PR reviewers, future
> migration docs, and content writing. Companion documents:
> `internals/rfcs/0001-consent-manifest.md` (manifest spec),
> `internals/rfcs/0002-provider-diet.md` (parked follow-up),
> `benchmarks/reports/gate-2026-07-05.md` (all benchmark numbers).

## The one-paragraph version

v3 is a **re-architecture of v2, not a feature release**. Same wire protocol,
same consent storage format — no site breaks, no visitor is ever re-prompted.
Under the hood: a zero-side-effect consent **kernel** shared by every
framework, a CDN-cacheable **consent manifest** that removes c15t from the
network critical path, a new **Vue/Nuxt integration** born on this
architecture, one **CSS system**, and a **cross-framework conformance suite**
that proves every adapter behaves identically. Every performance claim is
benchmarked, and the benchmarks killed as many ideas as they confirmed.

## The three guarantees

1. **Same wire protocol** — v3 clients speak `GET /init` + `POST /subjects` to
   every existing v2 backend, hosted or self-hosted.
2. **Same consent storage** — the kernel's persistence module writes the
   v2-compatible format (`c15t` cookie + localStorage). Upgrading never
   re-prompts a visitor. (This is tested, not promised: the conformance suite
   round-trips records between v2 core and every v3 adapter.)
3. **Same behavior, measurably faster** — the gate report is the release
   artifact: banner visible -19.6% to -22% vs v2 (React), banner in first HTML
   with CLS 0 on every SSR framework, and the manifest takes c15t's TTFB
   contribution from ~208ms to ~6ms at 200ms backend latency.

## v2 vs v3 at a glance

| | v2 | v3 |
|---|---|---|
| State | zustand store, side effects on construction (DOM probes, observers) | **kernel**: plain snapshot/subscribe, pure construction — no window writes, no network, no DOM until asked |
| Client | three baked-in client kinds (hosted/offline/custom) | pluggable **transports** (hosted / offline / manifest); custom = implement one interface |
| Side effects | entangled with the store | opt-in **modules**: persistence, script-loader, network-blocker, iframe-blocker |
| Init fetch | client → c15t backend, on the critical path | **manifest**: CDN-cached config + local resolution at the host's server/edge; direct `/init` remains the default & fallback |
| Framework adapters | per-framework re-implementations | thin adapters over one kernel; conformance-tested to behave identically |
| CSS | `@c15t/ui` precompiled monolith (all surfaces, always) | `@c15t/ui/styles/v3/*` CSS Modules — pay for what you render |
| SSR | banner mounts after hydration | banner in the first HTML, CLS = 0 (React, Next, Nuxt) |
| Packaging | packages: core, react, nextjs, iab, ui, … | same packages; v3 lives at **`/v3` subpaths** (`c15t/v3`, `@c15t/react/v3`, …) — unstable-by-path, root entries swap at v3 stable. `@c15t/config`, `@c15t/utils`, `@c15t/styles` dissolved into schema/kernel/ui |

## The kernel (`c15t/v3`)

The kernel is the consent engine every framework shares:

- `createConsentKernel(config)` — **pure construction**: no network, no DOM,
  no globals. Isomorphic-safe (Node/RSC/edge imports are clean);
  `sideEffects: false`.
- `getSnapshot() / subscribe()` — frozen snapshots, reference-equal when
  unchanged. React binds with `useSyncExternalStore`, Vue with a
  `shallowRef` + subscription, Svelte/Solid with their natives. This is why
  four frameworks pass one behavioral contract with thin adapters.
- `commands.init() / save() / identify()` — carried out by the configured
  transport; without one they're no-ops.
- **Consent-record model** (promoted from the Vue contractor's design — the
  strongest thinking on that branch): a policy-agnostic record storing only
  *explicit* user choices, with per-policy acknowledgements (policyId +
  fingerprint + timestamp). Interpretation happens at *read time* against the
  active policy — the same record travels EU → California without mutation
  (opt-in treats silence as denial, opt-out as permission). GPC honored;
  fingerprint change or expiry → re-prompt.

### Transports

| transport | what it does |
|---|---|
| `createHostedTransport` | `GET /init` + `POST /subjects` against a c15t backend — the v2 protocol, allowlisted headers only |
| `createOfflineTransport` | synthesizes init locally from policy packs — no backend at all |
| `createManifestTransport` | fetch-or-inline **manifest** → local resolution → same init shape; lazy GVL; sends decision inputs on save |

### Modules (opt-in side effects)

`persistence` (v2-compatible cookie/localStorage), `script-loader`
(consent-gated scripts), `network-blocker`, `iframe-blocker`. Adapters mount
them in effects; the kernel stays pure.

## The consent manifest (the headline)

**Problem:** every v2 page load does `client → c15t backend GET /init` before
the consent UI can resolve — a third-party, often cross-region round trip on
the critical rendering path (or worse, inside the host's SSR, adding 1:1 to
TTFB). Yet almost everything `/init` returns is per-tenant static data; only
geo, language, and GPC are per-request — and all three already sit in request
headers at the host's server/edge.

**Design (RFC 0001):** split `/init` into:

- **The manifest** — `GET /manifest`: geo-independent, CDN-cacheable
  (`s-maxage` + `stale-while-revalidate` + ETag), per-tenant document with
  **all** policy packs (each with a precomputed fingerprint), matching rules,
  translation inputs, branding, and the GVL **by reference** (fetched lazily,
  only in IAB jurisdictions).
- **Local resolution** — one shared, synchronous resolver in `@c15t/schema`,
  *extracted from the backend's own `/init`* and called by both the backend
  route and host middleware: `resolve(manifest, {country, region, language,
  gpc}) → InitOutput`. **Parity by construction** — there is exactly one
  implementation, plus a 24-cell byte-equal contract suite as regression
  insurance.
- **Audit via recompute-on-write** — manifest-mode saves carry the asserted
  decision inputs; `POST /subjects` re-derives the decision server-side and
  rejects stale/tampered fingerprints (409). Hosted-mode tokens unchanged.

**Non-breaking by design:** clients default to direct backend `/init` exactly
as today. Installing the Next route handlers (`@c15t/nextjs/v3/api`) or the
Nuxt module option upgrades them to same-origin manifest resolution. Static
sites inline the manifest at build time with a client geo microfetch;
degradation is always toward the *strictest* policy.

**Why it matters (measured):** direct-init SSR pays the consent backend's RTT
in the host page's TTFB (208ms at 200ms injected latency); manifest-SSR pays
~6ms. That's a **site-wide** TTFB/CWV/SEO claim, not just a banner claim.
Next client mode: 933ms → 713ms banner visible. Caveat we learned honestly:
under heavy CPU throttle, hydration hides network wins — manifest and
bundle-weight work **compound**; neither alone finishes the job.

## `@c15t/vue` (new package)

The first framework born on the v3 architecture, and the production pilot for
it (ships in the v2 release line — new package, v2 contract, kernel inside):

- **Nuxt module**: one line in `nuxt.config` + `<ConsentRoot />`. Injects
  cached Nitro routes for manifest mode (`/api/c15t/init` resolving locally
  from the cached manifest), registers auto-imported composables.
- **Framework-native I/O**: `useFetch` (SSR payload dedup — zero client init
  requests after hydration), `useCookie`, `useState`; a `#imports` stub-swap
  keeps a thin plain-Vue path.
- **Header hygiene**: only an allowlist (`accept-language`, geo headers,
  `sec-gpc`) is ever forwarded to the consent backend — never the host's
  cookies/authorization.
- **Manifest modes**: server (Nitro route) and full client mode (browser
  fetches the cached manifest once; **zero** init endpoint calls — the
  SPA/static tier).
- **Fastest measured host**: banner in first HTML, CLS 0, 39.5ms banner
  visible unthrottled.

## CSS: one system (`@c15t/ui/styles/v3`)

The Vue branch introduced per-component **CSS Modules** with `data-*`
state/variant conventions and CSS-custom-property tokens. An isolated
experiment (same page, byte-identical JS, only the CSS system swapped) settled
the question:

- **-67.5% CSS bytes** (10,061 → 3,268) for a banner site — because CSS
  follows code-splitting: IAB styles never ship to non-IAB sites
- Small consistent runtime wins (-3–4% banner visible, ~-13ms interaction)
- Structural wins: per-app hashed classes are immune to Tailwind/layer
  collisions (the repo's tw3/tw4 compat harnesses exist because the monolith
  is not); framework-neutral files; near-zero build pipeline

Decision: the modules live at `@c15t/ui/styles/v3/*.module.css` (merged into
the design-system package under the `/v3` convention; `@c15t/styles`
dissolved). Vue consumes them now; React migrates before the v3 major
(prereqs: port tw3/tw4 compat tests, precompiled fallback for non-transpiling
consumers). Public theming contract = `data-*` attributes + tokens, not class
names.

## The conformance suite (`internals/conformance`)

One behavioral spec, every framework must pass it identically: storage
identity (incl. the v2 round-trip = the no-re-prompt guarantee as an
executable test), network discipline (exactly-one init, header allowlist),
consent semantics (fingerprint/expiry/GPC matrix), events, i18n, SSR.

Status: **React 20/20 · Vue 20/20 · Solid 20/20 · Svelte 20/20 client**
(Svelte SSR is a documented todo — a vitest dual-compile constraint, not an
adapter gap). The drivers are thin projections over kernel snapshots — the
practical proof that the kernel-shared architecture works. Spec-first rule
going forward: v3.x features extend the spec before any framework implements.

## Benchmarks & the gate

Full report: `benchmarks/reports/gate-2026-07-05.md` (7 iterations/scenario;
mobile = 4× CPU + Fast-4G; 200ms injected backend latency; single machine,
localhost, fixture backend — relative comparisons only).

| Gate | Verdict |
|---|---|
| SSR: banner in first HTML + CLS=0 | **PASS** — all v3 arms (v2 fails it by design; that contrast is the feature) |
| Manifest ≥150ms @ 200ms latency | **PASS** — Next client -220ms; SSR TTFB 208→5.9ms |
| No regressions | **PASS** — interaction 30.3ms vs v2's 52.9 unthrottled; repeat-visitor -21.6% |
| First Load JS -25% | **FAIL** — v3 is -1.6% vs v2 (lighter *while adding* transports/manifest/SSR); -25% belongs to a future slim entry |

Harness improvements shipped alongside: latency injection, CPU/network
throttling, CLS + banner-in-first-HTML + TTFB decomposition metrics, mitata
micro-benches in the pipeline, Nuxt bench host, arm mapping for v3↔v2
comparisons, honest per-request direct-init arms.

## Things the measurements killed (kept deliberately)

Recording the falsified hypotheses is the point of the discipline:

- **RSC-first banner**: built (`@c15t/nextjs/v3/rsc`), measured ≈ zero — the
  client cost is dominated by the provider/kernel graph, not banner markup.
  Kept as an optional pattern, not a recommendation.
- **Legacy-compat cut** (`@c15t/react/v3/compat`): 0 bundle bytes (already
  tree-shaken) — shipped anyway as a guarantee (kernel apps can't accidentally
  pull the v2 runtime), not as savings.
- **Provider "bloat"**: the eager path (14.8KB gz) contains only reachable
  features. The remaining diet requires a kernel API change — parked with a
  full spec in RFC 0002.
- **Chunk warm-on-intent**: real for human hover-to-click gaps, invisible to
  synthetic clicks. Shipped; unmeasurable in CI.

And one accidental find worth more than several optimizations: **rslib strips
`'use client'` from dist files**, breaking any Server Component that imports
package client modules. Fixed with a post-build directive-restore step
(`packages/shared/restore-client-directives.mjs`) — 332 files in
`@c15t/react` alone.
