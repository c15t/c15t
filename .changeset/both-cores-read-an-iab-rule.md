A device under an IAB policy now asks instead of refusing. Both native cores used to reject the wire model `iab` as a contract they did not speak, which left a subject under an IAB rule looking at a deny-all snapshot with an unreadable policy. Both read it now and evaluate it with the web kernel's own answer: `defaultPermission` in `@c15t/core` grants an in-scope category only under `opt-out` or `none`, so an IAB rule still leaves every optional category denied until the subject makes a choice, `necessary` stays granted, and a rule carrying a prompt or a preselection that `@c15t/schema` forbids beside `iab` is refused rather than approximated. A model name neither core knows fails closed exactly as it did before -- only `iab` stopped being unsupported. The snapshot reports `opt-in` while an IAB rule is in force, following `deriveModel` in `@c15t/core`, because the name `iab` advertises a vendor-side record the device cannot produce: the `tcString` row of the storage bus stays reserved and no `tcString` goes on the save body, since a TC String has to open with a CMP ID IAB Europe assigned and this build holds no registered one. Nothing about the matched rule is hidden -- `resolution` still names the IAB policy and `iab.gvl` still carries the vendor list `/init` served.

Two bytes move with this, and only values move: no key appears on the save body, the snapshot, or the stored envelope that was not there before. The save body's `jurisdictionModel` now arrives as `opt-in` from a device whose matched rule is IAB, where that write used to carry the safe fallback because the rule was never readable. `IABTCF_gdprApplies` goes to `1` on the storage bus under a stored IAB rule, which is `packages/iab`'s own test (`policyRule.model === "iab"`) applied to the rule in the envelope rather than to the model the device reports; every other model keeps the `0` it already wrote. `IABTCF_PolicyVersion` and the rest of the table are untouched.
