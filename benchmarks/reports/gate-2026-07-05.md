## Gate evaluation

### G1 — First Load JS ≥25% lighter (banner scenario): **FAIL (improved, threshold missed)**
v3-react-full is 93,206 bytes gzip vs v2's 94,742 (**-1.6%**). v3 reversed an earlier +18.6KB regression and now ships less than v2 while adding capability (kernel transports, manifest resolution, SSR banner). Reaching -25% is a scope decision (dropping the aggregate/compat surface), not an optimization pass. Recommendation: keep the gate as a target for the slim entry (`banner-only`/headless arms), re-baseline the full-UI gate to "≤ v2".

### G2 — SSR: banner in first HTML + CLS=0 (v3 arms): **PASS**
| arm | firstHtml | CLS | TTFB | visible |
|---|---|---|---:|---:|
| nextjs/ssr (v2 baseline) | 0 | 0 | 6.4ms | 776.4ms |
| nextjs/nextjs-v3-ssr | **1** | 0 | 208.3ms | 762.6ms |
| nextjs/nextjs-v3-manifest-ssr | **1** | 0 | 5.9ms | 729.0ms |
| nuxt/ssr | **1** | 0 | 205.7ms | 975.1ms |
| nuxt/ssr-manifest | **1** | 0 | 3.9ms | 950.3ms |

Every v3/Nuxt SSR arm renders the banner in the server HTML with zero CLS. The v2 baseline does not — that contrast is the improvement being shipped.

### G3 — Manifest ≥150ms faster at 200ms backend latency: **PASS (Next client & SSR-TTFB); bounded on Nuxt client**
- **Next client: 933.2ms → 713.3ms = -219.9ms (-23.6%)** — exceeds the 150ms threshold. v3-direct measured 717.0ms: on this arm most of the win comes from v3''s lighter/earlier pipeline; the manifest removes the remaining request. 
- **TTFB decomposition (SSR): direct-init pays the backend RTT in TTFB (208.3ms / 205.7ms), manifest does not (5.9ms / 3.9ms) — a -202ms TTFB improvement for the entire page**, not just the banner. This is the cleanest expression of the manifest claim: direct-init SSR delays the host page''s first byte by the consent backend RTT; manifest-SSR removes c15t from TTFB entirely.
- Nuxt client: 1312.9ms → 1265.0ms (-47.9ms): under 4× CPU throttle, hydration dominates and the init fetch overlaps script execution, so network savings compress. The manifest win expresses fully only when JS is light — bundle work and manifest work compound.

### G4 — No regressions (interaction, repeat-visitor, longtasks): **PASS**
- interactionLatency — A: v2 52.9ms vs v3 **30.3ms** (v3 43% faster) · B: v2 94.4ms vs v3 95.2ms (parity)
- repeat-visitor bannerVisible — A: 62.7 → **49.1ms** · B: 949.5 → **744.1ms** (-21.6%)
- full-ui bannerVisible — A: 61.7 → **49.6ms** (-19.6%) · B: 949.2 → **740.8ms** (-22.0%)

## Addendum A — CSS-approach experiment (isolated), 2026-07-05

**Question:** does the `@c15t/styles` CSS-Modules approach (Vue) outperform the `@c15t/ui` precompiled monolith (React) — CSS alone, all else equal?

**Method:** one bench page (`react-v3-banner-css`), two builds differing ONLY in two module resolutions (`bench-css-entry` + banner style-map alias; webpack & turbopack aliases). Same JS, same DOM, same data-testids. 7 iterations per condition. NOTE: this experiment also revealed that **all other react-bench arms load no stylesheet at all** (class maps without CSS) — v2↔v3 comparisons were internally fair, but absolute numbers understate real pages, and Nuxt arms (which do bundle CSS) competed with a handicap.

| metric | @c15t/ui monolith | @c15t/styles modules | delta |
|---|---:|---:|---:|
| CSS transfer bytes | 10,061 | 3,268 | **-67.5%** |
| bannerVisibleMs (A: unthrottled/0ms) | 76.7 | 73.4 | -4.3% |
| bannerVisibleMs (B: mobile/200ms) | 848.6 | 821.0 | -3.3% |
| interactionLatencyMs (A / B) | 79.0 / 135.4 | 66.1 / 122.5 | ~-13ms both |
| CLS | 0 | 0 | = |
| CSS requests | 1 | 1 | = |

**Verdict:** CSS system alone is worth **-67% CSS bytes** and a small consistent runtime win (~3-4% banner visible, ~13ms interaction) — not a headline, exactly as predicted. The decisive arguments remain structural: CSS follows code-splitting (IAB CSS never ships to non-IAB sites), per-app hashing is immune to Tailwind/layer collisions (the tw3/tw4 harnesses exist because the monolith is not), framework-neutral files, near-zero build pipeline. **Recommendation: React v3 adopts `@c15t/styles`; the "one CSS system survives" rule resolves in favor of `@c15t/styles`.** Prerequisites: packaging story for non-transpiling consumers + port tw3/tw4 compat tests before the switch.

## Addendum B — v3 CSS modules in situ, 2026-07-06

**Question:** what is the real consumer impact now that `@c15t/react` v3 natively consumes `@c15t/ui/styles/v3` precompiled modules, with no aliases?

**Method:** new in-situ benchmark arms, not an aliased experiment. v2 arm imports root-entry React components plus `@c15t/react/styles.css`. v3 arm imports split v3 subpaths and relies on the shipped `@c15t/ui/styles/v3/*` JS modules to pull their CSS. React browser bench uses the same 7 measured iterations + 1 warmup and the same conditions as the gate report: **A** = no throttle, 0ms init latency; **B** = mobile profile (4x CPU, Fast-4G) + 200ms init latency. Bundle analysis now counts both route JS scripts and route CSS links from `.next` and reports gzip bytes.

### Runtime: banner-only, real styles loaded

| metric | v2 root + monolith CSS | v3 subpath + modules | delta |
|---|---:|---:|---:|
| CSS transfer bytes | 10,361 | 7,642 | **-26.2%** |
| CSS requests | 2 | 3 | +1 |
| bannerVisibleMs (A) | 76.5 (p95 91.2) | 42.5 (p95 45.4) | **-44.4%** |
| bannerVisibleMs (B) | 1059.2 (p95 1066.5) | 867.7 (p95 873.3) | **-18.1%** |
| bannerPaintMs (A / B) | n/a / n/a | 20 / 408 | v2 did not emit element timing |

| CLS (A / B) | 0 / 0 | **0.006 / 0.006** | under <0.01 threshold |

**Readout:** v3 in situ is materially faster on banner visibility and interaction, and ships fewer CSS transfer bytes. The CSS byte win is smaller than Addendum A because this is a real Next route with framework chunking and headers, not a one-file CSS isolation build. The original v3 CLS caveat is resolved below the `<0.01` gate threshold. A focused `LayoutShift.sources` probe showed the shifted node was `[data-testid="consent-banner-root"]`: before the fix the root moved from an oversized frame near the top of the viewport (`y=4`, `height=716`) to the bottom-left banner (`y=503`, `height=217`) when the late `consent-dialog.css` chunk loaded through lazy shared branding, producing `0.217` CLS; a second `0.003` shift came from late branding insertion. The fix makes banner branding eager and gives the banner shell a stable viewport-bounded width, leaving only a sub-threshold `0.006` height adjustment when async policy actions resolve.

### Verdict

The shipped v3 CSS-module architecture preserves the structural win: banner CSS is much smaller (**-58.9% gzip in the route build**) and IAB CSS can be deferred until the lazy IAB UI opens. End-to-end banner route bytes are roughly flat because JS offsets the CSS savings. Runtime visibility improves consistently, and the banner-only v3 fixture now stays under the CLS gate (`0.006` in both A and B). The previous blocker was paint-before-complete-banner-styles from lazy shared branding plus content-driven shrink-wrap sizing of the banner root; both are fixed in product code rather than in the benchmark fixture.

## Addendum D — authoritative-only banner: CLS 0 by design, 2026-07-06

**Question:** the residual v3 banner CLS (0.0057 → 0.00226 after the kernel
translations-merge fix) came from the optimistic pre-init banner's copy swap.
What does eliminating optimistic rendering cost, and does it reach CLS 0?

**Change under test:** the kernel gained `policyProvisional` — a placeholder
policy (the React provider's synthetic categories fallback in hosted mode)
keeps `activeUI='none'` until init completes; init failure promotes the
placeholder as the compliance fallback. Authoritative initial policies
(prefetch/SSR/manifest/offline config) are unaffected and still render at
first paint/HTML. To avoid paying hydration + init roundtrip back-to-back,
the React provider dispatches init at kernel creation (client render-time)
instead of a post-hydration effect. Also in this window: `transport.save`
defers one macrotask so the consent commit paints before the network call.

### Results (css-v3-banner-modules probe + full arms, condition B paired runs)

| metric | before (optimistic) | after (authoritative-only) |
|---|---:|---:|
| CLS (5-run probe) | 0.002259 (deterministic) | **0.000000 — zero LayoutShift entries** |
| banner visible B — v3 full | 878-895 (placeholder visible pre-init) | 1053.1 (real copy; v2 same-run: 962.9) |
| interaction B — v3 vs v2 | parity (95.2 vs 94.4 gate-era) | **89.3 vs 99.5 (-10.2%)** |

### Readout

- **CLS is exactly 0** on the hosted-client arm — the banner paints once,
  with final copy. Every v3 arm on every host now measures CLS 0.
- **The old B-condition banner-visible "win" was placeholder-driven.** The
  optimistic banner showed default copy ~200ms before init resolved; time to
  the *correct* banner is unchanged. The honest post-change number is
  **+90ms vs v2** (1053.1 vs 962.9 same-run) in legacy hosted-client mode —
  the price of never showing copy the user isn't actually consenting under,
  never swapping text mid-read, never flashing a banner the resolved policy
  suppresses, and never recording consent against a placeholder policy
  without a snapshot token. Eager init dispatch already recovered ~43ms; the
  remaining gap is dispatch/bundle-weight (RFC 0002 territory).
- **Manifest and SSR arms are untouched** — they resolve locally/server-side,
  keep first-paint banners, and were already CLS 0. They remain the
  recommended integration and carry the v3 performance story.
- Interaction stays ahead of v2 after the save-deferral (-10.2% this pairing).

### Verdict

Ship. CLS 0 across the board and consent-integrity guarantees beat a ~90ms
banner delay on the legacy path; the recommended paths lose nothing.

## Addendum E — desktop-real condition + framework/c15t decomposition, 2026-07-06

**Question:** condition A (unthrottled, 0ms backend) isolates compute but no
real deployment has a 0ms consent backend. What do the SSR arms look like on

each number is the host framework vs c15t?

paint floors remain the known open item. 7 iterations, medians, current tree
(post authoritative-only banner).

- **Framework dominates the absolutes.** The zero-consent shells hydrate at

compute-isolation lab condition. Harness note: the per-suite runners write
`<scenario>-<condition>.json` — same-named scenarios (`baseline`, `ssr`)
collide across suites when sharing one `BENCH_OUTPUT_DIR`; use per-suite
dirs (the default `bench` scripts already do).
